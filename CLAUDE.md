# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build entire solution
dotnet build iTerminal.slnx

# Run all tests (all test projects)
dotnet test iTerminal.slnx

# Run a specific test project
dotnet test iTerminal.Core.Test/iTerminal.Core.Test.csproj
dotnet test iConsole.Test/iConsole.Test.csproj

# Run the end-to-end suite: the whole app on a virtual terminal (~4-5 minutes, sequential)
dotnet test iTerminal.Test/iTerminal.Test.csproj

# Run a single test by name filter
dotnet test iTerminal.Core.Test/iTerminal.Core.Test.csproj --filter "FullyQualifiedName~FilePanelRefreshTask"

# Run the app
dotnet run --project iTerminal/iTerminal.csproj

# Build the Windows installer (Windows only; publishes the app first, ~5 minutes)
dotnet build iTerminal.Installer/iTerminal.Installer.wixproj -c Release -p:Version=1.2.3

# Build the Linux packages: tar.gz, deb and rpm (on Windows or Linux; ~5 minutes per runtime)
dotnet build iTerminal.Packaging.Linux/iTerminal.Packaging.Linux.proj -p:Version=1.2.3
dotnet build iTerminal.Packaging.Linux/iTerminal.Packaging.Linux.proj -p:Version=1.2.3 -p:Runtimes="linux-x64;linux-arm64"
```

Targets `net10.0`, nullable enabled. The `.slnx` is the source of truth for the project set; `iConsole.Inputs.Posix.Test` is marked non-building there (it only compiles on Linux). `Tools/clean.cmd` wipes all `bin`/`obj`/`TestResults` folders.

Runtime state lives outside the repo: the SQLite database (settings, folder cache, music library index, document index, portfolio, vault) is at `%APPDATA%/iTerminal/iTerminal.sqlite`, created on first run by `DatabaseInitializationHostedService`. The `DataDirectory` configuration key (`iTerminalApplicationBuilderExtension.DataDirectoryKey`) moves that folder — database, vault keys and playlists together; the end-to-end tests point it at a temporary folder so a run never touches the user's own.

`DatabaseInitializationHostedService` compares a hash of the EF model against the stamp in the `DatabaseMetadata` table and recreates the whole database when they differ — the app carries no migrations, so a model change means the cached tables are dropped. **That stamp must stay out of the `Settings` table.** `SettingsService` owns that table: it reads it whole at start-up and writes its cache back whole, so a stamp kept there is read into the cache before the initializer can replace it and written back over the new value afterwards. The check then fails on *every* run, and everything cached in the database — the music library index, the playing queue, the folder cache — is thrown away at every start-up, while the settings themselves survive in the cache and hide it. `SettingsService` treats any `__`-prefixed key as reserved for exactly this reason: it neither caches nor republishes one.

## Architecture

The core dependency chain is three layers: `iConsole` ← `iTerminal.Core` ← `iTerminal`. Two platform input plug-ins (`iConsole.Inputs.Posix`, `iConsole.Inputs.Windows`) also depend on `iConsole` and are selected at startup. `iConsole.Demo` is a standalone sample app for `iConsole` in isolation.

### `iConsole` — reusable terminal UI framework
General-purpose TUI infrastructure with no knowledge of file managers. Key subsystems:

- **Controls** (`iConsole/Controls/`): `Window` is the base for all interactive UI panels. Controls handle `HandleKeyEventAsync` and render into a buffer.
- **Commands** (`iConsole/Commands/Command.cs`): User actions. Override `Key`, optionally `CanExecute()`, and `ExecuteAsync(object? args)`. Commands are attached to controls and dispatched by the key router. `Command.RunAsync` wraps execution with `CanExecute` gating, exception capture, and `ICommandLogger` recording — dispatch through it, not `ExecuteAsync` directly.
- **Jobs** (`iConsole/Jobs/Job.cs`): Long-running background loops (rendering, keyboard polling, network info). Each `Job` subclass implements `RunIterationAsync`. Jobs are registered as `IJob` singletons and run on the `Desktop` lifecycle, not the `TaskManager`.
- **TaskManager** (`iConsole/Tasks/TaskManager.cs`): Priority queue (`Rendering=0 > Input=1 > Background=2`) with multiple worker threads. Used for one-shot async work (directory enumeration, file copy). `BackgroundTask` is the base; override `ExecuteAsync()` and `Priority`.
- **Data types** (`iConsole/Data/`): `Url`, `Container` (URL scheme constants), `KeyEvent`, `Position`, `Size`, `ConcurrentObservableCollection<T>` (thread-safe, `ReplaceAll` for atomic batch swaps), `ConxelString` (styled character strings for rendering).
- **Services** (`iConsole/Services/`): `IDateTimeProviderService` (cached `DateTime.Now`), `IFrequentExecutionGuardService` (throttles `PropertyChanged` to max ~20/s), `IStopwatchFactory`/`IStopwatch` (injectable timing), `IThemeService`, `IErrorPromptService`.
- **Notifications** (`iConsole/Services/INotificationService.cs`, `Jobs/NotificationJob.cs`, `Controls/Toast.cs`, `Controls/ToastHost.cs`): self-dismissing toasts posted from any thread — see "Notifications and toasts" below.
- **Diagnostics** (`iConsole/Diagnostics/`): `ICommandLogger`/`IScreenLogger` capture command executions and rendered screen snapshots for agentic/behavioural tests. `AddiConsoleCore` registers the `Null*` no-op implementations by default; `iConsole.Test.Core` provides `InMemoryCommandLogger`/`InMemoryScreenLogger`, and `AppHarness` wires those in so tests can assert on what ran and what was drawn.

### Notifications and toasts (`INotificationService`, `NotificationJob`, `ToastHost`)
A notification is a short message the app shows without stopping the user: a title, an optional message and a severity (`Info`, `Success`, `Warning`, `Error`). Any code posts one with `INotificationService.Notify` — from any thread, returning at once — and it appears as a `Toast` in the top right corner, over panels, dialogs and menus alike, then leaves by itself (4 s; a warning 6 s, an error 10 s; `Timeout.InfiniteTimeSpan` stays until dismissed). A click dismisses it. It never takes focus or a key.

- **Three parts, and only the first is needed to post.** `NotificationService` (iConsole, singleton) holds the lists: at most `MaxVisible` (4) on screen, the rest waiting their turn with their time not yet started, and a capped `History`. `NotificationJob` is the clock: every 100 ms it hands the service the time that passed (`Advance`). `ToastHost`, a control on the screen's root, draws `Active`. `AddiConsoleCore` registers all three; a screen only has to add the host (`TerminalScreen` takes it as an optional constructor argument).
- **Time is handed to the service, not read by it** — which is what lets the job stop it while the terminal is lent to a shell (`ConsoleOwnership.IsLent`): a "copy finished" that expired behind Ctrl+O would never have been seen. It is also what makes the service testable without a clock. The first `Toast` counted `OnIdle` calls instead, and an idle pass is not a length of time: a thousand a second on a quiet screen, none while a dialog repaints.
- **`ToastHost` synchronises from `OnIdle`, by polling `INotificationService.Version`.** Notifications are posted from task workers, and attaching a control there would race the renderer walking the tree — the same reason `ProgressWindow` closes itself from `OnIdle`. It must do nothing when the version has not moved: touching the tree moves `Control.TreeVersion`, and a host that did so on every idle pass would have the screen repainted from scratch for as long as a toast was up.
- **Each toast is a control of its own, attached and removed.** A layer is never cleared between frames, so one rectangle that merely drew fewer rows would leave the expired toast on screen; attaching and removing is what triggers the repaint from scratch.
- **The stack sits one layer above everything else on screen, worked out rather than fixed** (`ToastHost.ApplyZOrder`: the highest Z-order among the host's visible siblings, plus one, re-checked on every idle pass while a toast is up). A fixed high Z-order would cost a buffer layer for every number below it; and a dialog can open over the panels while a toast is showing.
- **A click reaches a toast only because `TerminalScreen.HandleMouseEventAsync` offers it to the host first**: the base implementation offers a click to the children in the order they were added, and the panel under the toast would take it. With a dialog open the mouse goes to the dialog, so a toast is not clickable then — it still expires.
- **Toasts use no frame characters.** `AssertNoStrayFrames` in the end-to-end suite reads any `╔╗╚╝║` outside the panels as the ghost of a closed window.
- **Every operation with a progress window announces how it ended** (`TaskNotificationHelper.NotifyWhenFinished`, armed by `ProgressWindowFactory.Create`): copy, move, delete, compress, extract and their batches — success, cancelled (warning) or failed (error, with `BackgroundTask.Error`). The window is gone the moment the task succeeds, or earlier when the user closed it to get on with something else, which is the case a notification is for. It checks the status when armed as well as subscribing: a small local copy is over before the window is built. The text comes from the task's `Description` (a heading, what it was done to, and a last line saying how it ended — or one sentence that says everything) and from `BackgroundTask.Subject`, the few-word form ("readme.txt to target") a task sets because two whole paths do not fit a toast. A new task meant for a progress window should set `Subject`.
- **Post a notification for what finishes behind the user's back, not for what they are looking at.** A dialog's own footer or the panel's footer is still the place for the result of a key just pressed there.

### Rendering pipeline
Two `JobPriority.Rendering` jobs run continuously and are deliberately decoupled — nothing renders synchronously from a key handler:

1. `ControlRendererJob` walks each `Screen`, collects controls whose `HasStateChanged` is set, renders them into per-Z-order `BufferLayer`s, then `Buffer.Merge()`s them into `MergedLayer` (only when something actually rendered — merging blank new layers would blank the screen).
2. `ConsoleBufferRendererJob` diffs `MergedLayer` against `LastBuffer` line by line (SIMD byte compare), batches runs of changed cells into single `IConsoleDriver.Write` calls, and detects terminal resizes. Both jobs force a full redraw every second as a safety net.

Set the `ITERMINAL_RENDER_DUMPS` environment variable to dump up to 100 frames (buffer contents, render steps, and a reconstructed "what the console actually received" snapshot) to `%TEMP%/iTerminal/renderer-dumps` — the fastest way to debug a visual glitch.

`Buffer.SyncLock` guards the layer array; take it around any resize or merge.

### Lending the terminal to a child process (`ConsoleOwnership`, Ctrl+O)
Ctrl+O hands the *whole* terminal to an interactive shell and takes it back when the shell exits — prompt, line editing, colours, `vim`, `top`, Ctrl+C, all the child's. The app's own terminal panel (now Ctrl+Shift+O, the "command log") cannot be that: it runs one command at a time with its output captured.

- **`ConsoleOwnership` (iConsole, singleton) is the app's claim on the terminal.** The loops that touch it — `ConsoleBufferRendererJob` (writes) and the input readers (`MouseEventPublisherJob`, `PosixTerminalInputPublisherJob`, the polling `KeyboardEventPublisherJob`) — bracket each pass with `TryBeginUse`/`EndUse` and skip the pass when refused. `LendAsync` refuses new passes, waits for the ones under way (a frame, or one 50 ms input wait), then calls every `IConsoleHandoverParticipant`'s `OnConsoleReleased`, runs the borrower on a thread of its own, and calls `OnConsoleReacquired` in reverse — also when the borrower throws. Lends are serialised. A new loop that writes to or reads from the real terminal must take part, or it will draw over the shell or steal its keys.
- **Each participant undoes exactly what it did.** The drivers (every `IConsoleDriver` is a participant; the defaults do nothing) reset colours, clear and show the cursor, and on return put back the colours they believe are set, re-enable VT processing on Windows (the child may switch it off) and clear. The Windows reader gives the console its *original* input mode back (captured before it turned mouse input on and quick edit off) and on return re-applies its own and `FlushConsoleInputBuffer`s — the Enter that ended `exit` is still releasing. The Linux reader leaves raw mode, mouse reporting and non-blocking stdin, and re-enters them (`TCSAFLUSH` drops what was typed). The renderer marks every cell of `LastBuffer` unknown so the next pass repaints the whole screen: a diff against the frame from before the shell would leave the shell's text wherever the panels happened to match.
- **Ctrl+C, Ctrl+\ and Ctrl+Z belong to the child** (`ConsoleInterruptShield`). They reach every process on the console or in the foreground group — the app too, and the generic host's console lifetime stops the app on Ctrl+C. Handlers cannot prevent that (all of them run, the host's among them), so the signal is ignored at the OS level: `SetConsoleCtrlHandler(NULL, TRUE)` on Windows, `sigaction(SIG_IGN)` on Linux with the runtime's own handler saved opaquely and put back (`signal()` would reinstall an `SA_SIGINFO` handler with the wrong calling convention). It is raised only *after* the child has started — an ignored Ctrl+C is inherited.
- **Where the shell runs is the panel's to say** (`IShellLaunchSource.GetShellLaunch`): a local folder starts the user's shell there (the `Shell` setting; else `pwsh` on PATH, else `%ComSpec%`, on Windows — Windows PowerShell 5 is too slow to start for a key that should feel instant — and `$SHELL` elsewhere); the git drive uses the repository's working tree and the archive drive the archive's folder; docker is `docker exec -it -w <folder> <c>` with bash if the image has it and sh if not; ssh is the system's `ssh -t user@host "cd '<folder>' && exec $SHELL -l"`, so it authenticates the way the user's ssh does, not with the drive's saved credentials. Any other panel gets a local shell in the home folder.
- **`InteractiveShellService` adds what a person needs around the handover**: a line saying where the shell runs and that `exit` returns, and — when the program cannot start, or fails within `QuickExit` (no Docker, a stopped container, a refused login) — its message and "Press Enter", since the repaint would otherwise wipe it unread. `InteractiveShellCommand` only *starts* the session (the key handler returns at once) and refreshes every panel once it is over: only the local drive notices its own changes. The end-to-end suite replaces the service with `SandboxServices.Shell`, which borrows the terminal through the real `ConsoleOwnership` and writes onto the virtual screen — so the renderer standing still, and repainting everything afterwards, are what the test sees.

### Platform input plug-ins — `iConsole.Inputs.Posix` / `iConsole.Inputs.Windows`
Each supplies an `ITerminalInputSource` + input-consumer `IJob` and a DI extension called from `Program.cs`: `AddLinuxTerminalInput()` (Linux, ANSI/SGR mouse + raw stdin) and `AddInputWindowsAsync()` (Windows). The Windows path is feature-gated by `WindowsConsoleDriver` (via `Microsoft.FeatureManagement`, config in `appSettings.json`); when off — and on all non-Windows/non-driver paths — it falls back to `AddPollingConsoleKeyboard()`.

### `iTerminal.Core` — file-manager and terminal behavior
Built on top of `iConsole`. Key subsystems:

- **Content models** (`iTerminal.Core/Model/ContentModels/`): Implement `IContentModel` (extends `IScrollableModel` + `IFileSystem`). `ContentModelBase` holds `Entries` (`ConcurrentObservableCollection<IEntry>`), `FilteredEntries` (cached snapshot), cursor/scroll state, and `Update()` (notifies UI after state change). One implementation per drive kind — see the URL-scheme table below.
- **ContentModelService** (`iTerminal.Core/Services/ContentModelService.cs`): Owns the left/right panel models (`"LeftPanel"`/`"RightPanel"`), tracks focus, remembers per-URL cursor positions, and swaps the model instance when a navigation crosses drive kinds.
- **File panel controls** (`iTerminal.Core/Controls/Contents/`): `FilePanel` → `ContentPanel` → `Window`. `ContentBrowser` renders the entry list; `ItemInformation` shows file counts and metadata.
- **Tasks** (`iTerminal.Core/Tasks/`): `FilePanelRefreshTask` enumerates a directory (memory cache → SQLite `FolderContentsCache` → filesystem), streams results in 50-item batches, and runs prefetch for neighbouring folders at `Background` priority. `FileInformationRefreshTask` counts files recursively. Copy/move/delete run as pipelines (`FolderCopyPipeline`, `FolderDeletePipeline`) fed by discovery tasks.
- **Services** (`iTerminal.Core/Services/`): `SettingsService` is SQLite-backed (key/value via EF Core, `iTerminalDbContext`); a no-arg constructor creates a temporary in-memory DB for tests. `MemoryCacheService` wraps `IMemoryCache` with a 5-second default TTL (overridden to 5 minutes for prefetch). `IVaultService` stores remote credentials and `INetworkProfileService` stores host profiles — SSH/SMB models resolve credentials through those, never from the URL alone. Feature services back the dialogs below and are async by contract (never touch the render thread): `IGitService`, `IDotnetSolutionService` (`dotnet build/test/run`), `IPackageManagerService` (WinGet on Windows / Apt on Linux, chosen at registration), portfolio + quote providers, `WeatherService`, and `IChatClient`/`IAiChatService`. Every provider is one OpenAI-compatible endpoint behind `AiChatClientFactory` (Microsoft.Extensions.AI's OpenAI adapter, Ollama included through its `/v1`); `AiProvider.None` registers a client that refuses every call and the availability check says AI is off.
- **Jobs** (`iTerminal.Core/Jobs/`): Periodic refreshers feeding status-bar and dialog models — `DriveInfoJob`, `NetworkInfoJob`, `FolderIndexJob`, `MusicLibraryIndexJob`, `DocumentLibraryIndexJob`, `OnlineQuoteJob`, `PortfolioQuoteJob`, `WeatherJob`, `RuntimeDependencyCheckJob`, `OllamaServerJob`, plus `SettingsSynchronizationJob` and `MemoryDriveSynchronizationJob` which flush in-memory state to SQLite. A job must not make a blocking call on its own thread that cannot be cancelled — the host gives shutdown five seconds, and `DriveInfoJob` asking `DriveInfo.IsReady` there (seconds on a card reader or a sleeping disk) held every F10 Quit for all five; such calls go on a task the job waits for cancellably.
- **Dialogs** (`iTerminal.Core/Dialogs/`, commands in `iTerminal.Core/Commands/`): The app's modal features (Git client, solution viewer, calculator, unit converter, portfolio, process/task/disk/network/theme/settings managers, file operations, etc.). Each is a `Dialog` registered as transient in DI and opened by a `ShowDialogCommand<TDialog>` subclass that declares its `Key`, `Title`, `Description`, and optional `OnBeforeShow`/`CanExecute`. Notable keys: Shift+F1 command palette, F2 terminal, Shift+F2 compare folders, F3 view (opens `SolutionViewerDialog` on `.slnx`/`.sln` and `MusicFileViewerDialog` on a local audio file), Shift+F3 open with, Ctrl+F3 quick view, F4 edit, Ctrl+F4 edit with, F5 copy (Insert / Shift+↑↓ / Num+ Num- Num* mark rows first to copy several), Alt+F5 compress, Shift+F5 extract, F7 find files, Shift+F7 create folder, F8 delete, Ctrl+L create link, Shift+F11 sort, Shift+F12 checksums, Ctrl+F12 properties, Ctrl+F6 git history drive, Ctrl+F8 recycle drive, Ctrl+F9 Docker drive (on a container row: Shift+F9 start/stop, Ctrl+Shift+F9 restart), Ctrl+G Git client, Ctrl+N network browser, Alt+F11 iPhone browser, Ctrl+A calculator, Ctrl+E unit converter, Ctrl+P portfolio, Alt+F3 document manager, Alt+F8 package manager, Ctrl+O interactive shell (Ctrl+Shift+O the full-screen command log), Ctrl+C / Ctrl+X / Ctrl+V file clipboard (Ctrl+Shift+X the password manager), Alt+F9 disk manager (E eject, F format, M disk image), Ctrl+Shift+F11 mount the image under the cursor, Ctrl+F2 AI model details (Ctrl+B swaps the AI bar for the terminal bar). The Tools menu lists them all; `MenuShortcutTest` checks every menu label against the key its command is bound to. The music player is *not* a dialog — Ctrl+F7 (or Ctrl+Shift+M) points the two panels at the music drives instead (see below).
- **Content lenses** (`iTerminal.Core/Controls/Lenses/`): `IContentLens` decorates the entry list without the browser knowing why — `GetHeaderIndicator` + `DecorateRow`. `GitLens` colours rows by git status. Registered as `IContentLens` singletons and applied by `ContentBrowser`.

### Audio playback (`iTerminal.Core/Audio/`, `Services/Music/`)
The music player owns its own audio path rather than driving an external player, which is what makes
real pause/seek/volume and a working output-device selector possible on both platforms.

- **Decoders** (`Audio/Decoders/`) normalise everything to signed 16-bit LE PCM (`PcmFormat`): `WaveAudioDecoder` (RIFF, 8/16/24/32-bit + float), `Mp3AudioDecoder` (managed, via the `NLayer` package), and `FfmpegAudioDecoder` which pipes `ffmpeg -f s16le -` for FLAC/OGG/Opus/M4A/WMA. `AudioDecoderFactory.IsSupported` distinguishes formats that always work from those needing ffmpeg on PATH.
- **Sinks** (`Audio/Sinks/`) consume that PCM: `WinMmAudioSink` (waveOut P/Invoke, device by index), `PulseAudioSink` (`libpulse-simple` P/Invoke, device by sink name), and `AplayAudioSink` (pipes into `aplay`) as the ALSA fallback. Each is wrapped by an `IAudioOutputBackend`; `AudioDeviceService` probes them **at runtime** by `Priority` — the same Linux binary may find PulseAudio on one machine and only ALSA on the next, so this cannot be a registration-time choice like `IPackageManagerService`.
- **`MusicPlayerService`** runs one background pump thread — at `ThreadPriority.AboveNormal`, because it is the only work in the app with a real-time deadline: the device drains its buffer whether or not the thread is scheduled, and being late is an audible gap rather than a slow repaint. It costs the render and task threads nothing, since the pump spends nearly all its life blocked in the sink's write. It owns the decoder and sink. The sink's blocking `Write` *is* the playback clock, so there is no timer; public transport methods only record a request and signal the pump, which keeps key handlers inside the 200 ms budget. Interrupting a write that is waiting on the device is what `IAudioSink.Stop` is for — the one sink member callable from another thread. The sink to stop is read *before* the request is posted (`PlayIndex`, `SetDevice`): read after, it could already be the sink the pump just opened for that request, and stopping it ended the new track after one chunk with "The audio device stopped accepting data". Track advancement happens inside the pump, so a playlist keeps playing after the panel navigates away — and the pump raises `StateChanged` as soon as it sets `Playlist.CurrentIndex`, since `SetState(Playing)` is a no-op from one track to the next and would otherwise leave the playlist panel highlighting the track that finished.
- **Saved playlists and the playing queue are stored differently, on purpose.** A `.m3u8` is a *document* the user made: plain M3U/M3U8 files via `IPlaylistService`, so they interoperate with other players and can be browsed, copied and opened in the panels. The *queue* is session state — no more a document than a panel's last folder — so it lives in SQLite (`MusicPlaylist` table, entity `MusicPlaylistEntry`, keyed by `Position` because a queue is an ordered list) behind `IMusicPlaylistStore`. Rows carry the tags alongside the path, so a restored queue draws itself without re-reading a single tag. `MusicSessionJob` writes session changes back, polling a version stamp (`PollInterval`, 5 s) because the player has no session-changed event and should not grow one — the pump would be raising it from inside playback. The queue used to be an auto-saved `last.m3u8`; the restore still reads that file once, when the table is empty, so an upgrade does not throw the queue away.
- **Restoring the session is `IMusicSessionRestoreService`, not the job**, because two things need it and neither can wait for the other: the job (so the queue comes back whether or not a music panel is ever opened) and `ContentModelMusicPlaylist`'s constructor (so a panel restored from the last session draws the saved queue on its *first* paint — panels are built while the app is still coming up, before the jobs have necessarily started, and waiting to be handed the queue is what made the panel show an empty list first and the queue a moment later). `RestoreOnce` is idempotent: whoever gets there first does the work. It is also exactly once *per run* — after the table has been read, memory is the truth, or clearing the queue and reopening the panel before the next save would hand the old queue straight back.
- **The cued track is restored too, stopped.** `Playlist.CurrentIndex` is saved as the `MusicCurrentIndex` setting rather than in the queue table: it is a cursor into that list, not a property of any row, and it moves every time a track ends while the queue's own version stamp never changes — so `MusicSessionJob` watches it in the settings signature, alongside the volume, not with the queue. It comes back cued and not playing: a restored session shows where the user was, it does not start making noise at start-up. An index that no longer fits the queue is dropped by `Playlist` itself.
- **A queue replaced from outside playback goes through `IMusicPlayerService.ReplacePlaylist`.** `Playlist` is a plain data type with no events of its own — every other change to it comes from the pump, which raises `StateChanged` afterwards anyway — so a restore that writes into the list directly leaves every panel drawing the list it was built with until some unrelated transport event repaints it.
- **The music library** (`IMusicLibraryService` → `MusicLibraryService`) is the opposite choice, and deliberately so: the *index* is a SQLite table (`MusicLibrary`, entity `MusicLibraryEntry`) because search must not re-read tags. `MusicLibraryIndexJob` (Background) calls `Preload()` immediately — reading the cached table is what makes the catalog panel usable, and leaving it to the lazy load would put a full SQLite read on whichever key handler opened the panel first — then walks the music folder five seconds after start-up and every 15 minutes after that, re-reading tags only for files whose size or timestamp moved; the steady-state cost is a directory enumeration. Durations are probed only for WAV/MP3, by constructing the managed decoders directly rather than through `AudioDecoderFactory`, so a scan can never fork one ffmpeg per file.
- **The table is what the catalog panel draws, not the scan.** `EnsureLoaded` fills the in-memory copy from `MusicLibrary` before anything else touches it, so a panel opened in a session that has not scanned yet still lists the previous run's index. (This only became visible once the database stopped being recreated at every start-up — see the schema-stamp note above; until then the table was empty at every launch and the catalog could not fill until a scan finished, however early it read.) That load is marked done only when it *succeeds* — a database being recreated at start-up or held by a second instance would otherwise leave the catalog empty for the whole session, with nothing left to trigger another look — and a failed attempt is retried no more often than `LoadRetryInterval` (5 s), because the panel reads this on every repaint.
- **A scan publishes as it goes, in both directions.** Every `ScanFlushBatchSize` (250) freshly read files, or every `ScanFlushInterval` (2 s), `FlushScan` writes that batch to the table *and* folds it into the in-memory snapshot. So a first scan of a large folder fills the panel while it runs (the panel rebuilds from `Entries` on each progress report), and an app closed mid-scan keeps what had been indexed. Deletions are the exception: a row is only dropped once the whole walk is over, since until then "not seen yet" and "gone" look the same — which is also why the running snapshot is seeded from the cached library rather than from what the scan has read, and can therefore never shrink under a user who is looking at it.
- **A scan runs in two reported stages**, because "indexed 120 files" means nothing without a denominator: *discovery* (the recursive folder walk, which can only report a rising count) then *indexing* (the per-file pass, which knows the total). `MusicIndexingProgress` is the immutable snapshot of that — `Phase`, `DiscoveredFiles`, `IndexedFiles`, and `IsDiscoveryComplete`, which is true exactly from the indexing stage on. `DiscoveredFiles` counts *audio* files, never files: a real music folder is mostly artwork cache (a stock `~/Music` with an iTunes library is ~2 700 `.itc2` files around ~30 tracks), and a denominator counting those could never be reached — the UI says "audio files" for that reason. Discovery enumerates with `IgnoreInaccessible = true` and guards the file listing, the directory listing and each sub-folder separately, so one unreadable entry costs that folder and not the sub-tree under it. `IsIndexing` is derived from it rather than kept alongside it. Progress arrives on `IndexingProgressChanged` (rate-limited to `ProgressReportInterval`, 250 ms, with stage changes and the end of the scan always published) — `LibraryChanged` only fires once the whole scan has landed, so the progress event is the one a panel needs to repaint while work is still running. The catalog panel puts it in the two places that frame the listing and must agree: the footer, and the panel title — where `GetHeader` reserves the state on the right and shrinks only the path, because `Shrink` elides a line's *middle*, which is exactly where the counts would be. It is deliberately *not* a row: the title and footer are on screen for every listing, so a progress row would spend a line of the catalog repeating them.
- The **music folder** comes from the `MusicFolder` setting (`SettingsMusicTabPage`, tab 4 of the settings dialog), defaulting to `Environment.SpecialFolder.MyMusic`. The job polls that setting rather than subscribing to it — `ISettingsService` is a plain key/value store with no change notification — so changing the folder in Settings is enough to trigger a re-index.
- Search runs against an in-memory copy of the table, so the catalog panel calls `Search` straight from the key handler.
- **Tag reading** has two shapes off one parser. `MusicTagReader.Read` returns title/artist/album for the playlist and the library index; `MusicTagReader.ReadAll` returns the whole ID3 block (every text frame, comments, cover-art size, numeric genres resolved) for the F3 viewer. `FlacTagReader` covers what ID3 cannot: FLAC's Vorbis comments *and* its STREAMINFO, which is also where a FLAC's duration and bit depth come from without forking ffmpeg. Ogg/Opus/M4A tags are not read — those files show their name, size and "needs ffmpeg" instead of inventing metadata.
- **`IMusicMetadataService`** (→ `MusicMetadataService`) is what the viewer actually calls: it picks the tag reader by container and probes duration/format with the managed decoders only, for the same reason `MusicLibraryService.ProbeDuration` does. Async by contract; the dialog awaits it on a background task and repaints when it lands.

### The F3 music file viewer
F3 on a local audio file opens `MusicFileViewerDialog` (`iTerminal.Core/Dialogs/Music/`): artist, title,
album and format at the top, every tag in a scrollable list, and a transport with a progress bar at
the bottom (Space play/pause, Enter from the start, `s` stop, ←/→ seek, +/- volume).

- It plays through the **shared `IMusicPlayerService`**, never a private decoder — otherwise viewing a
  track would start a second stream over whatever the music panels are playing. Starting a file that
  is not queued appends it to the playlist, the same thing choosing it in a panel does, and closing
  the viewer leaves it playing.
- The transport applies only while the player is loaded with *this* file (`CurrentTrack.Path` match),
  so seeking in a viewer opened over a different playing track cannot move that other track.
- The progress bar needs no timer: `Dialog.OnIdle` marks the dialog changed every idle pass, and
  `Draw` reads the player's live position.
- `ViewFileDialogCommand` routes to it only when the file exists locally (`File.Exists`), like the
  solution viewer — the player decodes from a path, so an `ssh://` track has nothing to open.

### The music player is two panel drives, not a dialog
Ctrl+F7 (or Ctrl+Shift+M) runs `MusicPanelsCommand`, which points the left panel at `musiccatalog://`
and the right panel at `musicplaylist://`. There is no music dialog: the library and the queue are
drives, so "add this album" is the same F5 that copies a file between any other two panels.

- **`ContentModelMusicPlaylist`** lists the queue, preceded by three control folders — `[Transport]`,
  `[Volume]` and `[Output]` — reachable with the cursor and `Enter`. Every control the old dialog
  bound to a key is a row in one of them, which is what makes the drive usable without memorising
  anything. The header carries now-playing plus a progress bar and the footer the volume, repeat,
  shuffle and output device. `Delete` drops a track from the queue (`F8`, "delete the file", stays
  what it always was and is not bound here). `Alt+<text>` filters it, the same type-to-search the
  file panels use: the model overrides the `Filter` setter and rebuilds the listing with only the
  matching tracks — artist, album, title or file name, every word having to match, in any order —
  rather than dimming the rest, because the row wanted among a few hundred tracks is as likely to be
  off-screen as on it. Rows keep their queue position (`PlaylistIndex`, and the number they show), so
  `Enter` and `Delete` still act on the real track; the three control folders stay listed, since they
  are how the panel is operated at all; `Esc` clears it.
- **`ContentModelMusicCatalog`** lists artists at the root, albums one level down, tracks below that.
  Search is the panel's own type-to-search: `Alt+<text>` sets `Filter`, and the model overrides the
  setter to replace the listing with library-wide hits rather than dimming non-matching rows — the
  point of searching a catalog is to reach rows that are not in the current folder. `Esc` clears it.
  The listing is nothing but the folder's own rows: the indexing state lives in the header and the
  footer, which are drawn for every listing anyway. `Ctrl+R` (`Refresh(forceRefresh: true)`) starts a
  re-index on a background task — the footer names that key, since no row does — and the panel
  repaints from `LibraryChanged`.
- **Marking is the catalog's only stateful UI.** `Insert` (`ToggleMusicSelectionCommand`) marks the
  row and steps down, F5 then adds every marked row instead of the cursor row, and the operation
  consumes the marks. The marks live in the *model* as a set of keys (`track <path>` /
  `Artist|Album <artist> <album>`), never on the `MusicEntry` rows: the listing is rebuilt from the
  library on every refresh — several times a second while a scan runs — so anything stored on a row
  would not survive a repaint. `MusicEntry.IsSelected` is projected onto each row as it is built.
  Rows that stand for no tracks (`..`) are stepped over rather than marked, and
  navigating or searching clears the marks, so F5 can never add rows the user cannot see.
- **Navigating clears the filter on both music drives** (`ContentModelMusicBase.SetUrl`). This is not
  cosmetic housekeeping the way it is for a file panel: both models build their *listing* from the
  filter, so one left set across a navigation would have the panel draw the old hits under the new URL.
- Both models derive from `ContentModelMusicBase`, are read-only, refresh synchronously (a playlist
  and an in-memory index cannot approach the 200 ms budget), and are `IDisposable` — they subscribe
  to singletons that outlive them, so `ContentModelService.AddContentModel` disposes the model it
  replaces. That is the only reason content models have a lifecycle at all.
- Artist and album URL segments are percent-escaped (`Uri.EscapeDataString`). This is not cosmetic:
  without it "AC/DC" would parse as an album inside an artist called "AC".
- The commands live in `iTerminal.Core/Commands/Music/` and are attached to *every* `ContentBrowser`,
  ahead of the file-system ones. `MusicPanelCommand.FocusedMusicModel` gates them: the focused model
  must be a music model **and** be this browser's own model. Both halves matter — a control-tree walk
  offers a key to the focused control first but then to every control, so without the identity check
  a key the focused panel declined would be picked up by the other panel.

### Document management (`iTerminal.Core/Documents/`, `Services/Documents/`, `Dialogs/Documents/`)
Alt+F3 (`DocumentManagerDialogCommand`) opens `DocumentManagerDialog`: a search box, the results, and
an optional preview. Behind it, `DocumentLibraryIndexJob` walks the configured documents folder,
extracts text from every file an extractor understands, and stores both the metadata and the text.

- **Three stores, not one, and the split is the design.** `DocumentEntry` (table `Documents`) is the
  metadata and is mirrored in memory — it is what lists, counts and sorts. `DocumentContentEntry`
  (table `DocumentContents`) is the extracted text, read one row at a time for the preview and never
  held in memory. `DocumentSearchIndex` is a SQLite **FTS5 virtual table** (`DocumentSearch`) and is
  what search actually runs against. The music library keeps everything in memory and searches there;
  that cannot work here, because a music tag is tens of bytes and a document's text is tens of
  kilobytes — the same design over a real documents folder would hold hundreds of megabytes of prose
  in the heap to answer a query SQLite answers from an index. **Consequently `SearchAsync` is
  asynchronous** where `IMusicLibraryService.Search` is not: it hits the database, so the dialog runs
  it on a background task and never from a key handler.
- **The FTS table is invisible to EF Core**, which is why `DocumentSearchIndex` exists as a class
  rather than three methods on the service. The app has no migrations — a model change drops and
  recreates the database — and `EnsureCreated` knows nothing about a virtual table, so every entry
  point calls `EnsureCreated` first, and it rebuilds the index from `DocumentContents` when the
  metadata survived something the index did not. Without that, search would come back empty until the
  next full rescan re-extracted every PDF, which is minutes of work to rebuild something derived from
  what is already stored. There is a LIKE fallback for a SQLite built without FTS5.
- **Name and metadata hits are matched in memory and always sort ahead of content hits.** Someone who
  types a file name wants that file, not the twenty documents that mention it. Only the body search
  goes to the database.
- **Extractors** (`Documents/Extractors/`) implement `IDocumentTextExtractor` and are chosen by
  extension through `DocumentTextExtractorFactory`. `PlainTextExtractor` (sniffs UTF-8, falls back to
  Latin-1 — never to UTF-8 with replacement characters, since a token containing U+FFFD is one no
  query can match), `MarkupTextExtractor` (a scanner, not a parser: the input is whatever is in the
  folder, and a parser would reject exactly the half-saved files most in need of being searchable),
  `OfficeTextExtractor` (OOXML and OpenDocument are zips of XML — no interop, no package), and
  `PdfTextExtractor`. Extraction is deliberately **synchronous**: it is CPU and disk work with nothing
  to await, and what keeps it off the render thread is that only the indexing job calls it.
- **`PdfTextExtractor` is hand-written for the same reason the ID3 and FLAC readers are.** It scans
  for `stream … endstream` pairs rather than following the xref, which reads damaged and
  incrementally-updated files a strict walk rejects; it inflates Flate streams (with the PNG
  predictor, which object streams use); and it reads the strings the text operators draw. The
  declared `/Length` is only ever a hint, verified against an `endstream` — producers get it wrong.
  A large negative `TJ` adjustment becomes a space, which is how most producers write one. What it
  *cannot* do is map a subset CID font's glyph indices back to characters; rather than index the
  mojibake, `LooksLikeText` checks the result and the document is recorded `Empty` with a note. The
  same note covers scanned PDFs, whose answer is OCR.
- **Images contribute text from two places, kept separate on purpose.** `ImageMetadataReader` reads
  PNG text chunks, JPEG comments, EXIF descriptions and XMP straight from the header bytes — free,
  always works, and for a photograph usually the only text worth finding. OCR is the other, and runs
  only when an `IOcrEngine` reports itself installed. `TesseractOcrEngine` shells out to `tesseract`,
  the same bargain the audio decoders strike with ffmpeg, and probes availability **once** — a scan
  asks per file. It is registered behind `SettingsGatedOcrEngine`, so the extractor only ever asks
  "can this run", never "does the user want it to"; the engine's `DisplayName` distinguishes "off"
  from "not installed", because only one of those is fixed in the settings dialog.
- **Extraction status is stored, not re-derived.** A scanned PDF, a file no extractor handles and a
  file that threw all yield an empty string, and an index that recorded them identically would be
  lying. `DocumentExtractionStatus` plus `ExtractionNote` is what lets the preview pane say *why*
  there is nothing to show instead of drawing a blank the user reads as "still loading".
- **A rescan re-extracts only what moved** (size or last-write time), which matters far more than it
  does for music: re-reading every tag in a music folder is a second, re-extracting every PDF and
  re-OCR'ing every scan is minutes — and the job would do it on every pass. That is also why
  `DocumentLibraryIndexJob`'s intervals are much longer than `MusicLibraryIndexJob`'s (20 s start-up
  delay, 1 hour rescan), and why the job polls the folder setting rather than subscribing to it
  (`ISettingsService` has no change notification).
- The scan runs in the same two reported stages as the music one (`DocumentIndexingProgress`:
  `Discovering` → `Indexing`), flushes in batches so the dialog fills while a first scan runs, and
  only drops rows for missing files once the whole walk is over. Unlike the music scan, discovery
  counts **every** file rather than only supported ones: an unsupported file is still listed and
  still searchable by name, so hiding it from the denominator would make the count disagree with the
  folder. Progress carries the current file name — the counts alone cannot show which document is
  taking the seconds. Build output, VCS internals, dot-files and Office `~$` lock files are skipped.
- The **documents folder** comes from the `DocumentsFolder` setting (`SettingsDocumentsTabPage`, tab 5
  of the settings dialog), defaulting to `\users\tamas\nata\documents` — anchored to the system drive
  on Windows by `DocumentLibraryService.ResolveDocumentsFolder`, because a path that starts with a
  separator but names no drive resolves against whichever drive the process happens to be running on.

### The Git client (`iTerminal.Core/Dialogs/Git/`, `Services/Git/`)
Ctrl+G opens `GitClientDialog`, a `SplitPaneDialog`: five stacked list sections on the left
(Unstaged / Staged / Branches / Commits / Stashes) and a detail pane on the right. `IGitService` is a
structured async wrapper over the `git` CLI — porcelain v1 `-z`, `ArgumentList` so nothing is quoted
by hand, a `SemaphoreSlim` write-lock so two mutating commands cannot collide on `index.lock`, and
`GIT_TERMINAL_PROMPT=0` so a push never hangs waiting for a credential prompt that has no TTY to
appear on. `GitLens` shares the same service.

- **Nothing runs git from a key handler or `Draw`.** Every command goes through `RunAction`, which
  starts a background task and returns; `Draw` reads cached fields and `Dialog.OnIdle` forces the
  repaint. `PendingOperation` is the task the most recent refresh or command started — nothing in the
  dialog awaits it, it exists so a test can wait for the work it just asked for instead of polling.
- **Section heights come from the content, not from a fifth each.** `DistributeSectionRows` gives
  every section one header row, then hands out the remaining rows round-robin to whichever sections
  still want more, so a long list cannot crowd out a short one. An empty section collapses to its
  header — a clean staging area and an empty stash list are worth ten rows to the file list in a
  repository with thirty changes. The section under the cursor is served first and always keeps at
  least one row, so it can say `(nothing staged)` rather than looking like a drawing glitch. Layout is
  therefore recomputed on every refresh and every focus change, not only at start-up.
- **`_activeSection` is what the detail pane follows, and it is not "the focused control".** The diff
  pane is itself focusable — a long patch has to be readable with the arrow keys — so tabbing into it
  must not blank the patch being read. `SyncActiveSection` adopts a section only when a *section*
  takes focus, and it runs from `OnIdle` as well as after Tab, because focus can move without a key
  the dialog saw.
- **A failed command's whole output goes in the detail pane**, with the first line in the footer.
  Git's errors (a rejected push, a conflicted merge) are paragraphs, and the footer is one line.
- **A conflicted file belongs to the working tree only.** Both sides of an unmerged path carry a
  letter, so read naively `UU` looks staged *and* modified and the file appears in both panels.
  `GitFileStatus.IsConflicted` is what keeps it in Unstaged, marked `!`; staging it is how git spells
  "resolved", and the dialog says so.
- **`P` publishes a branch that has no upstream** (`PushAsync(setUpstream: true)` → `push -u <remote>
  HEAD`, remote from `GetDefaultRemoteAsync`). A plain `git push` answers an unpublished branch with a
  paragraph of advice, which is never what the person who pressed the key wanted.
- **Remote-tracking branches are listed** (`GetBranchesAsync(includeRemotes: true)`) below the locals
  and drawn grey; checking one out is `checkout --track`, falling back to a plain checkout when the
  local branch already exists. The two ref spaces are read with two `for-each-ref` calls, because
  short names make a local branch called `origin/x` indistinguishable from a remote-tracking one.
- **`?` / F1 opens an in-dialog key reference**, and the panels are *hidden* while it is up rather
  than drawn over: `ControlRendererJob` renders controls from a `HashSet`, so nothing guarantees the
  parent's overlay lands after its children.
- **The inline input (commit / amend / new branch / stash message) tracks `_inputActive`, not the text
  box's `IsVisible`.** `Control.ShowAsync` makes every child visible on the way in, so a footer that
  reads `IsVisible` as "the input is up" never draws its key hints at all.
- Not built: in-pane conflict resolution (a 3-way view; resolving today means editing, staging and
  committing), tags, rebase, cherry-pick, and a multi-line commit body.

### The folder selector (`iTerminal.Core/Dialogs/FolderSelector*.cs`)
Ctrl+F1 opens `FolderSelectorDialog`: a vertical `Tab` whose seven pages are the seven ways of naming
a folder — Favourites, Drives, History, Places, Folder Tree, SSH, Path. Whichever page is up, the
keys are the same: the arrows move, **Enter goes**, Esc cancels, F1 explains.

- **The left strip is clickable, and a click lands the cursor in the panel on the right.** Both
  halves matter: the strip is drawn by the `Tab` and owns no controls, so a click on a page name
  used to reach nothing (see the `Tab` mouse note under Key patterns), and a page cannot hold focus
  itself, so focusing it hands the cursor to the first control of the page — which is what makes a
  click on the strip a complete gesture rather than one that leaves the user reaching for Tab.
- **Choosing a folder ends the dialog**: every select command navigates and then calls
  `Command.CloseContainingDialog`, which walks up from the command's control to the enclosing
  `Dialog`. Both routes have to work — Enter on the page's list and the page's own *Select* button —
  and for a long time only the button did, because the Enter route depends on the page being handed
  the key at all (see the `Tab` note under Key patterns).
- **Esc closes it at any time**, from any page, whatever is focused — and where the page has a
  sub-state on screen, **one press per layer**: an Esc with a suggestion list up on the Path or SSH
  page dismisses the list and leaves the selector standing, the next closes the selector; the F1 help
  over the top is the same story through the topmost-modal rule. Nothing in the dialog implements
  either half. `Dialog.HandleKeyEventAsync` claims Esc *ahead of the children* rather than offering it
  to the focused control first, so no text box or list can swallow it — and because of that a
  suggestion list had no key that could dismiss it on its own, which is what
  `ITransientOverlayHost` exists for (see Key patterns). It is still pinned down by
  `FolderSelectorDialogTest` page by page, because it is the promise the dialog makes on its own
  border.
- **Selecting a page puts the cursor on that page's first control**, by every route — Ctrl+Up/Down,
  Ctrl+&lt;number&gt;, a click on the strip. A `TabPage` cannot hold focus itself, so
  `Tab.SwitchToPage` focusing the page hands the cursor to the first *focusable* control inside; that
  is the whole reason every page adds its list or its text box before its buttons. Ctrl+&lt;number&gt;
  goes through `SwitchToPage` even for the page already showing, which makes it the keyboard's way
  back into the content — read as "only when that page is not already focused", as it used to be, the
  key did nothing at all once the cursor had reached one of the page's buttons, and on the Path page
  (where Tab belongs to the completion) nothing brought it back.
- **The suggestion list is placed directly below the box it belongs to, which is why the text boxes
  are laid out one row high.** A `TextBox` draws exactly one line whatever its `ViewSize.Height`, and
  the list is a `Popup` with `PopupPlacement.Below` — so the Path and SSH boxes, laid out as tall as
  the whole page (a leftover from when the list was drawn *inside* the box's rectangle), put their
  suggestions at the bottom of the screen, a dozen rows from the text being completed. Leaving a page
  also takes the list down (`Tab.SwitchToPage`): the popup is attached to the *root*, so hiding the
  page it belongs to does not hide it.
- **Enter is claimed by `FolderSelectorTabPage`, the shared base, ahead of the page's children.**
  Each page's real work lives in a command attached to its *Select* button, but the control that
  holds focus is the list — and `ListBox<T>` binds Enter to its own `SelectListItemCommand`, which
  reports the key handled unconditionally. Routed the ordinary way, Enter ticked a row's selection
  flag and stopped: the select command was reachable only by tabbing onto the button. A focused
  `Button` still keeps Enter for itself, so "Add to favourites" under the cursor adds rather than
  navigates.
- **Every page lists its list first.** `SetFocus` lands on the first focusable control, and a page
  that opens with a button focused answers the arrow keys with nothing.
- **`SelectedDrive` follows the cursor, not `ListBox.SelectedItem`.** That property reports the row
  whose `IsSelected` flag is set — a flag only Enter ever sets — so read that way it is null the
  first time it matters.
- **The Path page is what makes every drive kind reachable.** It hands the typed text straight to
  `Url` and lets `ContentModelService.AddContentModel` decide what it is, so a scheme added to the
  app works there the day it is added, without touching the page. Tab completes, from the paths typed
  there before *and* the folders the panels have visited (`FolderPathCompletionModel` — the history
  is read live rather than copied into the settings key, which would both duplicate it on disk and
  freeze it). `FolderUrlValidationModel` accepts a known scheme on sight — a remote URL cannot be
  checked without doing the very work the navigation is about to do, and a validator that blocks on
  the network has no business running off a keystroke — and only probes the disk for a local path.
  Its `SupportedSchemes` is also what generates the on-screen scheme hint, so the two cannot drift.
- **The Places page carries the app's own drives** (`memdrive://`, `musiccatalog://`,
  `musicplaylist://`) beside the OS special folders. They are not on the Drives page because that one
  is fed by `DriveInfoModel`, which the status bar's drive selector also draws from; and they are
  listed *somewhere* rather than left to the Path page, because a URL scheme nobody has written down
  cannot be typed.
- **The dialog draws its own footer** by overriding `DrawChrome` — `PopUpWindow` always passes an
  empty footer — and shrinks it first, since `StringHelper.AlignCenter` drops an over-long footer
  whole. The pages are full-height lists with no room for a hint line of their own.
- Favourites are stored in the `Favourites` setting. Two things about that were wrong for a long
  time and are worth not reintroducing: the list was **cleared before the setting was read**, and
  `Clear` raises `CollectionChanged`, which writes the now-empty list straight back — so saved
  favourites were erased a line before they were read, every start-up; and the write joined the `Url`
  objects rather than their `FullUrl`, and `Url` does not override `ToString`.

### Drives and URL schemes
A panel's drive kind is derived from the URL scheme (`iConsole/Data/Container.cs` → `Url.ContainerType`), and `ContentModelService.AddContentModel` maps it to a model:

| Scheme | Content model | Backing service |
| --- | --- | --- |
| `file://` | `ContentModelFileSystem` | `IFileSystemService` |
| `zip://`, `gz://`, `targz://` | `ContentModelFileSystemArchive` | `IArchiveFileSystemService` |
| `ssh://user@host:/path` | `ContentModelSshDrive` | `ISshFileSystemService` |
| `smb://[user@]host/share/path` | `ContentModelSmbDrive` | `ISmbFileSystemService` |
| `iphone://<udid>/<afc-path>` | `ContentModelIPhoneDrive` | `IIPhoneFileSystemService` (imobiledevice-net) |
| `memdrive://` | `ContentModelMemoryDrive` | `IMemoryDriveService` |
| `musicplaylist://` | `ContentModelMusicPlaylist` | `IMusicPlayerService` + `IAudioDeviceService` |
| `musiccatalog://` | `ContentModelMusicCatalog` | `IMusicLibraryService` |
| `docker://<container>/<path>` | `ContentModelDockerDrive` | `IDockerDriveService` (docker CLI) |
| `git://<repo>/<revision>/<path>` | `ContentModelGitDrive` | `IGitDriveService` (git CLI) |
| `search://` | `ContentModelSearchResults` | `IFileSearchService` (rows are `file://`) |
| `preview://` | `ContentModelPreview` | `IFilePreviewService` |
| `archive://<archive>/<path>` | `ContentModelArchiveDrive` | `IArchiveDriveService` (SharpZipLib; 7-Zip CLI) |
| `recycle://<name>` | `ContentModelRecycleDrive` | `IRecycleBinService` over an `IRecycleBinStore` |
| `dav://`, `davs://` `[user@]host[:port]/path` | `ContentModelWebDavDrive` | `IWebDavFileSystemService` (HttpClient + PROPFIND) |
| `mtp://<device>/<storage>/<path>` | `ContentModelMtpDrive` | `IMtpDriveService` over an `IMtpBackend` (`gio` / the Windows shell) |

When adding a scheme, all four pieces must line up — and if its file system is a shared service rather than one its panel hands over (`IFileSystemProvider`), add it to `FileSystemResolver`, which every file operation resolves through: the constant in `Container`, the parsing branch in `Url`, the `ContainerType` case in `ContentModelService.AddContentModel`, and the DI registration of the file-system service. Add it to `FolderUrlValidationModel.SupportedSchemes` too (`FolderUrlValidationModelTest` holds the list to `Container`), and to the Places page if a user should be able to pick it.

### The tool-backed drives, F7 search and quick view (`docker://`, `git://`, `search://`, `preview://`)
Ctrl+F9 points the focused panel at `docker://`, Ctrl+F6 at the git history of the repository it is in, F7 opens `FindFilesDialog`, and Ctrl+F3 turns the *other* panel into a preview of the entry under the cursor. Each of the drive keys toggles: pressed on its own drive it takes the panel back. F7 used to be Create Folder, which is now **Shift+F7**.

- **`ContentModelAsyncDrive` is the base of the first three**, because their listing comes from a process or a walk that cannot fit the 200 ms key-handler budget. `SetUrl` puts the `..` row up at once and lists on a background task; a result is written only if its generation and URL are still current (the same stale-result rule as `FilePanelRefreshTask`); a failure goes in the footer and keeps the `..` row. `ExistsFile`/`ExistsFolder` answer **from the listing** — they gate F3/F5/F8 on the key handler, and asking the tool would spawn a process there. `ListingTask` is the test seam.
- **The way out of a drive's root is the folder the panel came from.** `ContentModelService.SetUrlAsync` records it (`ContentModelAsyncDrive.RememberReturnUrl`, settings key `<panel>.ReturnUrl`) on *every* crossing into one of these drives — hot key, Places page, typed URL — and only from outside them, so docker → search still leads back to the disk. The root's `..` and the toggle keys both go there.
- **Copy/move/delete reach these drives through their panel.** `TransferCommand`/`DeleteCommand` resolve a file system by scheme; for these drives they fall back to the panel's `IFileSystemProvider.FileSystem` (the shared service). A cross-drive folder copy walks the source with `IFolderListingFileSystem.ListChildren`, which `ContentModelFolderTaskHelper` uses for any drive it has no case for.
- **`git://` escapes the repository and the revision, and nothing else.** The repository is a local path (`C:\src\app`) and a branch name routinely holds a slash (`feature/login`); the tree path stays raw so `Url.Name` — what a copy names its target — is the real file name. `GitDriveUrl` builds and parses. Levels: remembered repositories (setting `GitDriveRepositories`) → HEAD, branches, tags, remotes and the last 100 commits → the revision's tree (`ls-tree -z -l <rev>:<path>`). File contents are piped from `git cat-file blob`, so F3, F5 and the preview read an old version without a checkout. Read-only. The repository is found by walking up for `.git` (folder or worktree file), not by `rev-parse`: that runs on the key handler.
- **`docker://` lists with `ls` inside the container and moves bytes with `docker cp`.** `docker exec <c> ls -lAnL -- <path>` is the subset GNU and BusyBox agree on (numeric ids, symlinks followed so `/bin → usr/bin` is a folder); file contents go through `docker cp`'s tar stream, which also works on a stopped container and an image without a shell. The CLI rather than the Engine API, for the reason audio shells out to ffmpeg: it already knows how to reach the daemon. A daemon that is not running is reported in words, not as a named-pipe paragraph.
- **A container is operated from its row, and is never a folder to a file operation.** On the container list, Shift+F9 starts or stops the container under the cursor (by `DockerContainerEntry.IsRunning`) and Ctrl+Shift+F9 restarts it (`Commands/Docker/`, gated like the music commands: the focused model must be a docker panel *and* this browser's own). `ContentModelDockerDrive.RunContainerAction` runs `docker start|stop|restart` on a background task (`docker stop` alone waits ten seconds), says it in the footer, re-lists, and writes the outcome *after* the listing lands — a listing clears the footer's message. A container row's URL is the container's root folder and that folder exists, so F8 on it used to offer to delete it with *Recursively delete folder* ticked, and the delete walked the container removing `/etc`, `/usr` and the rest. `DockerContainerEntry` is an `IDriveObjectEntry`, which `FocusedEntry` refuses (cursor row and marks alike), the container list cannot be marked, and the service itself refuses to delete, move or read a container's root.
- **The quick view of a container is its log**: `IEntryPreviewSource` lets a panel answer for its own rows before `FilePreviewService` builds a file preview (null means "preview it as a file"). `docker logs --tail 200 --timestamps` replays stdout and stderr on two pipes, so they are merged by the timestamp (fixed-width RFC 3339, which sorts as text) and the stamps and colour codes dropped (`DockerDriveService.MergeLogs`). `FilePreview.StartAtEnd` opens it on the last line; Ctrl+R in the preview panel reads it again.
- **Ctrl+O opens a real shell inside the container** (`docker exec -it`, see "Lending the terminal"), and **the command log and terminal bar run their commands inside it too.** The terminal runs each command through the focused panel's model (`RunTerminalCommandAsync`), so the docker model runs `docker exec -w <folder> <c> sh -c <command>` — in the panel's folder, or on the container list in `/` of the container under the cursor — and the prompt says where (`ITerminalPromptSource`: `web:/etc>`). One command at a time, like the ssh drive, not an interactive shell: the terminal has no TTY to give one, so stdin is closed (a bare `cat` ends rather than hangs), and it goes through the streaming runner, which has no 30-second timeout. A failure that is docker's (no daemon, a stopped container) is said in words; the command's own stderr is shown as written (`DescribeDockerProblem` tells the two apart).
- **`search://` rows are the files themselves** (`file://` URLs, named relative to the search folder), which is what makes F3/F4/F5/F8 work on hits with no code of their own; Enter on a hit opens its folder with the cursor on it. The search belongs to the singleton `FileSearchService`, not to the dialog, so its results outlive it: Ctrl+P in the dialog hands them to the panel (the search keeps running); closing the dialog otherwise stops it. The walk (`FileSearch`) skips reparse-point *folders* (junction loops) but not reparse-point files (OneDrive placeholders), skips `.git`/`.svn`/`.hg`, streams content line by line and treats a NUL in the first 8 KB as binary.
- **`preview://` follows the other panel through `IContentModelService.ModelChanged`** and rebuilds only when the entry or the width changed, after `ContentModelPreview.Debounce`, on a background task. `FilePreviewService` reads at most 64 KB of a text file (hex dump when binary) and hands PDF/Office/HTML/images to F3's own `IFileToTextConverterService`, so the two never disagree. It reads through the panel's `IFileSystem`, so a commit or a container file previews like a local one.

### WebDAV (`dav://`, `davs://`) and MTP phones (`mtp://`)
- **WebDAV, `dav://[user@]host[:port]/path` (HTTP) and `davs://…` (HTTPS)** — `WebDavFileSystemService` over plain `HttpClient` and an XML reader (PROPFIND depth 0/1, GET, PUT, MKCOL, DELETE, MOVE and COPY with `Destination` and `Overwrite`); no package. One client is kept for the run (both panels may be on the same server) and replaced when scheme, host or user changes. The URL holds the raw path and each segment is percent-escaped when a request is built, the server's hrefs unescaped on the way back (`Escape`, `ParseMultiStatus` — `internal` for tests). MOVE and COPY are done by the server, so a rename on the drive costs nothing; a copy to another drive streams through `StreamToAsync`/`StreamFromAsync`. A 405 from MKCOL ("already there") and a 412 from a no-overwrite MOVE/COPY are not errors; a 401 says a login is needed. The password comes from a saved `NetworkProtocol.WebDav` profile (host + user) in the vault, never from the URL — as for FTP, **there is no dialog yet that creates such a profile**, so an authenticated server needs one saved by other means. Digest/NTLM are whatever `HttpClientHandler` negotiates; HTTPS certificates are validated normally.
- **MTP, `mtp://<device>/<storage>/<path>`** — the root lists devices, a device lists its storages, below that are folders (`MtpDriveService`, a `ContentModelAsyncDrive` like docker: listing off the key handler, `IFileSystemProvider`). Devices and storages are `IDriveObjectEntry` rows and the service refuses to delete or write to them. There is **no MTP library**: a phone only talks MTP to the operating system's own driver stack, so `IMtpBackend` is the seam — `GioMtpBackend` on Linux (GVfs through the `gio` CLI: `gio mount -li`, `list -l`, `cat`, `save`, `mkdir`, `remove`; the device must be unlocked, on *File transfer* and mounted) and `ShellMtpBackend` on Windows (the This PC shell namespace through PowerShell's `Shell.Application`, names passed as single-quoted literals; files move through a temp folder because the shell copies files, not streams). The WPD NuGet wrappers need a `-windows` target framework, which would end the app's plain `net10.0` build.
- **MTP has no rename or universal server-side copy**: a copy within a device is download + upload, a move of a file is that + delete, a folder move is refused (copy it, then delete it).
- **Honest limits:** both MTP backends were written against documented tool output and are tested against recorded output and a fake backend (`MtpTest`) — **neither has been run against a real phone**. On Windows deleting is refused on purpose (the shell's delete asks for confirmation in a window a terminal cannot answer); delete in Explorer. The end-to-end suite registers an `UnavailableMtpBackend` so no run asks the machine for its phones.

### Marking rows (multiple selection)
Insert marks the cursor row and steps down, Shift+↓/↑ mark while moving, Num+ / Num- mark or unmark by a name pattern (`MarkPatternDialog`, the same `*.jpg;*.png` syntax as F7, through `FileSearch.ParsePatterns`), Num* inverts the files; the Edit menu has all of them plus Mark All / Unmark All. F5, Shift+F6 and F8 then act on the marked rows instead of the cursor row.

- **The marks live in the model, as a set of URLs** (`IMarkableContentModel`, implemented once in `ContentModelBase`), never on the rows: listings are rebuilt on every refresh. `GetMarkedEntries` reads them back *from the listing*, so a marked file deleted meanwhile simply drops out, and the order is the order on screen. `ResetNavigation` — which every drive's `SetUrl` calls — clears them: an operation must never act on rows of a folder the user has left. The music drives and the preview opt out (`CanMark => false`); the catalog keeps its own Insert marks.
- **`FocusedEntry.ActionableUrls` is the one answer to "what does F5/F8 act on"**: the marks when there are any (even with the cursor on `..`), otherwise `ActionableUrl`. The dialog commands hand their panel to the dialog in `OnBeforeShow` (`SourceModel`), because once the dialog is up `GetFocusedModel()` is null.
- **Several entries run as one `BatchOperationTask`**: the single-entry tasks (with their discovery tasks, still side by side) one after another, under one progress window, Cancel stopping the rest. A failed step does not stop the others; the failures are listed and `Error` keeps the window up. The copy/move target is a *folder* (`TransferDialog.TargetUrlFor` puts each entry under its own name), created first on the task's thread if missing. The operation consumes the marks.
- **Name a target with `FocusedEntry.NameOf`, not `Url.Name`**, which is empty for a folder URL — a marked folder named by it would be copied onto the target folder itself.
- `ContentBrowser` paints a marked row (yellow; dark red under the cursor) *after* the lenses, so a git status colour cannot hide what the next F8 will delete. The footer counts the marks and their size.

### mc-style additions: hex view, user menu, folder size, FTP
- **F3 viewer hex mode.** `FileViewerDialog` owns a `HexViewer` beside the text control; **F4 toggles** between them (title says `[HEX]`). The bytes are read lazily on the first toggle through the panel's `IFileSystem.ReadFileAsync`, so any drive's file can be dumped, and the text view is never given up (ToggleHexModeAsync flips visibility and focus — `ShowAsync` re-hides the dump, since it makes every child visible).
- **User menu, Shift+F10** (`UserMenuDialog`, `UserMenuService`). mc's F2 menu; F2 is the terminal here, so it sits with the other Shift+F-keys. The menu is a text file, `usermenu.txt`, in the data folder, written with defaults on first use and read on every open (no cache, so editing it takes effect at once; F4 in the dialog opens it with the system default). Format: `<key> <title>` in the first column, indented command lines, `+ f <patterns>` before an entry to limit it to matching names, `#` comments. Macros (`UserMenuMacros`): `%f %b %x %d %D %s %t %%`, names quoted for the shell the script runs in. An entry is written to a temp script and run on the lent terminal (`IInteractiveShellService`, banner off) with a "press a key" pause, then every panel is re-read. Local folders only (`CanExecute`).
- **Ctrl+Space folder size** (`CalculateFolderSizeCommand`). Measures the folder under the cursor, or every marked folder, with `IFilePropertiesService.MeasureAsync` on a background task and writes the total into the row's `FileSize` (`…` while running). The figure lives on the row, so a refresh of the folder rebuilds the rows and drops it, as in mc. Local disk only, never `..`.
- **FTP drive, `ftp://[user@]host[:port]/path`** (`FtpFileSystemService` over FluentFTP, `ContentModelFtpDrive`). A singleton service holds one control connection, serialised by a lock — both panels may be on the same server — and reconnects when the host or user differs. No user means anonymous. A password comes from a saved `NetworkProtocol.Ftp` profile in the vault, never from the URL (the URL has no password part). FTP has no server-side copy, so a copy within the drive goes through memory; folder copy/delete walk through `IFolderListingFileSystem`. `Url.Host` holds `host:port`; `FtpFileSystemService.SplitHost` splits it. The path part of the URL takes anything after the first `/`, spaces included.

### The command line and the panels (mc niceties)
The terminal bar (Ctrl+B) is the command line; the panels feed it and run it, as in mc.

- **Alt+Enter / Ctrl+Enter** copy the name under the cursor, **Shift+Enter** the marked names (the cursor row when none), **Ctrl+Shift+Enter** the folder's path (`InsertIntoCommandLineCommand`). A name with a blank is double-quoted (`TerminalModel.QuoteName`); the text goes after a blank. **mc's Ctrl+X T / Ctrl+X P are not bound**: Ctrl+X is the password manager here, and a prefix would have to swallow it.
- **The command line is revealed, not focused**: `Content.RevealCommandLine` swaps the AI bar for the terminal bar without moving focus, because text copied into a line nobody can see is worse than none. Alt+Enter is swallowed by Windows Terminal (full screen) — Ctrl+Enter is the one that always arrives.
- **Enter in a panel runs the line when it holds something and is on screen** (`RunCommandLineCommand`, attached ahead of the Enter commands). It declines — so Enter opens the entry as before — when the line is empty, hidden behind the AI bar, or a command is running.
- **Alt+P / Alt+N walk the history** (`TerminalModel.RecallPrevious/RecallNext`), in the panels (`ContentBrowser.HandleKeyEventAsync`, ahead of the search) and in the terminal panel. The half-typed line is kept and comes back past the newest command. The cost: a type-to-search cannot start with P or N (use another letter, or Alt+<other> then keep typing).
- **`cd` is a panel navigation** (`TerminalModel.TryChangeDirectory`, called first in `StartCommand`): `cd`, `cd <folder>`, `cd ~`, `cd ~/x`, `cd -`, quoted or not, relative to the last panel's folder; recorded in the history, and a missing folder is an error line there. Only on a local panel and only when the line has no shell operator (`cd x && ls` goes to the shell) — a `cd` run as a command changed nothing the user could see.

### Archives as folders (`archive://`)
Enter on a ZIP, TAR, TAR.GZ or TAR.BZ2 — and, with 7-Zip installed, 7z, RAR, ISO or CAB — opens it as the `archive://` drive (`NavigateToArchiveCommand` → `SetUrlAsync`, so the way back is recorded): real folders, F3/Ctrl+F3 on entries, F5 to copy files and folders out, read-only otherwise. It is a `ContentModelAsyncDrive` like docker/git, so listing never runs on the key handler; `IsDriveRoot` is overridden because the archive's top level, not the bare scheme, is where `..` leaves it — back to the folder the archive is in, **with the cursor on the archive** (`ContentModelService.LandOnTheArchiveLeft`).

- The archive's local path is one percent-escaped segment (`ArchiveDriveUrl`), as git escapes its repository; the inner path is left raw so `Url.Name` is the entry's name.
- **An archive's listing is read once and cached, keyed by size and write time** (`ArchiveDriveService.GetIndexAsync`): every folder is drawn from it, and a TAR.GZ cannot be listed without decompressing all of it. Folders an archive only implies (most ZIPs store `a/b/c.txt` and no `a/`) are added (`WithImpliedFolders`). A TAR entry is read by scanning to it; a ZIP entry by seeking; a 7-Zip entry with `7z x -so`.
- 7-Zip is always given a closed stdin: an archive with encrypted names makes it ask for a password, and inheriting the app's console it would wait there for good. Encrypted content is pointed at Shift+F5.
- The old `zip://…@/` drive (`ContentModelFileSystemArchive`) is still there for typed URLs; Enter no longer leads to it.

### File associations: Open with / Edit with (`Services/FileAssociations/`, `OpenWithDialog`)
Shift+F3 ("Open with…") and Ctrl+F4 ("Edit with…") list the programs for the file under the cursor; Ins adds one, F4 changes it, Del removes it (y/n), Space makes it the default, Enter opens the file with the row. From then on **Enter uses the default "open" program and F4 the default "edit" program** for files like it. With nothing chosen both keys do exactly what they did: Enter opens an archive as a folder or runs the file in the command log, F4 opens the built-in editor.

- **A `FileAssociation` is a name, patterns, a command, a kind (`Open`/`Edit`) and "runs in the terminal".** The patterns are F7's (`*.jpg;*.png`, `*` for all, through `FileSearch.ParsePatterns`). They live in the `FileAssociations` setting as JSON, and **the order of the list is the priority**: the first that matches is the default, so "make default" is "move to the top" and a program just added goes first. `FileAssociationService` re-reads the setting on every call, parsing only when its text changed.
- **No shell reads the command** (`FileAssociation.BuildCommandLine`): it is split into words (blanks, double quotes, no escape character — a Windows path is full of backslashes) and the placeholders `%f` file, `%d` folder, `%n` name, `%b` name without extension are replaced inside each word afterwards. So a path with spaces is one argument without quoting `%f`, and nothing in a file name can become a second argument. A command that names the file nowhere gets it last, which is what typing just `notepad` means.
- **Two ways to run, and the user says which** (`FileLauncher`). A windowed program is started detached with no console and its output thrown away — inheriting the app's console, a GUI tool that prints a line on start-up would print it across the panels. A terminal program (vim, nano) is lent the whole terminal through `IInteractiveShellService`, as Ctrl+O lends it to a shell, with `ShellLaunch.Banner` empty: the shell's "type exit to return" line means nothing in an editor. The panels are re-read when it exits.
- **The program is resolved on the PATH first, with `PATHEXT` on Windows** (`FileLauncher.ResolveProgram`): `code` is `code.cmd`, and a process cannot be started by a name without its extension. It is also what turns "not installed" into a sentence instead of a `Win32Exception`.
- **A launch is only started** (`FileAssociationRunner.Start`): the dialog closes first and the key handler returns. A failure therefore has nowhere to be shown by the time it is known, and is posted as an error notification. `LastRun` is the test seam.
- **Local files only** (`FileAssociationRunner.LocalFilePath`): a program is handed a path, so a file in an archive, a container or on a remote host is not offered — the same limit the music and solution viewers have. `search://` hits are `file://` URLs and work.
- **F4's choice is made inside `EditTextFileDialogCommand`**, not by a second command ahead of it: the panel, the hot key bar's button and the File menu's entry each build that command, and they must not disagree. With an edit association F4 applies to any file type, not just the built-in editor's list. Enter's is a separate command (`OpenAssociatedFileCommand`), attached ahead of `NavigateToArchiveCommand` and inert without an association.
- **"Edit with…" always keeps the built-in editor one row away** (when the file is a type it takes), and "Open with…" the system default (`UseShellExecute` on Windows, `xdg-open`/`open` elsewhere) — otherwise choosing a program would be a one-way door.
- **`OpenWithDialog` is handed out by a `Func<OpenWithDialog>`**: each consumer (a panel, the File menu) needs two instances, one per kind, and a dialog instance is one control. Its height is fixed — the list changes while it is open, and a dialog that shrank would leave rows on its layer.
- The end-to-end suite replaces `IFileLauncher` with `SandboxServices.Launcher`, which starts nothing and records what would have been. **A test must never reach the real launcher through the app**: Enter on a file would start a program on the machine running the suite.

### Links: symbolic links, junctions and hard links (`FileLinkHelper`, `Services/Links/`, `CreateLinkDialog`)
A symbolic link or a Windows junction is listed as `name → target` (and `Link: name → target` in the info strip), is entered with Enter like the folder it leads to, and **is one entry of the folder it is in to every operation that walks a tree**. Ctrl+L (`CreateLinkDialog`) makes a link to the entry under the cursor: symbolic by default, optionally with a relative target, or a hard link (files only, same volume). The link is offered in the other panel's folder under the same name, as F5 offers its copy.

- **`Url.LinkTarget` / `Url.IsLink` say whether a local entry is a link**, set by both constructors — the `FileSystemInfo` one a listing uses and the string one rows restored from the folder cache use. The attributes are asked first (`FileLinkHelper.GetLinkTarget`): they came with the enumeration, so an ordinary entry costs nothing, and only a reparse point is opened to read its target. A reparse point with no target (a OneDrive placeholder) reads as ordinary.
- **A recursive delete never walks through a link.** It used to: the delete discovery listed whatever a folder link showed and handed those files to be deleted — the files of the folder the link led to, anywhere on the disk — and F8 opens with *Recursively delete folder* ticked. Three places hold this together, and all three are needed: `FolderDeleteDiscoveryTask` hands a folder link on as one entry instead of descending (and finds nothing at all under a root that is itself a link); `FileSystemService.DeleteFile` — what the pipeline calls for each entry — removes a link to a folder with `Directory.Delete(recursive: false)`; and `DeleteFolder` removes a link before it considers recursion or the recycle bin. A link is deleted outright, not recycled: it is a pointer, and recreating it is one Ctrl+L. `LinkServiceTest` and `LinksTest` pin each of these down with a real link and a file that must survive.
- **Copying follows a link** (the copy holds what the link led to), as before — **except a link back to a folder it is inside** (`FileLinkHelper.LeadsToAnAncestor`), which both folder walkers (`FolderDiscoveryTask`, `FileSystemService.CopyFolderRecursive`) leave out: copied through, it never ends. The recursive file count in the info strip does not go through links at all.
- **A hard link cannot be shown as one.** It is a second name for the same file, and neither name is "the" link; nothing in the listing tells it from any other file.
- **Hard links are P/Invoke** (`CreateHardLinkW`, `link(2)`): .NET has `File.CreateSymbolicLink` and no hard-link counterpart. Crossing volumes is said in words ("has to be on the same volume").
- **Windows refuses symbolic links to an ordinary account unless Developer Mode is on**, as "A required privilege is not held by the client". `LinkService.DescribeSymbolicLinkFailure` says what to do instead, and that a hard link needs neither. Junctions are displayed and deleted correctly but not created — .NET cannot, and `mklink /J` is what the tests use to get a folder link on a machine without the privilege (`CreateFolderLink`).
- **A dangling link exists to neither `File.Exists` nor `Directory.Exists` on Linux.** Anything asking "is something already there" or "is there anything to delete" has to ask `FileLinkHelper.IsLink` as well.
- Local disk only: `CreateLinkDialogCommand` gates on a `file://` entry and never the `..` row. A failure stays in the dialog, wrapped over three rows — these messages are sentences.

### Checksums and properties (`ChecksumDialog` Shift+F12, `PropertiesDialog` Ctrl+F12)
Shift+F12 shows the MD5, SHA-1, SHA-256 and SHA-512 of the file under the cursor; Ctrl+F12 shows what the disk records about the file or folder under it and lets the changeable part be changed.

- **Checksums work on any drive; properties are local only.** A checksum needs nothing but the file's bytes, so `ChecksumDialogCommand` resolves the drive's `IFileSystem` (`FileSystemResolver`, while the panel still has focus) and `ChecksumService` streams through it — a file in a container, an archive or over ssh hashes like a local one. Sizes, dates and attributes are read from the disk itself, and the other drives' rows carry no more than the listing already shows.
- **All four algorithms in one pass** (`IncrementalHash` × 4 over a single read): reading is what takes the time, and over ssh a second read is a second transfer. The read runs on a background task (`ComputeTask`) with the percentage shown meanwhile, and **closing the dialog cancels it**.
- **A typed checksum is compared as it is typed**, against the algorithm its length implies (32/40/64/128 hex digits; blanks, `:` and `-` ignored). There is no *text* clipboard yet (the file clipboard is below), and the checksum on a download page is what one has in the other window. `ChecksumDialog.CompareVerdict` is the whole rule.
- **A checksum written down beside the file is checked without being asked** (`ChecksumService.FindWrittenChecksum`): `name.sha256` (or `.md5`, `.sha1`, `.sha512`) first, then the folder's `SHA256SUMS`-style list. `ParseChecksumFile` reads `hash  name`, `hash *name`, the BSD `SHA256 (name) = hash`, and a file holding nothing but the hash — the last only when it is the single line, or a list of other files' checksums would be read as this file's. A list over 1 MB is not read.
- **F2 writes `name.sha256`, never over one that says something else**: that file may be the publisher's, and the one thing it must not be is replaced by whatever the file hashes to today.
- **A folder's size is added up behind the open dialog** (`FilePropertiesService.MeasureAsync`, `MeasureTask`), the running total shown as "… so far"; closing cancels the walk. It does not go through links, and a folder it could not read makes the total say "at least".
- **The properties dialog reads the link, not its target** (`FileInfo` on the trimmed path): the entry the panel listed is the link.
- **Only what a user sets is written back**: read-only, hidden, system and archive on Windows (`ChangeableAttributes` — the rest are facts about the entry), the permission bits as octal elsewhere. The dialog attaches only the controls its system has a use for; attached and hidden they would be shown again by `ShowAsync`. The Unix form is covered by unit tests of the service and the octal helpers only — the end-to-end suite has run on Windows.
- `InfoLines` (`iTerminal.Core/Controls/`) is the block of coloured read-only rows both dialogs draw their facts with.

### The file clipboard: Ctrl+C / Ctrl+X / Ctrl+V (`Services/Clipboard/`, `Commands/Clipboard/`)
Files copied here paste in Explorer, a mail client or an upload dialog, and what they copied pastes here. The Edit menu lists the three; Ctrl+Insert, Shift+Delete and Shift+Insert are the CUA twins.

- **`IFileClipboardService` is the system clipboard as far as files go**, async by contract (another program may hold the clipboard open for a moment). `WindowsFileClipboardService` writes what Explorer writes — `CF_HDROP` (a DROPFILES header and wide, double-null-terminated paths) and "Preferred DropEffect" (1 copy, 2 move, which is the whole difference between Ctrl+C and Ctrl+X) — with plain Win32, no OLE and no STA thread; the clipboard's owner is the console window, because a null owner makes `SetClipboardData` fail after `EmptyClipboard` succeeded. `LinuxFileClipboardService` uses `wl-copy`/`xclip` with `x-special/gnome-copied-files` (`copy`/`cut` then `file://` URIs); it has not been run on a real Linux desktop. `FallbackFileClipboardService` (what DI registers) answers from an `InProcessFileClipboardService` for the rest of the run once the system one has failed, so a copy and its paste still agree. The end-to-end suite registers the in-process one: a run must not overwrite what its user had copied.
- **Only local entries go on the clipboard** (`FileClipboardOperations.LocalPathsOf`): another program is handed a path. What is copied is what F5 acts on — `FocusedEntry.ActionableUrls`, the marks else the cursor row — and never the `..` row. Marks are left standing (a copy does not consume them, unlike F5).
- **Cut is a promise, not an act**: nothing is touched until the paste, and what moves is whatever still exists then.
- **Paste goes through the F5/Shift+F6 tasks** (`TransferCommand.StartAsync`, a dialog-less twin of the dialog's path), so it has their progress window, cancel, panel refresh and completion toast. It never overwrites — there is no conflict dialog to ask in: a copy pasted into the folder it came from is named like Explorer does (`a - Copy.txt`, `a - Copy (2).txt`), a cut pasted there does nothing, a folder is refused into itself, and a file gone since the copy is skipped with a notification. `FileClipboardOperations.Plan` is the pure part a test can call.
- **Ctrl+C and Ctrl+X were taken.** Ctrl+C is `QuitCommand`'s alternate key and Ctrl+X the password manager's. The clipboard commands sit on every `ContentBrowser` and decline (`CanExecute`) when there is nothing a file operation may act on, so on the `..` row, an empty folder and every non-file-panel context both keys behave as before; on a file Ctrl+C copies instead of quitting (F10 quits) and Ctrl+X cuts. The password manager's always-reachable chord is therefore **Ctrl+Shift+X** (`PasswordManagerDialogCommand.AlternateKey`). A command built for a panel acts only while that panel's model is the focused one (the same identity gate as the music commands).
- **Terminals may keep Ctrl+V for themselves**: Windows Terminal turns Ctrl+V and Shift+Insert into a text paste (of the clipboard's file *names*) and the app never sees the key. Unbind them in the terminal's settings, or use the Edit menu / the command palette (Shift+F1).

### Drive actions in the disk manager: eject, format, disk images, BitLocker (`Services/Drives/`, `DiskManagerDialog`)
Alt+F9 lists the drives and, under the list, what is known about the one under the cursor (label, type, file system, space, BitLocker). **E** safely ejects it, **F** formats it, **M** mounts or unmounts an ISO/VHD/VHDX by path, **B** reads BitLocker again. A panel with the cursor on an image offers **Ctrl+Shift+F11** (`MountDiskImageDialogCommand`) with the file already filled in; Enter on an ISO stays "open as an archive".

- **`IDriveActionsService` runs the platform's own tools** through `IExternalProcessRunner` (so it is faked in tests): PowerShell's storage cmdlets (`Format-Volume`, `Mount-DiskImage`, `Dismount-DiskImage`) and the shell's Eject verb on Windows, `udisksctl`/`findmnt`/`lsblk`/`losetup` on Linux. Nothing is P/Invoked. A letter reaches a script only after a strict pattern match, a file system only from `DriveActionsService.FileSystems`, a path/label only quoted — nothing typed is spliced in as code. Linux formatting is not offered (`CanFormat`); BitLocker is Windows-only.
- **Everything is a background task** and the dialog says "Ejecting E: ..." until it ends; the outcome is the status line *and* a toast (the dialog may have been closed). Facts about the drive under the cursor are read on a task when the cursor arrives (`FollowCursor`, guarded by a generation counter so a slow read cannot paint over the row the user moved to): `DriveInfo.IsReady`, `VolumeLabel` and `DriveFormat` block for seconds on a card reader, and `Draw` must not wait.
- **BitLocker is read from the shell property** `System.Volume.BitLockerProtection` (what Explorer draws its padlock from), because `Get-BitLockerVolume` and `manage-bde` need an elevated session and this does not. 0 is shown as Off and 1 as On; any other value is shown as "Unknown state (n)" rather than guessed — the meaning of the other values is not documented anywhere checked.
- **Eject** accepts a removable or optical drive, or a fixed disk on the USB bus, and waits (up to 10 s) for the letter to disappear before saying "can be removed safely"; "in use" is reported otherwise. An ISO mounted as a CD-ROM drive is dismounted by the same Eject.
- **Format is hard to do by accident**: `WhyCannotFormat` refuses the system drive, network/optical/RAM drives, and any drive a panel (or this program, or the working folder) is on — before the dialog opens — and `FormatDriveDialog` makes the drive letter be typed back. It needs an elevated session; an "Access is denied" is turned into "start iTerminal as administrator". Quick by default.
- **The end-to-end suite registers `SandboxServices.DriveActions`**, which records the calls: no test may eject, format or mount a drive of the machine running it. Mounting a VHD and dismounting by drive (rather than by image path) are exercised against the fake only.

### The recycle drive (`recycle://`, Ctrl+F8)
Ctrl+F8 — beside F8, which fills it — points the focused panel at the recycle bin: one flat list of what was deleted, newest first, each row dated by *when it was deleted* and the info strip saying where from. **Enter restores** the row under the cursor or the marked rows to where they were deleted from; **F8 deletes for good**, through the ordinary Delete dialog; F3, quick view and F5 read a deleted file where it lies. Pressed again, Ctrl+F8 goes back. It is a `ContentModelAsyncDrive`, so listing never runs on the key handler.

- **The bin is read from the files it is made of, not through the shell** (`IRecycleBinStore`). On Windows every volume keeps `\$Recycle.Bin\<SID>`, where a deleted file is a pair: `$R<random>.ext`, the file, and `$I<random>.ext`, a record of its original path, size and deletion time (`WindowsRecycleBinStore.ParseRecord`: version 1 is a fixed 260-character path field, version 2 a length and that many characters). Restoring is moving the `$R` file back — always within one volume, so a rename — and removing the record. The shell's COM route restores by invoking a verb whose name is translated with the system's language; the file format has been stable since Vista, and makes the store something a test can build in a temporary folder. On Linux it is the freedesktop trash (`~/.local/share/Trash/files` + `info/*.trashinfo`), the home trash only. macOS keeps no record of where a file in the Trash came from, so the drive says so instead of listing.
- **A row's URL is its name** (`recycle://report.pdf`), not an id: copying a row out then names the copy correctly, and `Url.ParentUrl` is `recycle://`, which is what `PanelRefreshHelper` matches a panel by after a delete. Two deleted files can share a name, so the second is listed as `report (2).pdf` — numbered oldest first, by the store's key on a tie (`RecycleBinService.Name`), so a row's URL does not move between listings. The service keeps the name→item map of the last listing.
- **A deleted folder is one row, and a file to every operation** (no trailing slash). Restore and delete-for-good take the whole folder, the only thing either can mean here; it cannot be entered or copied out. Were it a folder URL, F8 would send the delete discovery walking into it.
- **Restore asks nothing and never overwrites.** It is undone by deleting the file again, so a y/n would be noise; and when something has taken the deleted file's place it is reported ("already exists there") and both are left alone — what is there now is the newer of the two. The folder it was in is recreated if that was deleted too. The outcome is written to the footer *after* the re-listing lands, as on the docker drive (a listing clears the status).
- **Emptying the bin is Mark All, then F8** — the Delete dialog is the confirmation, and there is no separate "empty" key to press by accident. On this drive the dialog's recycle box is off: `RecycleBinService.DeleteFile` purges whatever the flag says.
- **`RestoreRecycledCommand` (Enter) reads the focused model and nothing of its own**, so both panels' instances answer alike, and declines on the `..` row, where Enter still leaves the drive.
- **The end-to-end suite registers a store rooted in the sandbox** (`TerminalApp.RecycleBinFolder`, in the Windows format on every system; `PutInRecycleBin` seeds it). The drive restores and deletes for good: **no test may reach the real bin through the app**, and `RecycleBinTest` builds its bins under a temp folder for the same reason.
- **On Linux F8 puts the file in the freedesktop Trash** (`FreedesktopTrash`, `ITrashService`; the Delete dialog's box reads *Move to Trash*), in the form `FreedesktopTrashStore` and every Linux file manager read: `files/<name>` plus `info/<name>.trashinfo` (`Path=` percent-encoded, `DeletionDate=` local time). A file on the same volume as `$XDG_DATA_HOME/Trash` goes there with its absolute path; one on another mount goes to `<mount>/.Trash-<uid>` with a path *relative to the mount point*, because moving it to the home trash would be a copy across volumes — a slow delete that can fail half-done. Volumes come from `/proc/self/mountinfo` (longest mount point that contains the path; octal escapes such as ` ` are decoded). The name is reserved by creating its `.trashinfo` with `FileMode.CreateNew` before the file moves (`name`, `name.2`, …), so two programs trashing `a.txt` do not collide, and a failed move removes the record again. A file already inside a trash is deleted for good (nowhere further to move it); a volume where no trash can be made throws in words rather than silently deleting. The store lists the home trash *and* the existing `.Trash-<uid>` / `.Trash/<uid>` folders. `directorysizes` is not maintained (readers rebuild it). The end-to-end suite registers a `FreedesktopTrash` rooted in the sandbox with no per-volume trashes: **no test may put a file in the real Trash.**
- Not built: browsing inside a deleted folder, and the `$topdir/.Trash` (sticky-bit) variant of a per-volume trash — `.Trash-<uid>` is the form the specification allows when it is absent.

**The info strip follows a panel's model across a change of drive kind** (`ItemInformation.FollowModelSwap`). A navigation that crosses drive kinds replaces the panel's model with a new instance, and nothing handed that instance to the strip: it went on describing the old model's cursor row — "Up to: …" for the folder the panel had left — for as long as the panel stayed on docker, git, an archive or the search results. It now asks the service for the model registered under its panel's name whenever `ModelChanged` fires.

### Panel sort modes (`PanelSort`, `SortDialog` Shift+F11)
Shift+F11 orders the focused panel by name, extension, size or date, either way, or "as listed" — the drive's own order, which is the default and what every panel did before. In the dialog a mode's first letter applies it at once, `r` reverses and leaves the dialog open, ↑/↓ and Enter choose. The footer says `Sort: size ↓` whenever the order is not the drive's own.

- **The sort is applied in `ContentModelBase.FilteredEntries`**, the one list the cursor, the marks and the drawing all index — so every drive sorts alike and none has to know how, and "the row under the cursor" is the same row to F5, F8 and Insert as it is on screen. The sort is part of the snapshot's stamp, beside the filter and the entries version.
- **Three things hold whatever the mode** (`PanelSort.Apply`): the `..` row stays first; folders stay ahead of files in *both* directions ("largest first" must not bury the folders); and rows that tie are in name order, ascending — a sort by extension or date then reads as a list, and reversing does not shuffle the ties.
- **"As listed" is a mode, not the absence of one.** The drives' own orders mean something — newest first in the recycle bin, history order on the git drive — and a default of "by name" would have discarded them.
- **The order is the panel's, not the drive's or the folder's**: saved as `<panel>.Sort` (`Size,desc`), and `ContentModelService.AddContentModel` gives it to every new model, so it survives a change of drive kind — which makes a new model instance — and a restart.
- **`SetSort` keeps the cursor on its entry**, by URL: the entry is what the user was looking at, and it is somewhere else in the new order.
- **Size comes from the row where the row knows it** (`VirtualDriveEntry.Size`) and from `Url.Length` otherwise; date is the listing's own `Date`+`Time` text, which sorts as text and is to the minute.
- The music drives and the preview opt out (`CanSort => false`): a queue's order is the queue, and a preview's rows are the lines of a file.

### The Panels settings page (`SettingsPanelsTabPage`, tab 6 of Shift+F8)
Each panel's order (the same `<panel>.Sort` setting Shift+F11 writes, here for both panels at once) and three options that hold for both: **show hidden files and folders**, **keep folders ahead of files when sorting**, and **sort numbers in names by value**. All three default to what the panels did before the page existed, except the last — and that one only matters once a sort by name is chosen.

- **A change on the page is the setting**, as on every page of this dialog: written as it is made, and pushed into the open panels (`ISortableContentModel.SetSort` / `SetViewOptions`), which re-list behind the dialog. `_loading` keeps filling the controls from the settings from being read as the user changing them. The page is filled again every time the dialog opens, since Shift+F11 may have changed a panel's order in between.
- **`PanelViewOptions` travels the way the sort does**: `ContentModelService.AddContentModel` loads it into every new model, and it is part of the `FilteredEntries` snapshot's stamp. Both go through `ContentModelBase.Reorder`, which keeps the cursor on its entry — and on a row that exists when the entry itself has just been hidden.
- **Hidden means what the local disk says** (`Url.IsHidden`): the Hidden attribute on Windows, a leading dot elsewhere — which is how .NET reports that attribute there. Other drives have nothing to say and hide nothing. **The `..` row is never hidden**: inside a hidden folder its URL is that hidden folder's parent chain, and it is still the way out. Hiding is filtering in `PanelSort.Apply`, so it also applies under "as listed" — the one thing that mode does not leave alone.
- **Hidden entries are only not listed.** A recursive delete, a copy or a folder's size still include them: those walk the disk, not the panel.
- **`PanelSort.NaturalCompare` never parses the numbers**: a run of digits is compared by its length with leading zeros off, then digit by digit, so a name with thirty digits sorts correctly. `file01` and `file1` are the same number and fall back to plain text order, so the sort is stable.
- With "folders ahead of files" off, folders sort among the files by the same key (a folder has no size or extension of its own, so by name there).

### The command palette (Shift+F1)
`CommandPaletteDialog`: every command that can run now, by name, with its key beside it; type to narrow (every word must match the title, key or description, in any order), ↑/↓ and Enter to run; with an empty query the commands run last (setting `CommandPalette.Recent`) come first. `CommandCatalog.Collect` walks the whole control tree **including hidden controls** — the hot key bar's Ctrl/Alt layers and every closed menu are hidden and hold most features — keeps a command only if `CanExecute()` (first per key per control, as F1 help does), and leaves out plain cursor and typing keys.

- **The list is gathered before the palette opens** (`CommandPaletteDialogCommand.OnBeforeShow`), while the panel still has focus: a panel's commands only say they apply while their panel is the focused one, and once a dialog is up nothing is.
- **Running a command closes the palette first**: `Dialog.Close` hands focus back synchronously, so the chosen command runs against the panel the palette was opened over. A new command's `Title` and `Description` are what the palette shows — the default title is made from the type name ("Theme Manager Dialog"), so give every user-facing command its own.

### Comparing folders (Shift+F2)
`CompareFoldersDialog` compares the folders the two panels show (`FolderComparer`), lists every difference (◀ only left, newer right ▶, ≠ different…), and **ends in marks**: each panel gets marked what that side has and the other lacks or holds an older copy of, so F5 from either panel is the sync. What differs with no newer side — same date and different size or bytes, a file against a folder, a folder with changes both ways — is listed but marked on neither: which copy wins is the user's call.

- **Modes**: name + size + date (default), name + size, name + content (both files are read and hashed; a local file directly, any other through `StreamToAsync`). "Include subfolders" looks into folders present on both sides; a folder then stands for what is inside it (`FolderComparer.Aggregate`: newer on the left when every difference inside points left).
- **Any two drives compare**: a local side is listed with `DirectoryInfo` (dates to the second), the archive/docker/git drives through `IEntryListingFileSystem.ListAsync` (their entries carry size and date; the bare URLs `ListChildren` returns do not), the rest through the F5 walker. **Dates are compared at the coarser side's resolution** — within 2 s for two local files, to the minute otherwise — or a folder and a fresh ZIP of it would come out "newer" over rounding.
- The comparison runs on a background task (`CompareTask` is the test seam); closing the dialog cancels it. Marks are applied only to a panel still showing the compared folder. Enter is claimed by the dialog ahead of its controls — the compare-mode `ComboBox` takes focus first and would answer Enter by opening itself.
- `FileSystemResolver` is the one answer to "which `IFileSystem` serves this URL" — copy, move, delete, compress, extract and compare all ask it (see the URL-scheme notes).

### Comparing files (Ctrl+F10) and the right-click menu
`DiffFilesDialogCommand` opens `FileDiffDialog`: two files side by side, differences coloured, `N`/`P` to the next/previous difference, `W` ignores whitespace, `C` ignores case. Which two: exactly two marked files in the focused panel, otherwise the cursor file against the other panel's cursor file.

- **The engine is `TextDiff`** (Myers O(ND), common ends peeled off first). A run of deletions beside a run of insertions is paired into `Changed` rows so an edit sits beside its old self. The search gives up at `MaxEdits` and shows what is left between the shared ends as replaced (`IsApproximate`) — its memory is the square of that figure.
- **Reading is bounded and off the key handler** (`LoadTask`): a local file directly, any other drive through the `IFileSystem` the command resolved while the panel still had focus; over `MaxBytes` (8 MB) is refused in words; a NUL near the start makes a file binary and it is compared by bytes only. Text is UTF-8 or, failing that, Latin-1 — never with replacement characters.
- **Right-click on a row** moves the cursor there and opens a `Popup` at the pointer (`ContentBrowser.ShowContextMenuAsync`, `Popup.Anchor` for a manual placement). `FileContextMenu.Build` offers nothing of its own: Open (Enter), "Open with/Edit with <program>" from the file associations, then the panel's own commands by type, each only if `CanExecute()` and with its key. A choice runs *after* the popup has closed and handed focus back, so the command finds the panel focused. Nothing on `..`, on container rows or on the music drives.

### Compressing (Alt+F5)
`CompressDialog` packs the marked rows (or the cursor row) into a new archive or adds them to an existing one; `CompressTask` does the work and `IArchiveCompressionService` writes. Formats (`ArchiveFormat`): ZIP (levels 0–9, password with AES-256 or ZipCrypto), 7z (levels 0–9, AES-256, optionally encrypted names), TAR.GZ, TAR.BZ2 (levels 1–9) and TAR. Each format declares what it honours, and the dialog *disables* the rest rather than accept a setting that would be ignored. The archive's name and the format follow each other: typing `.7z` picks 7z, picking TAR.GZ renames `x.zip` to `x.tar.gz`.

- **ZIP and the TAR family are SharpZipLib** (`ManagedArchiveWriter`): the BCL cannot write an encrypted ZIP. **7z is the 7-Zip CLI** (`SevenZipArchiveWriter`), found on PATH or in `%ProgramFiles%\7-Zip` (its installer does not add itself to PATH); without it, 7z is left out of the list and the hint says why.
- **Adding to an existing ZIP/TAR rewrites it**: entries are read into a new archive beside the old one, the new files added, and the result moved over the old file only once complete — a failure or Cancel leaves the old archive byte for byte. An encrypted ZIP can only be added to with its password. 7-Zip adds to its own archives in place. "Replace files the archive already has" decides which copy of a duplicate name wins.
- **The 7z password goes to 7-Zip on stdin (`-p` with no value), never on the command line**, and is written *twice*: adding to an archive with encrypted names, 7-Zip asks once to open it and once for the new entries. Stdin is redirected even with no password: an encrypted archive makes 7-Zip ask anyway, and with the app's console inherited it waited forever. Closed, it exits 255, which `DescribeFailure` turns into words.
- Sources come from any drive (walked with `ContentModelFolderTaskHelper.ListChildren`; the archive itself is never put inside itself), and the archive may live on any drive: a non-local one is fetched to a temp folder, written, and uploaded. TAR needs each file's length before its bytes, so a file not on the local disk is staged first.

### Extracting (Shift+F5)
`ExtractDialog` unpacks the marked archives (or the one under the cursor; non-archives among the marks are ignored, and the key is not offered without one) into a folder — the other panel's by default, **each archive into a folder of its own** unless unticked, which is also what keeps two archives holding the same file name from overwriting each other. `ExtractTask` runs the archives in order (a failure is listed, the rest still go); `IArchiveExtractionService` (`ArchiveExtractionService`) unpacks.

- **What reads what.** ZIP (AES-256 and ZipCrypto), TAR, TAR.GZ, TAR.BZ2 and a lone `.gz`/`.bz2` are read in-process with SharpZipLib; 7z, RAR, XZ (and `.tar.xz`: 7-Zip takes off the XZ, the TAR is unpacked here), ISO and CAB go to the 7-Zip CLI. A 7-Zip format on a machine without it is still offered, and the dialog says on opening why it will fail.
- **Nothing is written outside the target folder**: `SafePath` refuses an entry named `../x`, an absolute path or a drive letter (the "zip slip"), counts it, and goes on; TAR links and devices are skipped for the same reason.
- **Passwords**: a missing one and a wrong one are told apart in words. A file whose ZipCrypto check fails is deleted rather than left half-written. **7-Zip gets no `-p` when extracting** — there a bare `-p` means "the password is empty" (when *adding* it means "ask") — so it asks only if the archive is encrypted and reads the answer from stdin; without a password it meets the closed stream. Its "Wrong password?" also appears when none was given, so which message is right is decided by whether one was typed.
- "Overwrite files that are already there" is off by default (`-aos` / skip); archives and targets on other drives are fetched to and uploaded from a temp folder, like Alt+F5.
- **Name a child of a folder URL with `UrlPath.Child`**: trimming separators and appending one turned `memdrive://` into `memdrive:` and "a folder in the memory drive's root" into a local path. The copy dialog's per-item targets and Alt+F5's default name had the same bug.

Inside a dialog **`GetFocusedModel()` is null**: opening a dialog takes focus from the panel, and `ContentPanel` clears `FocusedPanel` when it loses it. A dialog that acts on "the panel" uses `GetLastContentModel()`; a command that can also run from an open menu uses `GetFocusedModel() ?? GetLastContentModel()`.

### Runtime dependencies (`Services/RuntimeDependencies/`, `RuntimeDependencyDialog`)
Components the app needs at run time but does not ship are downloaded into the data folder (`%APPDATA%/iTerminal/runtimes`) by a setup dialog, not packaged. Today that is Playwright — the .NET library is shipped, but its driver (a Node.js runtime and Playwright's JavaScript package, ~130 MB) and the Chromium it drives are not — and Ollama, the local model server the AI bar talks to (see the last bullets of this section).

- **The shipped build must not carry the driver.** `Microsoft.Playwright` is referenced with `ExcludeAssets="build;buildTransitive"`: its build targets are what copy `.playwright` into the output, and the Windows installer and the Linux packages both pack whatever was published. Remove that attribute and every package grows by the driver again.
- **`PlaywrightRuntimeDependency` installs the driver from the NuGet package for the version the build was compiled against** (`Microsoft.Playwright` `<v>.nupkg`, `.playwright/package` and this machine's Node only), then runs the driver's own `install chromium`. The package is checked against the SHA-512 its NuGet catalog entry records before anything is unpacked, and a mismatch is deleted. The library finds the driver through `PLAYWRIGHT_DRIVER_SEARCH_PATH` and the browsers through `PLAYWRIGHT_BROWSERS_PATH`, both set by `Activate()` — nothing has to sit next to the executable. The nupkg is ~210 MB because it carries Node for every platform.
- **An update stays on the build's line** (same major.minor). Playwright's protocol is tied to its library, so a newer line is reported as a note ("1.64.0 is out, but this build uses 1.63.0") rather than installed; adopting it is a rebuild.
- **`OllamaRuntimeDependency` is the same contract for Ollama, from GitHub releases**: versions come from `ollama/ollama` (stable tags only, the same `major.minor` line rule as Playwright), and the program is the asset of this platform (`ollama-linux-amd64.tar.zst`, `ollama-windows-amd64.zip`, `ollama-darwin.tgz`). The download is checked against the `sha256` digest GitHub records for the asset, and an asset without one is refused. Linux ships zstd only, so `ZstdSharp.Port` decodes it (.NET has no zstd in its BCL). Extraction refuses entries that would land outside the folder, and keeps symlinks only when their target stays inside too. A version counts as installed only with the configured model downloaded into it (`model.installed` holds the name); installing pulls the model through `/api/pull` on a server started for the purpose.
- **`OllamaServer` never takes over a server that is already there**: `EnsureRunningAsync` returns at once when the configured address answers (a system Ollama is used as it is), starts `ollama serve` from the data folder only when nothing answers and the address is this computer, and stops only the process it started. `OllamaServerJob` keeps that server up while the app runs and re-checks the AI bar (`CheckAvailabilityAsync`) whenever reachability changes, because the bar checks once when it starts. Only registered when `AI:Provider` is `Ollama`; the end-to-end suite omits the job and replaces the dependency service.
- **An Ollama that was there before iTerminal counts as installed** (`IRuntimeDependency.IsExistingInstall` / `ExistingInstallNote`, default no). `OllamaRuntimeDependency` looks for a running server (`OllamaServer.GetInfoAsync`: version and models, asked during the *check*, never from `InstalledVersion`, which runs on the render thread) and for an `ollama` program on the PATH and the usual per-OS folders (never one inside the data folder). It is complete once the configured model is in it (the server holds it, or `model.installed` says it was pulled). Such an install is never offered an update, is started by `OllamaServerJob` with its own models folder (`ModelsDirectoryFor` returns null, so `OLLAMA_MODELS` is not set), and installing only pulls the model. Tests pass the search folders explicitly (`null` looks nowhere) so a machine with Ollama on it cannot change the result.
- **The runtime-dependency dialog lets each dependency be ticked** (Up/Down move, Space ticks, every one that needs work starts ticked; shown only when more than one does). Enter installs and S skips the ticked ones through `IRuntimeDependencyService.StartInstall(ids)` / `SkipOffers(ids)`; with all ticked the parameterless calls are used, as before.
- **`RuntimeDependencyService` owns the list**: `Statuses` is an immutable snapshot replaced whole, the install log is capped, and one install runs at a time (`StartInstall`). Settings keep the newest version seen (`RuntimeDependencies.Latest.<id>`, so the start-up offer needs no network), the skipped version (`…Skipped.<id>`) and the announced one (`…Announced.<id>`).
- **Start-up** (`TerminalScreen.OnInitializeAsync`) opens the dialog when something is missing or newer and not skipped for that exact version. `RuntimeDependencyCheckJob` checks the publisher 30 s after start and every 12 h, and announces a new version once by notification; the offer at the next start and Tools > Runtime Dependencies show it until it is installed or skipped.
- **`OnlineQuoteJob` waits** while Playwright is not installed, and a failed launch calls `InvalidateInstalled` so the dialog offers Chromium again. It no longer runs `pwsh playwright.ps1`.
- The end-to-end suite replaces the service with `SandboxServices.Dependencies` (nothing to install, no offer) and omits the check job, so no run downloads anything or opens the offer over the panels.

### Cloud drives, disk usage and elevation (`Services/Cloud/`, `Services/DiskUsage/`, `Services/Elevation/`)
- **`s3://[accessKeyId@]bucket/key`, `onedrive://[account]/path`, `gdrive://[account]/path`** are `ContentModelAsyncDrive`s over `HttpFileSystemServiceBase` (signing/retry/spooled uploads); listing and sign-in never run on a key handler. S3 is hand-signed (`AwsSignatureV4`, checked against AWS's worked examples), path-style on custom endpoints, region learned per bucket from `x-amz-bucket-region`; credentials come from a password-manager entry titled `S3…` (user name = access key id, password = secret, notes `endpoint=`/`region=`/`token=`), else `AWS_*` env, else unsigned (public buckets).
- **OneDrive (Graph) and Google Drive use the OAuth device flow** (`OAuthTokenProvider`): no client id is shipped, so set `Cloud:OneDrive:ClientId` / `Cloud:GoogleDrive:ClientId`+`ClientSecret` in `appSettings.json`. The first listing starts the grant, posts the code as a persistent notification and throws `CloudSignInRequiredException` (shown in the footer); Ctrl+R after approving. Refresh tokens live in the password manager. Deletes go to the provider's own bin/trash. Drive has no paths: `GoogleDriveFileSystemService` resolves segment by segment with a 60 s cache.
- **Disk usage, Ctrl+Shift+F12** (`DiskUsageDialog`): background walk of a local folder (links not followed), tree kept in memory with the 40 largest files per folder; Enter/←, `g` goes to the panel, `s` sort, `r` rescan.
- **Elevation, Ctrl+Shift+A restarts as administrator/root, Ctrl+Shift+R runs the program under the cursor elevated** (`IElevationService`). Windows: `runas`, the new copy gets `--wait-for-parent <pid>` so it opens the data folder only after this one exited. Unix: `sudo -v` on the lent terminal, then `PendingRelaunch` makes `Program.cs` `execvp` `sudo iTerminal` after shutdown; an elevated Unix session uses root's own data folder when sudo resets HOME. The Unix paths and live OneDrive/Google/S3 calls have not been exercised against real services.

### `iTerminal` — composition root
`Program.cs` (top-level statements) wires DI via `AddiConsoleCore()` and `AddiTerminal()`. New services and controls should be registered in `iConsoleApplicationBuilderExtension` or `iTerminalApplicationBuilderExtension`, not in `Program.cs`. `appSettings.json` holds the `FeatureManagement` flags and the `AI` section (`Provider` — `None` (no AI, Ollama is never offered), `Ollama` (the default; the server is downloaded when the start-up offer is accepted) or `OpenAI` for an OpenAI-compatible API — the model id, base URL, `DisableThinking`, prompt-bar height).

### `iTerminal.Installer` — the Windows installer
A WiX Toolset 5 project (`WixToolset.Sdk` from NuGet — nothing to install on the build machine) that produces `bin/Release/iTerminal-<version>-x64.msi`: the app in `Program Files\iTerminal`, a Start menu shortcut, the install folder on the machine PATH (a feature, on by default), an entry in Apps & features, and in-place upgrade.

- **Building it publishes the app** (`PublishApp` in the `.wixproj`): `dotnet publish ../iTerminal -c Release -r win-x64 --self-contained` into `obj/publish`, emptied first. The MSI therefore needs no .NET runtime on the target machine, and always holds the app as it is in the checkout. It is a separate `dotnet publish` rather than an MSBuild task call so the runtime identifier does not leak into the installer project's own evaluation.
- **`Package.wxs` packs whatever was published** (`<Files Include="…**">`), minus `*.pdb` and `*.log`: listing files by name would have to be kept in step with every package the app references. Only `iTerminal.exe` is authored by hand, because the shortcut points at it. A file added to the app's output needs nothing here.
- **In the solution, never built by it** (`<Build Project="false" />` in `iTerminal.slnx`): it is Windows-only, and it publishes and compresses ~240 MB each time. `dotnet build iTerminal.slnx` and `dotnet test iTerminal.slnx` are unaffected.
- **`UpgradeCode` in `Package.wxs` must never change** — it is what lets a newer MSI find and replace an older install (`MajorUpgrade`). The version comes from `-p:Version=`, default `1.0.0`, and is also stamped on the published `iTerminal.exe`; Windows Installer only compares the first three parts.
- **The shortcut starts in Documents, not in the install folder**: the app writes `iTerminal.log` into its working directory (`Logger` — a relative path), and `Program Files` is not the user's to write to. Started from a shell, the log still lands in whatever folder the shell is in; moving it under the data directory is an app change, not an installer one.
- **The wizard has no licence page** — the repository has no licence text, so `WixUI_InstallDir`'s page is skipped by two `Publish` elements. Add a `License.rtf` and remove them to bring it back.
- **Not signed, and no icon**: Windows SmartScreen will warn on an unsigned MSI. Signing needs a certificate (`signtool` after the build).
- Most of the size is the .NET runtime. The Playwright driver is not in the package: the app downloads it on first start (see *Runtime dependencies*).
- **To check an MSI without installing it**, extract it: `msiexec /a <msi> /qn TARGETDIR=<short path>` — a short path, since Windows Installer refuses paths over 260 characters and the Playwright files are deep. The ICE60 warnings in the build are about four font-like files without a language and are harmless.

### `iTerminal.Packaging.Linux` — tar.gz, deb and rpm
One command produces, per runtime, `iterminal-<v>-linux-x64.tar.gz`, `iterminal_<v>_amd64.deb` and `iterminal-<v>-0.x86_64.rpm` in `iTerminal.Packaging.Linux/bin/Release` — all self-contained, so the target needs no .NET runtime. The packages install to `/usr/share/iterminal` with `/usr/local/bin/iTerminal` linking to the executable; the tarball unpacks to `iterminal-<v>/`, run `./iTerminal` from it.

- **The formats are written by Packaging.Targets** (NuGet, MSBuild tasks in managed code): no `dpkg`, no `rpmbuild`, so the packages build on Windows as well as on Linux. Its targets have to be in the project being packaged, so `iTerminal.csproj` references it — **only when `LinuxPackaging` is `true`**, which only the packaging project sets. An ordinary build neither restores nor loads it.
- **`iTerminal.Packaging.Linux.proj` is the loop and the names**: for each runtime in `Runtimes` it runs `dotnet msbuild ../iTerminal -restore -t:CreateTarball;CreateDeb;CreateRpm` as its own process (the runtime identifier must not leak into anything else, and the restore has to be for that runtime), then copies the results to the names each format's tools expect. `KnownRuntime` maps a runtime to Debian's and RPM's word for the architecture; a runtime not listed there is refused by name. It is a plain MSBuild file, not in the solution.
- **The Debian dependency list is ours, in `iTerminal.csproj`.** Packaging.Targets' own stops at `libssl1.1` and `libicu70`, which nothing since Ubuntu 22.04 ships — with it the package cannot be installed on a current system at all. Each line is alternatives (`libssl3t64 | libssl3 | libssl1.1`); **a new Debian or Ubuntu release means a new `libicuNN` to add**.
- **The RPM is finished by `RpmFinisher.cs`** (an inline MSBuild task — compiled against .NET Standard 2.0, which is why it is written the old way), run on the copied RPM. Packaging.Targets' RPMs **cannot be installed on a current Fedora**: their signature header holds two placeholder signatures, a SHA-1 and an MD5, and no payload digest, and rpm 6 (Fedora 44) answers "does not verify: no digest" — 0.1.232, the latest, is no different. The task puts the payload's SHA-256 in the main header (`PAYLOADDIGEST`) and writes a new signature header with the header's SHA-1 and SHA-256, the MD5 and the sizes, and no signatures. It also **replaces the dependencies**: the tool's are Fedora package names (`openssl-libs`, `libicu`, `krb5-libs`), which openSUSE does not have, so zypper refused the package. `RpmRequire` in the `.proj` lists shared-library names instead (`libssl.so.3()(64bit)`), which every RPM distribution's packages provide whatever they are called, and ICU — whose library carries its version in its name — as one rich dependency, `(libicuuc.so.80()(64bit) or … or libicuuc.so.60()(64bit))` (the task adds `rpmlib(RichDependencies)` for it). `SkipRpmDependencies` keeps the tool's list out. The rest of the header and the payload are kept byte for byte. `-t:FinishRpm -p:RpmToFinish=<rpm>` runs the task alone, without rebuilding the app.
- **The RPM has a `%postun` that removes `/usr/share/iterminal` on uninstall** (`PostRemoveScript` in `iTerminal.csproj`: `if [ "$1" = 0 ]; then rm -rf /usr/share/iterminal; fi`). rpm removes the files it installed but not the folders, which the tool never lists, so a removed package left a tree of empty folders. `$1` is the number of versions left: 0 is an uninstall, 1 an upgrade, when the folder holds the new version. The app writes nothing there. It is not `find -empty -delete`, which it was first: openSUSE's base system has no `find`, and the script silently did nothing. **The `.deb` gets no such script** — dpkg removes its own folders, and a `.deb` with a `postrm` is kept as "config-files" after `dpkg -r` until it is purged — which is why the packaging project builds the tarball and the `.deb` in one inner build and the RPM in a second, with `LinuxPackagingRpm=true` (incremental, so it costs little).
- **Two switches go on the inner command line because they must reach the referenced projects too**: `DebugType=none`/`DebugSymbols=false` (set in the csproj they cover that project only, and four `.pdb` files came along). The Playwright driver is not in the package at all (see *Runtime dependencies*), so the old `PlaywrightPlatform` switch is gone.
- **`TarballPrefix` starts with a slash**: the task writes `.` in front of it, and without one the top folder is `.iterminal-<v>` — hidden.
- **What has been tested, and where** (`x86_64` only). **Ubuntu 22.04** (WSL): the tarball unpacked and run; the `.deb` installed with `dpkg -i` (its dependencies resolve with nothing extra to install), checked against its own `md5sums`, run, removed. **Fedora 44** and **openSUSE Tumbleweed** (Docker containers): the `.rpm` installed with `dnf` and `zypper` — each pulling in its own ICU (77 and 78) — `rpm -K` "digests OK", `rpm -V` clean, run, removed. In every case the app was started by an ordinary user from the PATH on a pseudo-terminal (`script -qec "stty rows 40 cols 140; timeout 8 iTerminal"` — it draws the menu, the splash and the hot key bar), with its data in `~/.config/iTerminal` and nothing written into `/usr/share/iterminal`. `dpkg -r` warns that `/usr/local` is not empty: the package lists that folder because the link is in `/usr/local/bin`. zypper needs `--allow-unsigned-rpm`: the RPM is not signed.
- **The data folder's parent is asked for with `SpecialFolderOption.Create`** (`iTerminalApplicationBuilderExtension.UserDataRoot`, also used by the vault and the playlists). That first run on Linux is what found it: on an account with no `~/.config` yet, `Environment.GetFolderPath(ApplicationData)` answers with an *empty string*, and "iTerminal" under an empty string is a folder in whatever directory the app was started from — the database, the vault keys and the playlists, a new set in every folder the app was run in.
- What the tool decides and this project does not: the RPM's summary ("iterminal version 1.2.3-0") and licence field ("iterminal License"), and `/usr/local/bin` rather than `/usr/bin` for the link.
- `linux-arm64` is mapped but has not been built here.

## Key patterns

**Navigation flow**: Key event → `ContentBrowser.HandleKeyEventAsync` → `Command.ExecuteAsync` → `ContentModelService.SetUrlAsync` → `ContentModelFileSystem.SetUrl` (synchronous, returns immediately after enqueuing `FilePanelRefreshTask`) → `TaskManager` runs refresh off-thread.

**`SetUrl` is non-blocking**: It cancels in-flight refresh tasks, clears entries, adds `..`, enqueues a new `FilePanelRefreshTask` (Input priority), and fires `SchedulePrefetch` via `Task.Run`. Key handlers must return within ~200 ms.

**Prefetch**: After navigating to a folder, `SchedulePrefetch` warms the memory cache for the parent and all immediate children at `Background` priority. A `CancellationTokenSource` swapped atomically with `Interlocked.Exchange` prevents stale prefetch tasks from running after a rapid navigation away.

**Stale-result guarding**: A refresh task compares its own `Url` against the model's current `Url` (`IsCurrentUrl()`) before every UI write, so a task that outlives a fast navigation cannot repaint the panel with the old folder. Any new async producer that writes into a content model needs the same check.

**UI update batching**: `ContentModelBase.Update()` is guarded by `FrequentExecutionGuardService` (max ~20 `PropertyChanged` per second). `Entries.ReplaceAll(list)` is the only safe way to do a bulk atomic swap of the entry list.

**`FilteredEntries` is a snapshot stamped with the entries version it was taken under**: the cache used to be invalidated by setting it to null, and a reader that took its snapshot just before a listing landed on a worker thread stored that stale snapshot *after* the invalidation — it was then served until the next change. A panel restoring its cursor (`RestoreNavigation`) read one row where there were several and parked the restore for a listing that had already arrived; the search panel's "go to this hit" intermittently landed on `..`. Don't reintroduce a cache that is invalidated by clearing.

**A control paints every cell of its rectangle, every time it draws**: `ControlRendererJob` never clears a layer between frames, so a cell a control skips keeps whatever the last frame left there. A `Label` whose text got shorter, a `ListBox` or `Table` whose rows were filtered away, a `TreeView` node that was collapsed — all used to leave the old text on screen until something else repainted that area. Pad lines to `ViewSize.Width` and draw blank rows below the content. The corollary: a parent must not draw *over* a child's rectangle expecting it to stay — the child repaints its whole area the next time it renders alone. That is why an empty list says so through `ListBox.EmptyText` / `Table.EmptyText` rather than the dialog writing a placeholder on top of it (the Git client's `(nothing staged)` used to).

**A layer is composited only where it was written, and a hidden control writes nothing**: `BufferLayer` tracks the cells each row was written to, and `Buffer.Merge` copies a layer over the ones below across exactly those cells. It used to grow its bounds by the `Size` argument of every `Write` — and most controls pass their whole `ViewSize` for each single row — then composite the whole bounding rectangle, blanks included: every dialog blanked the status lines below it, and an open menu blanked the panels beside it. `Control.Render` likewise draws nothing for a hidden control (a repaint from scratch marks the whole tree, and the status bar's hidden date pop-up drew its blank rectangle into layer 1 — invisible until a menu lifted itself onto that layer). A control that must clear its row when it has nothing to say stays visible and draws an empty line — `ErrorMessage` does.

**A child hidden in the constructor is visible after `ShowAsync`**: `Control.ShowAsync` runs `OnInitializeAsync` and *then* shows every child. A dialog with an on-demand part (an inline input, a connect form) must re-hide it by overriding `ShowAsync`, and must track "is it up" in its own flag rather than reading `IsVisible` — the package manager and portfolio dialogs keyed their footers off `IsVisible` and never drew them (key hints, y/n confirmations), and the network browser showed its connect form over the host list. `GitClientDialog`, `PackageManagerDialog` and `PortfolioManagerDialog` all use `_inputActive` + `ApplyInputVisibility`.

**A dialog's footer shows its status *and* its keys**: `SplitPaneDialog.DrawStatusAndHints` puts the status first (in its severity colour) and fills the rest with the key hints. Showing one or the other hid the keys for good after the first command reported anything. A `Button` built with a title shows *that* title; only a button built from a command alone follows the command's `Title` (which is what lets a calculator key read `[HEX]`) — hence "F1-Help" in the hot key bar and "Cancel" rather than a cut-off "Cancel Dia" on every form. Hint rows are fitted with `StringHelper.FitHints`, which leaves out whole hints from the end but keeps the last — so write them most important first and the way out (`Esc:close`) last; a row cut at the edge used to end in "Esc:clos".

**Nothing slow runs before a dialog appears**: HTTP (the AI model details), drive and interface enumeration (System Info) and terminal commands (`TerminalModel.StartCommand`) start on a background task and fill in afterwards, with a "Loading…/Collecting…" line meanwhile and a `…Task` property a test can await. A list that is empty says why through `EmptyText`; a list whose *filter* changed is rebuilt with `ListBox.RefreshItems` — `UpdateModel` only re-projects after the items change.

**An open dialog repaints itself at most 20 times a second**: `Dialog.OnIdle` marks the dialog changed so background results show up without an event, throttled to `IdleRepaintInterval` (50 ms). Unthrottled, the repaint ended every idle pass and the dialog redrew hundreds of times a second for as long as it was open. A list fed by a job says "Reading…" until the job's first pass (`DriveInfoModel.IsLoaded`, `NetworkInfoModel.IsLoaded`) — "No drives found" before the first look is a wrong answer, not an empty one. The panel's info strip does not count the `..` row: its URL is the parent, so the cursor's default position started a recursive count of the whole parent tree after every navigation; it says "Up to: <name>" instead, and a running count ("Files: 1,234…") replaces the spinner elsewhere.

**Destructive keys ask first, and recoverable is the default**: deleting a saved network connection, a branch, a stash, a holding, a package, or discarding a file's changes all go through a y/n prompt in the footer. The Delete dialog starts with *Move to Recycle bin* ticked where one exists (local files on Windows, `DeleteDialog.CanRecycle`) and disables it, saying the delete is permanent, everywhere else — the flag is ignored by the remote and memory drives. The theme chosen in the theme manager is saved in the `Theme` setting and restored by `TerminalScreen` before the first frame (`ThemePersistence`).

**File operations never act on the `..` row**: its URL is the parent folder, and that folder exists, so a check that only asked "does it exist" let F8 offer to delete the folder the user was standing in — with *Recursively delete folder* already ticked. F5, Shift+F6, F6 and F8 all decide through `Commands.FocusedEntry.ActionableUrl`, which refuses the `..` row and anything gone from disk. F5 copies folders too (it used to accept files only, though the transfer has always had a folder pipeline).

**The screen is repainted from scratch whenever its shape changes**: a buffer layer composites everything inside the rectangle it has *ever* been written to, and nothing used to clear it — so a dialog closed while anything else still drew on its Z-order stayed on screen, and the next dialog opened on top of its ghost. `Control.TreeVersion` moves on every `AddControl`/`RemoveControl` and every `IsVisible` change; `ControlRendererJob` sees it move, wipes every layer and refreshes the whole tree before the next merge (`RepaintFromScratch`), so the wiped layers are never seen. A control that changes the tree must go through those members, not `Controls.Add`/`Remove` directly.

**An open menu drop-down is lifted off layer 0**: every `MenuItem` sits on layer 0 so the bar is part of the screen, and a drop-down left there was painted over by the panels within a second — Ctrl+F gave the keyboard to a menu nobody could see. `MenuItem.OpenMenu` raises the opened item to one layer above whatever opened it; `CloseMenu` puts it back. And a menu's Ctrl+letter mnemonic gives way to a command bound to the same chord anywhere on screen (`MenuItem.HandleHotKeyEventAsync`): the Edit menu's Ctrl+E used to swallow the unit converter's own key. ←/→ still reach every menu once one is open. A drop-down opens under its own name in the bar (`MenuBar.GetDropDownColumn`, pulled left only to stay on screen), and its entries draw the label and, right-aligned in one column, the shortcut written after the tab in the label (`"Create File\tShift+F4"`) — never the command's bare `ConsoleKey` as well, which is what used to print "Create File	Shift+F4 F4".

**Validation results are stamped when the change happens, and only go forward**: `ValidationModel` validates on a background task. It used to stamp results with `IDateTimeProviderService.Now` — cached for half a second — while dialogs validate on opening with the real clock, so for up to half a second every keystroke's result was older than the opening one and thrown away; a name typed quickly and confirmed left the dialog "invalid" for good, Enter doing nothing. Stamps are now monotonic and taken on the change, and a command that acts on a result calls `EnsureCurrent()`, which validates on the spot when a change is still pending. An empty required field is invalid but says nothing — the button is disabled — and messages carry no `Error: ` of their own (the error line adds it).

**A suggestion list only opens for the box being typed in**: `AutoCompletion` works out its matches when it initialises, and used to put the list up with them — for a box nobody was typing in, on a tab page that was not even showing. `ShowPopupAsync` now requires its owner to have focus. A `Tab` also closes and hides *every* page, not just the one showing (`Tab.Controls` is the showing page's children, so the base implementations never reached the others): the folder selector's hidden Path page left its list, attached to the root, floating over the panels after the selector had closed.

**Text boxes take any printable character**: `ConsoleKeyHelper.TypeableCharacters` is an ASCII whitelist (letters, digits, six marks), and it used to be the whole rule — "Photos (2024)", "Tom's notes", an accented name or a URL with `?`/`&` could not be typed into any dialog. `ConsoleKeyHelper.IsTypeable` accepts any printable character, and `IsTypingKey` treats Ctrl+Alt *together* as typing, because that is how Windows reports AltGr — the only way to type `@`, `{` or `\` on most non-US layouts (Hungarian AltGr+V is `@`). Ctrl or Alt alone is still a chord.

**One failing key handler must not cost the keyboard**: `TerminalInputConsumerJob` is the only loop reading input, and an exception let out of a handler ended it (`Job.ExecuteAsync` swallows it) — the app went on drawing and ignored every key from then on. Each event's handler is contained (`DispatchAsync`). Commands already contain their own exceptions; this covers a control's `HandleKeyEventAsync`.

**The hot key bar shortens its labels for a reader, not proportionally**: when the full labels do not fit, `HotKeys.FitTitlesToBudget` cuts only the longest words, to one common length, keeping short words whole and the key part ("F2-", "Ctrl-F5-") always; below four letters a word reads as a typo, so it then leaves out the least important buttons instead (F12, F9, F11, F2, F4, then from the right, with F1-Help and F10-Quit last; never more than half) — the keys still work, they are just not advertised; only past that does it cut the remaining words further. It used to scale every button alike: `[F1-Hel][F2-Termi][F3-Vie]` at 100 columns. Each button's label names the key its command is bound to — `HotKeysTest.EveryButtonNamesTheKeyItsCommandIsBoundTo` holds them together, since the Ctrl layer used to advertise `Ctrl-C-Calc` (Ctrl+C quits) and the Alt layer `Alt-F6-Tasks` for the theme manager. `LayoutHotKeysRow` decides every button's visibility first and sets it once: showing a button and hiding it again in the same pass moved the tree version on every layout, each move repainted the screen from scratch, which laid the row out again — below ~100 columns the renderer never went idle, and nothing that waits for an idle pass ran (dialog lists stayed empty, progress windows open).

**An AI bar with no model behind it takes one row**: once the availability check has answered no (`AiPromptBar.IsCollapsed` — not while it is still checking), `Content` lays the bar out one row high and gives the rest to the panels, and the row says why and where to look (`AI  unavailable: server unreachable  —  Ctrl+F2: details, Ctrl+B: terminal bar`, the hints dropped first when it is narrow). It used to keep its five rows, four of them blank. `AiPromptBar.PreferredHeightChanged` is what makes `Content` re-lay out when the answer arrives.

**Input captions go through `TextBox.FormatLabelPrefix`**: an empty label draws no caption at all, a label already ending in `:` keeps its own colon, anything else gets `": "`. `ProgressBar` uses the same rule. Fields hosted in a `FormPanel` are built without a `Label` — the panel draws the captions, and highlights the one whose field has focus.

**Panel footers are shrunk by the control, not the model**: `ContentBrowser.Draw` calls `Shrink` on `GetFooter()` before handing it to `DrawBorder`. A footer that does not fit is not truncated by the border — `StringHelper.AlignCenter` only writes a title *shorter* than the line, so an over-long footer is dropped whole and the panel silently loses its counts and its key hints. `GetFooter()` has no width to work with; the control that draws it does.

**Restoring a panel's position**: `FilePanel` saves the cursor row, the first visible row *and the focused entry's URL* on close, and hands all three to `IContentModel.RestoreNavigation` at start-up. It cannot assign them: the folder is enumerated on a background task, so at that moment the listing is one `..` row and `Update()` clamps anything set against it to zero. `ContentModelBase` therefore holds the restore until a listing that can carry it arrives — at once for a drive that lists synchronously, on the completed listing for a cold folder (`FilePanelRefreshTask` passes `isComplete`, false for a streamed batch). The URL is what the cursor is really restored to; the index is the fallback for when that row is gone, because a folder is rarely the list it was when the app closed. Two refresh tasks can be replacing the same listing at once — the navigation enqueues one and the panel's start-up another — so `ApplyPendingNavigation` refuses a listing too short to hold the saved index rather than collapsing onto row zero, and `RememberFocusedEntry` does nothing while a restore is outstanding (the cursor is on `..` until it lands, and remembering that would overwrite the row being restored to).

**The cursor-restore state is guarded, and listings land through one method**: the pending restore, the remembered row and the cursor are written from the key handler *and* from the worker landing a listing. Unguarded, a listing landing while a restore was being applied remembered the cursor in the instant between the restore clearing its flag and moving the cursor — and put it back on `..` (the F7 "Enter on a hit" end-to-end test failed one run in six, on `main` too). `ContentModelBase` now takes `_navigationLock` in every restore method, and every producer of listings calls `ReplaceEntriesAndRestoreFocus(entries, isComplete)` instead of remembering, replacing and restoring itself. The key handler cannot take that lock (it would hold it across awaits), so the method checks instead whether the cursor moved while the listing was swapped and lets that move win — otherwise Down on a folder refreshing in the background snapped back to `..`. A restore asked for during a *streamed* batch waits for the complete listing rather than settling for its fallback index. And `ContentModelService.SetUrlAsync` never writes a remembered index into the cursor itself: written as `ScrollableSize.Height - 1` it was -1 on a momentarily empty listing, `Position`'s assertion threw (the test host turns a failed `Debug.Assert` into an exception), and the key handler died before Ctrl+PgUp asked to land on the folder left. It hands the index to `RestoreNavigation` like every other restore.

**Dialogs & feature services stay off the render thread**: `ShowDialogCommand<T>` calls `OnBeforeShow(dialog)` then `Control.ShowDialogAsync(dialog)`. External processes (git, `dotnet`, package managers, HTTP quote/AI calls) run only through their async `I*Service` — never inline in a key handler or during rendering, same 200 ms handler budget as navigation.

**A modal pop-up must be *removed*, not hidden**: `Desktop.GetModalChildControl` returns an `IsModal` control without asking whether it is visible, and the keyboard job routes every key to it. So a modal window that only clears `IsVisible` — which is all `PopUpWindow`'s stock `[X]`/`HideCommand` does — leaves the app looking frozen. `Dialog.Close` gets this right (`Parent?.RemoveControl(this)`); `ProgressWindow` overrides `Close` and its action button for the same reason.

**The keys belong to the *topmost* modal, which is the last one in the child list**: `Desktop.GetModalChildControl` and `Control.GetModalChildControl` scan children in reverse and look inside a control before taking it. Everything that overlays — a `Dialog`, a modal `Popup` — attaches itself to the **root** rather than to whoever opened it (`ShowDialogAsync` defaults its parent to `GetRootControl()`), so a dialog opened over a dialog is a *sibling* listed after it, and list order is also draw order. Read first-modal-wins, as it used to be, every key went to the overlay *underneath* the one on screen: F1 over the folder selector put the help on top but left Esc closing the selector behind it, stranding a help dialog with nothing to return to. A new overlay therefore needs nothing but to be attached last.

**F1 help lists what a key would do**: of several runnable commands one control binds to the same key, only the first takes it, so only that one is listed (the panel used to list Enter as both "Open folder" and "Open or run"). Keys are ordered plain, Shift, Ctrl, Alt, function keys by number.

**Esc belongs to the `Dialog`, but an open overlay gets one press first**: `Dialog.HandleKeyEventAsync` claims Esc *ahead of* its children, so no text box or list can swallow it and strand the user in a dialog they cannot dismiss. That rule alone left a suggestion list with no way of being dismissed at all — the first Esc took the whole dialog, and the path being typed, with it. `ITransientOverlayHost` (`IsOverlayOpen` / `CloseOverlay`, implemented by `AutoCompletion`) is the one declared exception: `ITransientOverlayHost.TryCloseInnermostOverlay` searches the dialog's subtree — children before the control holding them, in reverse, the same "deepest and last-attached wins" rule as `GetModalChildControl` — and closes one layer per press, from the dialog, not by handing the key to the control that owns the list. So Esc still cannot be swallowed, and it still always means "back out of one thing". A new floating sub-state needs nothing but to implement the interface.

**A `Popup` claims its open state before the first `await`, not after**: `Popup.ShowAsync` used to guard on `IsOpen`, which it only set once initialisation had finished, so two shows that overlap both got past the guard and both called `AddControl` — attaching the same overlay to the root twice. An autocompletion list does exactly this as a matter of course, from the keystroke that shows the owning text box and from the background match update that same keystroke triggers. Closing then detached one of the two entries and left an invisible orphan on the root for the rest of the run: one per dialog opened, each raising the root's maximum Z-order and so the number of buffer layers the renderer allocates. `AutoCompletion.Hide` closes its popup unconditionally for the same reason — an interrupted show has already attached it while `IsOpen` is still false.

**Dismissing a suggestion list has to beat the match update already in flight**: `AutoCompletion` matches on a background task — *two* per keystroke as a matter of course, one from the text-changed handler and one from the `ShowAsync` that same keystroke triggers — so a dismissal (Esc, a page switch, a completed Tab) regularly lands between a keystroke and the update it started. Read naively that update then calls `ApplyVisibility(true)` a few milliseconds later and puts the list the user just dismissed back on screen; as a test it is a coin-flip, as a bug it is a list that reappears on its own. `AutoCompletion.Hide` therefore moves a **generation** counter on, and an update only shows the list when its generation is still current. Cancelling the update instead does not work and is worse: the token is only checked *before* the work starts, so it cannot stop the update already past that point — the one that actually resurrects the list — while it does leave `CompletionModel.UpdateTask` cancelled under everything that awaits it. The next keystroke reads the new generation, so dismissing still costs nothing.

**A `Popup` that is closed mid-show must not finish opening**: `Popup.ShowAsync` attaches itself and *then* awaits `OnInitializeAsync`, so a `Close` landing in that window has already detached the overlay and released the show claim. Carrying on afterwards set `IsOpen = true` on a popup that is no longer on the screen — and `IsOpen` is what every later `Close` and every idempotence check reads, so it stayed that way for the rest of the run: closed to look at, open to ask, and impossible to reopen. `ShowAsync` re-checks the claim after the await and unwinds instead (detaching, and popping its focus entry if it pushed one). An autocompletion list overlaps the two constantly, being shown from a background match update and dismissed from a key handler.

**The copy/move/delete dialogs close on Enter; the progress window closes itself**: `TransferCommand`/`DeleteCommand` enqueue the task, show a `ProgressWindow` over it and close the dialog immediately — the operation is not awaited, and the panel is usable while it runs. The progress window then dismisses itself from `OnIdle`, not from the task's `PropertyChanged`: that event arrives on a `TaskManager` worker thread (removing a control there would race the renderer), and polling the status also catches the task that *finished before the window existed*, which a small local copy regularly does. A failed run stays on screen — see below.

**Only the local drive notices its own changes**: `ContentModelFileSystem` runs a `FileSystemWatcher` over the folder it is showing; the memory, SSH, SMB, iPhone and archive models have nothing watching them. So a finished copy/move/delete arranges its own panel refresh — `PanelRefreshHelper.RefreshWhenFinished`, armed by `TransferCommand`/`DeleteCommand` *before* the task is queued (a small local copy is regularly over before `TaskManager.Add` returns) and matching a panel by whether its URL is the parent of the source or target. It runs **inline on the worker that finished the task**: that is off the render thread and off the key handler, which is all a content model requires, and handing it to the thread pool instead is the one unreliable option here — `TaskManager`'s workers park forever in a blocking loop on pool threads, so a queued continuation can wait seconds. A copy does not refresh the source panel (`TransferCommand.RemovesSource`), since that folder did not change. `Refresh(forceRefresh: true)` is what re-reads rather than re-serves the cache — which is why `ContentModelRemoteDrive.Refresh` has to skip its `IMemoryCacheService` entry on a forced refresh instead of only clearing `Entries`.

**A failed task still reports `TaskStatus.Completed`**: the transfer/delete tasks catch their exception and describe it rather than letting it escape `ExecuteAsync`, so `Status` alone cannot tell a copy that worked from one that copied nothing. `BackgroundTask.Error` is that signal (also set when a folder operation finishes with a partial-failure list), and it is what keeps the progress window up long enough to read the message — the window is the only place it is shown.

**An input control acts on a key only when it has focus**: a key the focused control declines is offered to *every* control, so a control that reacts without checking `IsFocused` takes keys meant for something else. `ComboBox`, `NumericUpDown` and `RadioGroup` did exactly that — nothing in the app used them until the Compress dialog, where Enter in the archive box opened the format list instead of compressing. Check `IsFocused` (and `IsEnabled`) in any new control's `HandleKeyEventAsync`.

**`Key` constructor argument order**: `new Key(consoleKey, shift, alt, control)` — `alt` comes before `control`, which is *not* the order the properties are declared in. Getting this wrong silently binds the wrong chord.

**Choosing a global hot key**: two layers eat chords before a status-bar command ever sees them, which is why nearly every global feature here is on a function key.
1. *The focused file panel goes first.* `ContentBrowser.HandleKeyEventAsync` claims `Alt`+printable to start its type-to-search filter, so **no Alt+letter chord can be a global hot key**. F1–F12 are excluded from `IsFilterCharacter`, so function keys pass through.
2. *The terminal host goes before that.* Ctrl+M is ASCII CR (identical to Enter on a Linux TTY), and hosts commonly reserve Ctrl+M / Ctrl+Shift+M — VS Code binds both.

Set `ITERMINAL_KEY_TRACE=1` to log every key the app receives (chord, char, whether it was handled) to `%TEMP%/iTerminal/key-trace.log`. A missing line means the host swallowed the key; a line with `handled=False` means the binding did not match. Test a new hot key against a *real* focused `FilePanel` (see `MusicPanelsHotKeyWithFilePanelTest`) — a stand-in control does not reproduce layer 1. Better still, press it in `iTerminal.Test` (`DialogsTest` lists every dialog by its key): the iPhone browser was bound to Alt+I, advertised in the Tools menu, and passed a routing test built on a stand-in panel — and never once opened in the app. It is Alt+F11 now.

**A `Tab` offers a plain arrow to the focused control before it changes page**: `Tab.HandleKeyEventAsync` claims Left/Right (horizontal) or Up/Down (vertical) for the tab strip only when the focused control declines them; **Ctrl+arrow always belongs to the strip**, as does Ctrl and the number in a page's name. Taking the arrow unconditionally — which is what it used to do — meant a vertical tab swallowed Up/Down before the focused list ever saw them, so the list could not be scrolled at all, and a horizontal one did the same to Left/Right in a text box. The strip's own keys are surfaced through `GetKeyHints`, which is what puts them in F1 help.

**A `Tab` puts the cursor on the arriving page's first control, and takes the leaving page's overlay down**: both live in `Tab.SwitchToPage`, which every route to a page goes through — Ctrl+arrow, Ctrl+&lt;number&gt; (**including for the page already showing**, which is what makes it the keyboard's way back into the content), and a click on the strip. A `TabPage` cannot hold focus itself, so focusing it hands the cursor to the first *focusable* control inside, which is why a page's list belongs in front of its buttons; and the other pages have to be `ResetFocus`ed explicitly, because `Tab.Controls` returns only the focused page's children and a page no longer showing is not reachable from the root at all. The overlay half is the popup-attaches-to-the-root problem again: leaving a page does not hide a suggestion list opened on it, so `SwitchToPage` dismisses it through `ITransientOverlayHost` or it floats over the page that arrives next.

**A `Tab` routes keys to the focused *page*, not to `base.HandleKeyEventAsync`**: `Tab.Controls` is overridden to return the focused page's children — which is what makes a tab transparent to layout, rendering and focus, but also means a `TabPage` is not in any parent's child list. So the base implementation walks straight past the page into its list boxes and buttons, and **a `TabPage` that overrides `HandleKeyEventAsync` is never called**. That is the only reason to override it (to claim a key ahead of one's own children), and it is what `FolderSelectorTabPage` does with Enter: read through the base, Enter on a folder row reached `ListBox`'s own `SelectListItemCommand`, which ticks the row's selection flag and reports the key handled — so choosing a folder neither navigated nor closed the dialog, while the same page driven directly in a unit test did both. `Tab.HandleKeyEventAsync` therefore hands the key to `FocusedPage` and keeps only its own Ctrl+&lt;number&gt; jump, in the position it had. A page's children, hot key and commands are all still reached — through the page. **A test that drives a tab page directly proves nothing about the app**; go through the dialog (`FolderSelectorSelectionTest`).

**The tab strip is painted, not built from controls, so it needs its own mouse handling**: `Tab.Draw` writes the page names itself — there is no control under the pointer for `Control.HandleMouseEventAsync` to route a click to, and the base implementation offers the click to the *current* page's children, which do not cover that part of the screen, so clicking a page name did nothing at all. `Tab.HandleMouseEventAsync` maps the click back to a page with `GetTabStripPageAt`, whose arithmetic mirrors `DrawVertical`/`DrawHorizontal` (vertical: a top border, then a name row and a rule per page, the strip as wide as the longest name + 6 — the same figure `OnInitializeLayout` starts the pages after; horizontal: one row of names, each the name + 4). **Change the drawing and that method together.** A click switches page through `SwitchToPage`, which focuses the page — and since a `TabPage` cannot hold focus itself, focus goes on to the first control inside it. So clicking a name puts the cursor in the panel on the right, and clicking the page already showing is the way back into its content.

**Drive-specific panel commands**: `ContentBrowser.OnInitializeCommands` attaches the same command set to both panels, and `Control.HandleKeyEventAsync` offers a key to the focused control first but then to *every* control. A command that only applies to one drive must therefore gate on `ContentModelService.GetFocusedModel()` **being reference-equal to its own model** — not on its own model's type. Gating on type alone lets the unfocused panel act on a key the focused one declined; `MusicPanelCommand` is the worked example, and `CopyDialogCommand` gates the same way. `Command.RunAsync` returns false when `CanExecute` is false, so several commands can share a key and the applicable one wins by order.

**`IStopwatchFactory` / `PhaseDurations`**: `FilePanelRefreshTask` accepts an optional `IStopwatchFactory`. When injected, it populates `PhaseDurations` (`"CacheLookup"`, `"Enumeration"`, `"UiUpdate"`) after execution. Use `RecordingStopwatchFactory` (in `iConsole.Test.Core`) for timing assertions in tests; production passes `null`.

## Code style

Follows the root `.editorconfig` and `.github/copilot-instructions.md`:

- 4 spaces, CRLF, braces on new lines, accessibility modifiers on non-interface members.
- Prefer explicit types over `var` unless the type is obvious from the right-hand side.
- File-scoped namespaces; primary constructors for small command/service classes; top-level statements in `Program.cs`.
- Constructor injection over ad-hoc construction; keep reusable primitives in `iConsole` and app behavior in `iTerminal.Core`.
- Logging in `iTerminal.Core` goes through `Serilog.ILogger`.
- Async-first: don't convert an existing async flow to a blocking call.

## Testing conventions

- Framework: MSTest (`[TestClass]`, `[TestMethod]`), Moq for fakes. Test projects (`iConsole.Test`, `iTerminal.Core.Test`, `iConsole.Inputs.Windows.Test`) mirror the source folder layout — put a new test in the folder matching the type under test.
- Shared test helpers live in `iConsole.Test.Core` (e.g., `MockBuffer`, `RecordingStopwatchFactory`).
- **Assert on what a control drew with `ScreenBuffer`, not `MockBuffer`.** `MockBuffer` keeps text only, and a control's visual state (focused, disabled, read-only, invalid, the cursor row) lives in the colours. `ScreenBuffer` keeps each cell's character, colours and style flags per Z-order layer, and has `AssertLines`, `AssertColors`, `CellOf` and `AssertFillsBounds`; `TestThemeService` serves the stock `ColorScheme`, whose state colours are all distinct. Draw twice into one `ScreenBuffer` to catch a control that leaves stale text behind. The `*RenderTest` files in `iConsole.Test/Controls/` are the worked examples.
- `SettingsService()` (no-arg) creates a temporary SQLite DB — use it in tests instead of mocking.
- `IFrequentExecutionGuardService` is commonly mocked to execute actions immediately: `.Setup(g => g.Execute(It.IsAny<Action>())).Callback<Action>(a => a())`.
- Integration tests in `FilePanelIntegrationTest` wire the full stack via `AppHarness` (real `TaskManager`, `ContentModelService`, `FilePanelFactory`). Use `WaitForEntryAsync` (polling with deadline) to observe async results.
- `Generated/InstantiateAllTypesTest` reflects over every exported non-abstract type in the `iConsole*`/`iTerminal*` assemblies and asserts it can be constructed. A new public type with a constructor the resolver can't satisfy fails this test — give it a resolvable constructor rather than weakening the test.
- Dialog and panel tests use `Helper/UiTestHelper` (`iTerminal.Core.Test`): `ShowAsync` attaches the dialog to a 120×40 root as the app does, `Render` draws the whole control tree into a `ScreenBuffer`, `WaitUntilAsync` polls background work with a deadline. Fakes that background tasks write to must lock their recorded calls.
- Both big test assemblies raise the thread-pool floor in `TestAssemblySetup` (`[AssemblyInitialize]`). `dotnet test iTerminal.slnx` runs the projects side by side, and MSTest runs every `[Timeout]` test on a pool thread — without the floor, trivial tests missed 2-second timeouts before their body started. `[Timeout]` values are hang guards; keep them generous and put real timing assertions on `PhaseDurations`.
- Performance budgets: key handler < 200 ms, content load < 3 000 ms. Timing tests use `FilePanelRefreshTask.PhaseDurations` rather than external `Stopwatch` polling.
- Fixture files for manual/file-type testing live in `Test/FileTypes/` (archives, scripts, PDF, binaries).
- **Driving a whole console app: `iConsole.Test.Core/Automation`.** `ConsoleAppDriver.StartAsync<TScreen>(configureServices, options)` runs any iConsole application in-process — generic host, `Desktop`, every registered job, the real input routing and both render jobs including the diffing `ConsoleBufferRendererJob` — with only the two ends virtual: `VirtualConsoleDriver` (an in-memory terminal; `Snapshot()` is what the renderer actually wrote, colours included) and `VirtualTerminalInput` (a keyboard and mouse whose sends complete when the handler has run, through the production `TerminalInputConsumerJob`). Press keys with readable chords (`KeyChord`: `"F5"`, `"Ctrl+G"`, `"Shift+Tab"`, `"Alt+r"`, `"Ctrl+Alt+Shift+F1"`, the keypad's `"NumPlus"`/`"NumMinus"`/`"NumStar"`; a bare capital is Shift, a chord's letter is not), `TypeAsync`, `ClickAsync("OK")`, `ResizeAsync(w, h)`; assert with `WaitForTextAsync` / `WaitUntilAsync` / `WaitForModalAsync<T>` — rendering is asynchronous, so never read the screen right after a key. A failed wait throws with `ConsoleSnapshot.Dump()` of the screen, which is also the fastest way to see what a screen really looks like. `iConsole.Test/Automation` tests the driver against a small sample app.
- **The end-to-end suite: `iTerminal.Test`.** `TerminalApp.StartAsync()` boots the real `AddiTerminal` composition on the driver inside a sandbox: a fresh data folder (every test is a first run), two panel folders with known contents (`LeftRoot`: `alpha/`, `beta/`, `notes.md`, `readme.txt`; `RightRoot`: `target/`, `right_only.txt`), empty music and documents folders. Only the weather and quote pollers (internet) and `FolderIndexJob` (walks every drive) are left out, and the services that reach outside the machine are `SandboxServices` fakes — the network scan (one host, SSH and an SMB share), the package manager, the quote provider and the docker CLI (`DockerCli`: one container, `web`, holding `/etc/motd`, under the real `DockerDriveService`) — so no test probes the network, runs WinGet or lists the machine's containers, and the dialogs on them are driven like any other (`OutsideWorldDialogsTest`). git is the real git: `SearchPreviewAndDrivesTest` seeds a repository into the left folder. Unit tests fake a tool's output with `Helper/FakeProcessRunner` (`iTerminal.Core.Test`), which answers by command-line prefix and records stdin. `RestartAsync()` relaunches on the same sandbox, for what a session keeps. Helpers read the screen as a user does (`LeftPanelLists`, `AssertNoStrayFrames`, `SelectEntryAsync`). The assembly is `[DoNotParallelize]`: each test is a whole app whose render threads run at the highest thread priority, and two at once starve each other into timing failures. (Apps no longer share state otherwise — `Control.FocusedStack`, where dialogs remember who had focus, is one per root; it used to be a single static stack, and a dialog closing in one app or test could hand focus to a control in another.) **A test that drives a dialog directly cannot see what this suite caught** — dialogs left painted after closing, a menu drawn under the panels, a suggestion list orphaned on the root, Alt+I eaten by the panel's search — because each of those lives between controls, in the renderer or the key routing.
