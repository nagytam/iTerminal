### Runtime dependencies (`Services/RuntimeDependencies/`, `RuntimeDependencyDialog`)
Components the app needs at run time but does not ship are downloaded into the data folder (`%APPDATA%/iTerminal/runtimes`) by a setup dialog, not packaged. Today that is Playwright — the .NET library is shipped, but its driver (a Node.js runtime and Playwright's JavaScript package, ~130 MB) and the Chromium it drives are not — and Ollama, the local model server the AI bar talks to (see the last bullets of this section). PowerShell 7 (`PowerShellRuntimeDependency`, about 70–115 MB per platform) is downloaded the same way, for the remote PowerShell sessions and Ctrl+O on Windows (see the PowerShell bullet below).

- **The shipped build must not carry the driver.** `Microsoft.Playwright` is referenced with `ExcludeAssets="build;buildTransitive"`: its build targets are what copy `.playwright` into the output, and the Windows installer and the Linux packages both pack whatever was published. Remove that attribute and every package grows by the driver again.
- **`PlaywrightRuntimeDependency` installs the driver from the NuGet package for the version the build was compiled against** (`Microsoft.Playwright` `<v>.nupkg`, `.playwright/package` and this machine's Node only), then runs the driver's own `install chromium`. The package is checked against the SHA-512 its NuGet catalog entry records before anything is unpacked, and a mismatch is deleted. The library finds the driver through `PLAYWRIGHT_DRIVER_SEARCH_PATH` and the browsers through `PLAYWRIGHT_BROWSERS_PATH`, both set by `Activate()` — nothing has to sit next to the executable. The nupkg is ~210 MB because it carries Node for every platform.
- **An update stays on the build's line** (same major.minor). Playwright's protocol is tied to its library, so a newer line is reported as a note ("1.64.0 is out, but this build uses 1.63.0") rather than installed; adopting it is a rebuild.
- **`OllamaRuntimeDependency` is the same contract for Ollama, from GitHub releases**: versions come from `ollama/ollama` (stable tags only, the same `major.minor` line rule as Playwright), and the program is the asset of this platform (`ollama-linux-amd64.tar.zst`, `ollama-windows-amd64.zip`, `ollama-darwin.tgz`). The download is checked against the `sha256` digest GitHub records for the asset, and an asset without one is refused. Linux ships zstd only, so `ZstdSharp.Port` decodes it (.NET has no zstd in its BCL). Extraction refuses entries that would land outside the folder, and keeps symlinks only when their target stays inside too. A version counts as installed only with the configured model downloaded into it (`model.installed` holds the name); installing pulls the model through `/api/pull` on a server started for the purpose.
- **`WhisperRuntimeDependency` is the offline speech model for voice input in the AI bar** (see `key-patterns.md`). The engine (whisper.cpp through `Whisper.net` + `Whisper.net.Runtime`, MIT, about 2 MB of CPU natives per platform) is shipped, so — unlike the Playwright driver — those packages have no `ExcludeAssets`; only the 148 MB `ggml-base.bin` is downloaded, to `<runtimes>/whisper/<pack version>/`. The URL is pinned to a commit of `ggerganov/whisper.cpp` on Hugging Face (never `main`) and the file is accepted only with the pinned size and SHA-256 (`VerifiedDownload`: `.partial`, check, rename; a mismatch deletes it). The version is that of the model *pack* ("1.0.0"): nothing is published to look up (`ListVersionsAsync` is empty, as for git), so another model later means a new pack version in code — a new folder and a bumped major, which an install of the old pack does not satisfy. It counts as installed when the file has the pinned size (hashing 148 MB must not run where `InstalledVersion` is asked from). **It is offered at start-up like Ollama**, until it is installed or skipped (S stores the skipped version). The pinned URL, size and hash were verified once by a real download when this was added; change them only together with that check.
- **`OllamaServer` never takes over a server that is already there**: `EnsureRunningAsync` returns at once when the configured address answers (a system Ollama is used as it is), starts `ollama serve` from the data folder only when nothing answers and the address is this computer, and stops only the process it started. `OllamaServerJob` keeps that server up while the app runs and re-checks the AI bar (`CheckAvailabilityAsync`) whenever reachability changes, because the bar checks once when it starts. Only registered when `AI:Provider` is `Ollama`; the end-to-end suite omits the job and replaces the dependency service.
- **An Ollama that was there before iTerminal counts as installed** (`IRuntimeDependency.IsExistingInstall` / `ExistingInstallNote`, default no). `OllamaRuntimeDependency` looks for a running server (`OllamaServer.GetInfoAsync`: version and models, asked during the *check*, never from `InstalledVersion`, which runs on the render thread) and for an `ollama` program on the PATH and the usual per-OS folders (never one inside the data folder). It is complete once the configured model is in it (the server holds it, or `model.installed` says it was pulled). Such an install is never offered an update, is started by `OllamaServerJob` with its own models folder (`ModelsDirectoryFor` returns null, so `OLLAMA_MODELS` is not set), and installing only pulls the model. Tests pass the search folders explicitly (`null` looks nowhere) so a machine with Ollama on it cannot change the result.
- **`GitRuntimeDependency` is installed by the system's package manager, not downloaded into the data folder.** git is found on the PATH (then the standard install folders, which `Activate()` adds to the process PATH — the Windows installer only updates the machine one), and a git that is there counts as an existing install (never offered an update; the system updates it). When missing, `GitInstallPlan.For` picks the first manager present: winget (`Git.Git`, elevates itself), Homebrew, then apt-get / dnf / zypper / pacman / apk. A non-root Linux user goes through `sudo -n`: a password prompt has no terminal to appear on, so a failure says the exact `sudo …` command to run by hand. The version is read with one short `git --version` per program found (cached by path and write time) — `InstalledVersion` is first called when the service is built, not on a key handler. `ListVersionsAsync` is empty: the package manager installs whatever it offers.
- **`FfmpegRuntimeDependency` is the same contract for `ffmpeg` and `ffprobe`**, which the F3 video and image viewers and the FLAC/Ogg/Opus/M4A audio decoders run. It installs through the system's package manager by way of `SystemPackageInstallPlan` (the generic form of `GitInstallPlan`, with one package name per manager): winget `Gyan.FFmpeg`, Homebrew `ffmpeg`, then apt-get / zypper / pacman / apk `ffmpeg` and dnf `ffmpeg-free` (Fedora's own repositories; the full build needs RPM Fusion). Both programs ship in one package but are separate files, so it counts as installed only when **both** are found (PATH, then the winget link and package folders on Windows, `/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin` elsewhere); any that is there already is an existing install, never offered an update. Any 4.x or later is compatible, and a development build (`N-…`, no number) reads as a very high version rather than as missing. `FfmpegAudioDecoder` and `FfmpegVideoDecoderFactory` probe for the programs **once per process**, so `Activate()`/`Invalidate()` reset those answers — without that the viewers keep saying "needs ffmpeg" until restart after a successful install. The viewers' message points at Tools > Runtime Dependencies.
- **`YtDlpRuntimeDependency` is the same contract for `yt-dlp`**, which the YouTube dialog uses for search and to find the stream it plays (`Services/YouTube/`). It installs through `SystemPackageInstallPlan` (winget `yt-dlp.yt-dlp`, then Homebrew, apt-get, dnf, zypper, pacman and apk `yt-dlp`). The version is the first line of `yt-dlp --version` and is cached by path and write time. The compatibility line is the **year** (`IsCompatible` accepts 2025 and later): YouTube changes often, so a dated yt-dlp is the usual cause of a failing search, and a newer year is never offered as a downgrade. Because it is a registered dependency, a machine without yt-dlp is **offered it at start-up** like a missing ffmpeg, until it is installed or skipped for that version.
- **The runtime-dependency dialog is shown only when something is missing or can be updated.** At start-up it opens when `ShouldOfferAtStartup` is true (a dependency is missing or newer, and not skipped). From Tools, `RuntimeDependencyDialogCommand.CanExecute` is true only while `RuntimeDependencyDialog.HasWork` is, so the command is unavailable when everything is up to date. When shown, the dialog is a wizard (unless an install is already running) with one `Wizard` step per dependency that needs work (installed, up-to-date ones get no page and are not listed anywhere in the dialog) in list order, so the first page is the first dependency that needs work (`RuntimeDependencyStepPage`: name, state, note, and a tick that starts on), then a last "Install" summary step (`RuntimeDependencySummaryPage`; it refuses to finish with nothing ticked). The overview page (`RuntimeDependencyOverviewPage`) is shown only when nothing needs work (or none is registered), and says so; Enter closes it. The plain list shown while an install runs (`Rows`) lists the same dependencies. The wizard's header ("Step 2 of 3: Ollama") and `StepIndicator` show how many steps there are. Enter/→ next, Backspace/← back, Space ticks the step's dependency (ignored on an up-to-date one), P skips it for good (`SetPermanentlySkipped`, persisted in `RuntimeDependencies.Permanent.<id>`; P again offers it), S skips the ticked versions. A dependency skipped for good keeps its page and is listed at every start (`ShouldOfferAtStartup` stays true for it), but it starts unticked, so Enter leaves it out; Space still installs it once. The last step never refuses to finish: with nothing ticked Finish just closes. Finish calls `IRuntimeDependencyService.StartInstall(ids)` / `SkipOffers(ids)`, or the parameterless calls when every one is ticked, and the dialog then shows the plain list with the install log; with nothing to install Finish just closes.
- **`RuntimeDependencyService` owns the list**: `Statuses` is an immutable snapshot replaced whole, and the first one is built on a background task (the probes start `git`, `ffmpeg` and `ollama` and walk the PATH, seconds that would otherwise sit on the start-up path): `Activate()` stays synchronous in the constructor because it sets the PATH, and every read waits for the first build, so a read in the first seconds may block that long (the start-up dialog opens after the splash, 5 s in) and must not come from a key handler — a build that started later is never replaced by an earlier one that finished last, and a probe that throws leaves the list empty. The install log is capped, and one install runs at a time (`StartInstall`). Settings keep the newest version seen (`RuntimeDependencies.Latest.<id>`, so the start-up offer needs no network), the skipped version (`…Skipped.<id>`) and the announced one (`…Announced.<id>`).
- **Start-up** (`TerminalScreen.OnInitializeAsync`) opens the dialog when something is missing or newer and not skipped for that exact version, or skipped for good (which the dialog lists every time, unticked). `RuntimeDependencyCheckJob` checks the publisher 30 s after start and every 12 h, and announces a new version once by notification; the offer at the next start and Tools > Runtime Dependencies show it until it is installed or skipped.
- **`OnlineQuoteJob` waits** while Playwright is not installed, and a failed launch calls `InvalidateInstalled` so the dialog offers Chromium again. It no longer runs `pwsh playwright.ps1`.
- The end-to-end suite replaces the service with `SandboxServices.Dependencies` (nothing to install, no offer) and omits the check job, so no run downloads anything or opens the offer over the panels.

- **`PowerShellRuntimeDependency` is PowerShell 7 from its GitHub release (`PowerShell/PowerShell`), zip on Windows and tar.gz elsewhere.** The newest stable 7.x is the target (`IsCompatible` is the major version 7; `Built` is 7.7.0). The archive is unpacked into `<version>.staging`, its `pwsh` is run once to read `$PSVersionTable` *before* the folder is moved into place, and a program that does not report the version is deleted and the install fails with the ICU hint (Linux's usual cause). A `pwsh` on the system (PATH, or `C:\Program Files\PowerShell\7` and the usual Unix folders) is an existing install: used as it is, never downloaded over, its version read once by a short process and cached by path and write time. `Activate()` (the constructor, and after each install) puts a folder first on the process PATH — the system one when it is off the PATH, else the newest download — with file lookups only, never the version process. The `.pkg` and `.msi` installers are not used. Ctrl+O reads the PATH only on Windows; elsewhere it still uses `$SHELL`, so the download serves the remote PowerShell sessions there.
- **`RarRuntimeDependency` and `UnrarRuntimeDependency` are system tools for RAR archives** (`SystemToolRuntimeDependency`, the same contract as ffmpeg). `rar` writes RAR archives (the Compress dialog and the AI tool) and `unrar` reads them when 7-Zip is not installed. Both are installed through the package manager (winget `RARLab.WinRAR` on Windows, which keeps `Rar.exe` and `UnRAR.exe` in `%ProgramFiles%\WinRAR`, off the PATH and looked for there; Homebrew, apt, dnf, zypper, pacman and apk `rar` / `unrar`) and are never bundled: RARLAB's compressor is not free software. The version is the banner `rar` or `unrar` prints with no arguments. Passwords go to them on stdin, never on the command line.

### Self-update (`Services/Updates/`, `UpdateDialog`, `UpdateCheckJob`)
iTerminal checks its own GitHub repository (`nagytam/iTerminal`) for a stable release newer than the running build, using the same `GitHubReleaseFeed` as Ollama. The compare is over the whole version, so release builds numbered `0.0.0.<run>` order correctly (the dependencies' `ToString(3)` would drop the build number).

- **`UpdateCheckJob` checks 30 s after start (its start mode defaults to Delayed, not on demand, so an update is offered without opening About) and every 12 h.** The first finding opens `UpdateDialog` on the first screen (resolved on demand, like `ErrorPromptService`, to stay out of the desktop's construction graph); later ones only post a notification. A release is announced once per run, and S in the dialog stores it in `Updates.Skipped` so it is not offered again until a newer one appears. A check that fails (offline, rate limited) offers nothing and says nothing.
- **Windows installs; a Linux package (deb, rpm, or the non-portable tar.gz) gets a toast naming the release and its address, no dialog.** Linux portable copies take the dialog as well (see below). The Install updates button downloads the release's `.msi`, checks it against the `sha256` digest GitHub records (an asset without one is refused, as for every download here), **checks its own Authenticode signature** (`WinVerifyTrust` through `IAuthenticodeVerifier`, whole-chain revocation, no UI), starts `msiexec /i … /passive /norestart` and then cancels the desktop so the installer can replace the running files. The digest comes from GitHub, so the signature is what ties the file to the publisher even if that account is compromised. A valid signature is logged with its signer; an unsigned MSI is a warning and still runs, because release signing is not configured yet; a signature that does not match, an untrusted or revoked chain, or a check that could not be made stops the install and deletes the download. The verifier is faked in the update tests. The MSI is per-machine, so Windows asks for administrator rights itself; its `MajorUpgrade` replaces the old install. A release without an `.msi` asset is reported in the dialog.
- **Portable copies update from the portable archive, on Windows and on Linux.** A copy with `iTerminal.portable` beside the program (`UpdateService.PortableMarker`; only the portable archive contains it) is a *portable* install on either system (`UpdateService.KindFor`, `IsPortable`), and its update downloads `iTerminal-<v>-x64-portable.zip` on Windows, or `iTerminal-<v>-linux-x64-portable.tar.gz` / `…-linux-arm64-portable.tar.gz` on Linux (`PortableSuffixFor`, by architecture) instead of the MSI. The Linux archive wraps its files in one folder, which is found by its marker; its tar entries are unpacked with the same no-escape rule, links are refused, and the executable bit is kept. The archive is checked by its SHA-256 digest only (Linux releases are not Authenticode-signed). `apply-update.sh` waits for the process to exit, runs `cp -a` from the unpacked folder into the install folder, and deletes the staging files and itself. It does not restart iTerminal (a terminal program has no window for a script to reopen it in), so the dialog says to start it again. The zip is digest-checked, unpacked into `staging` beside the download (an entry that would land outside that folder stops the unpacking; a zip without the marker and `iTerminal.exe` is refused), and the `iTerminal.exe` in it is checked with the same Authenticode policy as the MSI. `apply-update.cmd` then waits for this process's PID to exit, runs `robocopy /E` from `staging` into the install folder (copies only, so the person's own files there stay), starts `iTerminal.exe` from there, and deletes the staging folder, the zip and itself. A failed `robocopy` (for example a Program Files folder without administrator rights) keeps `staging` and starts the copy that is there. An install folder with a `%` in its path is refused: the batch file would read it as a variable.
- **About shows the release type**: "Package" (the MSI or a Linux package) or "Portable" (the marker is beside the program), the `About.Release` row, from `AboutDialog.ReleaseType`.
- **The release publishes the MSI, the portable archives (Windows zip, Linux x64 and arm64 tar.gz) and the packages.** `release.yml` builds the Windows ones (the archive is a self-contained `dotnet publish` with the marker added, zipped by `ZipFile.CreateFromDirectory`) and attaches them to the GitHub Release tagged `v<version>` on merge. An update is offered once a release carries the asset for the install's kind.
- The end-to-end suite omits `UpdateCheckJob`, so no run reaches GitHub or opens the offer over the panels.
