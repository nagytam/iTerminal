### `iTerminal` — composition root
`Program.cs` (top-level statements) wires DI via `AddiConsoleCore()` and `AddiTerminal()`; `AddiTerminal()` also calls `AddFileFormats()` (`iConsole.Formats`), which registers the file-to-text converter and the format services that iConsole only knows by interface. New services and controls should be registered in `iConsoleApplicationBuilderExtension` or `iTerminalApplicationBuilderExtension`, not in `Program.cs`. `Program.cs` reads its switches once through `LaunchOptions` (`iTerminal.Core/Application`, System.CommandLine): `--help`, `-h` and `-?` print the introduction and the switches and exit before any service is built; `--update` runs `UpdateCommandLine` after the services are built and before the interface starts, then exits with its code (`--wait-for-parent` is hidden and used by the elevation relaunch). An unknown switch (a token starting with `-` that matches no option, such as `--udpate`) does not stop the start: `Program.cs` writes a warning line to standard error and the interface still starts. Words that are not switches are ignored. The elevation relaunch drops its old `--wait-for-parent` value before it adds the new pair. `iConsoleApplication.CreateBuilder(args)` does not read `args`; only `LaunchOptions` does. `appSettings.json` holds the `FeatureManagement` flags and the `AI` section (`Provider` — `None` (no AI, Ollama is never offered), `Ollama` (the default; the server is downloaded when the start-up offer is accepted) or `OpenAI` for an OpenAI-compatible API — the model id, base URL, `DisableThinking`, prompt-bar height).

### `iTerminal.Installer` — the Windows installer
A WiX Toolset 5 project (`WixToolset.Sdk` from NuGet — nothing to install on the build machine) that produces `bin/Release/iTerminal-<version>-x64.msi`: the app in `Program Files\iTerminal`, a Start menu shortcut, the install folder on the machine PATH (a feature, on by default), an entry in Apps & features, and in-place upgrade.

- **Building it publishes the app** (`PublishApp` in the `.wixproj`): `dotnet publish ../iTerminal -c Release -r win-x64 --self-contained` into `obj/publish`, emptied first. The MSI therefore needs no .NET runtime on the target machine, and always holds the app as it is in the checkout. It is a separate `dotnet publish` rather than an MSBuild task call so the runtime identifier does not leak into the installer project's own evaluation.
- **`Package.wxs` packs whatever was published** (`<Files Include="…**">`), minus `*.pdb` and `*.log`: listing files by name would have to be kept in step with every package the app references. Only `iTerminal.exe` is authored by hand, because the shortcut points at it. A file added to the app's output needs nothing here.
- **Off Windows it is skipped, not failed.** The WiX SDK is imported only when `IsOSPlatform('Windows')`; elsewhere the project has just a `Build` and a `VSTest` target that print a skip message. So `dotnet build iTerminal.slnx` and `dotnet test iTerminal.slnx` succeed on Linux (and the same project is built for real on Windows, where a solution build also publishes and compresses ~240 MB each time).
- **`UpgradeCode` in `Package.wxs` must never change** — it is what lets a newer MSI find and replace an older install (`MajorUpgrade`). The version comes from `-p:Version=`, default `1.0.0`, and is also stamped on the published `iTerminal.exe`; Windows Installer only compares the first three parts.
- **The shortcut starts in Documents, not in the install folder**: the app writes `iTerminal.log` into its working directory (`Logger` — a relative path), and `Program Files` is not the user's to write to. Started from a shell, the log still lands in whatever folder the shell is in; moving it under the data directory is an app change, not an installer one.
- **The wizard has no licence page** — the page is skipped by two `Publish` elements, although the repository has a `LICENSE` file (MIT) that could be shown. Add a `License.rtf` and remove them to bring it back.
- **Starting the app after the install**: the last wizard page has a "Start iTerminal now" checkbox, ticked by default (`WIXUI_EXITDIALOGOPTIONALCHECKBOX = 1`); Finish runs `WixShellExec` on the Start menu shortcut, as the user who ran the installer. A silent install never shows that page, so `msiexec /i <msi> /qn LAUNCHAFTERINSTALL=1` starts the app after `InstallFinalize` instead. That one is off unless passed, because silent installs usually come from a deployment tool running as SYSTEM, where an interactive terminal app would only leave a stray process. A failed launch never fails the install. To check the wiring without installing, read the `Property`, `CustomAction`, `ControlEvent` and `InstallExecuteSequence` tables of the MSI (Orca, or the `WindowsInstaller.Installer` COM object).
- **Not signed, and no icon**: Windows SmartScreen will warn on an unsigned MSI. Signing needs a certificate (`signtool` after the build).
- **WinGet manifests** are in `iTerminal.Packaging.WinGet/manifests/`, laid out as the `microsoft/winget-pkgs` repository lays them out (`manifests/t/TamasNagy/iTerminal/<version>/`), in schema v1.28.0 (the version `microsoft/winget-pkgs` asks for in its pull request template; `winget validate` of the current client accepts it): a version, an installer and a default-locale file. The folder is not a project and is not in the solution. Each release needs a new version folder, because the installer manifest's `InstallerSha256` and `ProductCode` belong to one MSI: WiX writes a new `ProductCode` in every build, while the `UpgradeCode` stays fixed. The files are checked against the schema on Linux; `winget validate` and a test install (`winget install --manifest <folder>`, with `winget settings --enable LocalManifestFiles` in an elevated shell) passed for every version submitted so far (the first submission is the pull request microsoft/winget-pkgs#485881; the author signs the Microsoft CLA once, by commenting on it) and must pass again for each new version before anything is submitted to `microsoft/winget-pkgs`. The installer manifest has no `ElevationRequirement`: for an MSI WinGet would start the file with the `runas` verb, which `Msi.Package` does not have, and the install fails with "no app associated"; `msiexec` raises its own UAC prompt. `UpgradeCode` belongs only inside `AppsAndFeaturesEntries`. A local manifest is not attached to a source, so `winget list --id` does not find it; uninstall with `--product-code`. Nothing creates or updates them on a release. The `Publish to WinGet` workflow (`.github/workflows/winget.yml`) runs only when started by hand (Actions tab, or `gh workflow run winget.yml -f version=0.0.0.728`): for a published release it runs `wingetcreate update` against the release's MSI, validates the result, attaches the manifests to the run, and with `submit` ticked opens the pull request on `microsoft/winget-pkgs` using the `WINGET_PAT` secret (a `public_repo` token of an account that forks `winget-pkgs`). It can only update a package that already exists there, so the first version is submitted by hand with `wingetcreate new`; the manifests in this folder are the starting point for that. Do not publish every build: releases appear every few minutes, and `winget-pkgs` maintainers expect only releases you want users to get.
- **Update paths by install variant:** an MSI copy updates by running its `.msi` (msiexec), a portable copy by its archive script, and a Linux package is only announced. A WinGet install is an MSI too, but its manifest passes `MANAGEDBYWINGET=1`, which writes `HKLM\Software\iTerminal\ManagedBy = WinGet`; the app then does not install a release itself and says to run `winget upgrade TamasNagy.iTerminal` (`UpdateInstallKind.PackageManager`). Nothing forces an install: the dialog's Install button and `--update` are the only triggers, and background checks only announce.
- Most of the size is the .NET runtime. The Playwright driver is not in the package: the app downloads it on first start (see *Runtime dependencies*).
- **To check an MSI without installing it**, extract it: `msiexec /a <msi> /qn TARGETDIR=<short path>` — a short path, since Windows Installer refuses paths over 260 characters and the Playwright files are deep. The ICE60 warnings in the build are about four font-like files without a language and are harmless.

### GitHub Releases are immutable
Immutable releases are switched on for the repository (Settings, General), from release 0.0.0.736 on: a published release's assets and tag can never be changed or deleted, so the `InstallerSha256` in a WinGet manifest stays true for good. The setting does not reach back to earlier releases. It also decides how `release.yml` publishes: `gh release create --draft` with every file, then `gh release edit --draft=false`, because files cannot be added to a release once it is published. A release that was published wrongly cannot be fixed; ship the next version instead.

### The portable archives (`release.yml`, not a project)
`iTerminal-<v>-x64-portable.zip` is the app without setup: the same self-contained `dotnet publish -r win-x64` as the MSI, into a `portable` folder, plus an empty `iTerminal.portable` marker, zipped with `ZipFile.CreateFromDirectory` (forward slashes, no wrapping folder) into `iTerminal.Installer/bin/Release` so the Windows job uploads it with the MSI. The marker is what makes a copy portable: the app reads it to pick the archive for its updates and to show "Portable" in About (see *Runtime dependencies*, Self-update). It is added after the publish and never by the project, so an ordinary build is never portable.
The Linux archives, `iTerminal-<v>-linux-x64-portable.tar.gz` and `…-linux-arm64-portable.tar.gz`, are the same thing for Linux: a self-contained `dotnet publish -r linux-x64|linux-arm64` into a folder named after the archive, the marker added, then `tar -czf`. They sit beside the packages in the Linux job. Unlike the packages they install nothing, so the folder can be unpacked anywhere and started with `./iTerminal`. A portable Linux copy updates itself from the newer tar.gz of its architecture (see *Runtime dependencies*, Self-update); the marker also changes the About row to "Portable".

### Third-party licences in the packages
Every installable form carries `THIRD-PARTY-NOTICES.txt` and `LICENSE.txt` beside the executable: `Program Files\iTerminal` in the MSI and the portable zip, `/usr/share/iterminal` in the deb and rpm, the folder of the tar.gz and the portable tar.gz. The licences of the NuGet packages that ship with the app require their copyright notice and licence text to travel with a binary, so the file is part of each release, not an extra.

- **It is generated at publish, not kept by hand.** `Build/ThirdPartyNotices.targets` (imported by `iTerminal.csproj`) runs after `Publish` and calls `iTerminal.ThirdPartyNotices`, a console program (`dotnet run`), which writes the file into the publish folder. Every packaging path publishes first, so they all get it. `LICENSE` is copied from the repository root.
- **It lists the packages of the runtime being published.** The packages are the ones in `obj/project.assets.json` under `net11.0/<rid>` that carry a `runtime`, `native` or `resource` entry: a build-only or compile-only package is not shipped. A Windows publish therefore lists the Windows natives and a Linux publish does not.
- **Each package's licence comes from its nuspec**, in the NuGet cache: the `license` element as an SPDX expression, or the bundled file it names. A package whose nuspec states nothing is listed in `iTerminal.ThirdPartyNotices/Licenses/Overrides.txt` (`<id> <version> <licence>`), and checked by hand against its source repository when the line is added. Without an override the build prints a warning and the notice shows the licence URL.
- **The notice has three sections**: the packages (licence, copyright, project URL); the licence texts the licences name, once each (`Licenses/*.txt`: MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, MPL-2.0, LGPL-2.1, LGPL-3.0 with GPL-3.0, MS-PL); and every licence or notice file the packages and the self-contained runtime pack ship (`LICENSE*`, `NOTICE*`, `THIRD-PARTY*`, `COPYING*`), each text once, with the packages that carry it.
- **A licence the generator has no text for** is a warning, and the notice says where the text is. To add one, put `<name>.txt` in `iTerminal.ThirdPartyNotices/Licenses`.
- **Not included**: the Playwright driver, the Whisper and Ollama runtimes and the other downloads of *Runtime dependencies*. They are fetched when the user asks for them, and each carries its own licence in its own download.
- **The licence reading is ours, not legal advice.** The file is a release obligation for the MIT, BSD, Apache-2.0, MPL-2.0, LGPL and MS-PL terms; a change of licence in a package has to be read again when the package is updated.
- **To check a release**: `tar -tzf` (tar.gz), `dpkg -c` (deb), `rpm -qlp` (rpm), `msiexec /a` (MSI, see below) must list `THIRD-PARTY-NOTICES.txt` and `LICENSE.txt`.

### `iTerminal.Packaging.Linux` — tar.gz, deb and rpm
One command produces, per runtime, `iterminal-<v>-linux-x64.tar.gz`, `iterminal_<v>_amd64.deb` and `iterminal-<v>-0.x86_64.rpm` in `iTerminal.Packaging.Linux/bin/Release` — all self-contained, so the target needs no .NET runtime. The packages install to `/usr/share/iterminal` with `/usr/local/bin/iTerminal` linking to the executable; the tarball unpacks to `iterminal-<v>/`, run `./iTerminal` from it.

- **The formats are written by Packaging.Targets** (NuGet, MSBuild tasks in managed code): no `dpkg`, no `rpmbuild`, so the packages build on Windows as well as on Linux. Its targets have to be in the project being packaged, so `iTerminal.csproj` references it — **only when `LinuxPackaging` is `true`**, which only the packaging project sets. An ordinary build neither restores nor loads it.
- **`iTerminal.Packaging.Linux.proj` is the loop and the names**: for each runtime in `Runtimes` it runs `dotnet msbuild ../iTerminal -restore -t:CreateTarball;CreateDeb;CreateRpm` as its own process (the runtime identifier must not leak into anything else, and the restore has to be for that runtime), then copies the results to the names each format's tools expect. `KnownRuntime` maps a runtime to Debian's and RPM's word for the architecture; a runtime not listed there is refused by name. It is a plain MSBuild file, not in the solution.
- **The Debian dependency list is ours, in `iTerminal.csproj`.** Packaging.Targets' own stops at `libssl1.1` and `libicu70`, which nothing since Ubuntu 22.04 ships — with it the package cannot be installed on a current system at all. Each line is alternatives (`libssl3t64 | libssl3 | libssl1.1`); **a new Debian or Ubuntu release means a new `libicuNN` to add**.
- **The RPM is finished by `RpmFinisher.cs`** (an inline MSBuild task — compiled against .NET Standard 2.0, which is why it is written the old way), run on the copied RPM. Packaging.Targets' RPMs **cannot be installed on a current Fedora**: their signature header holds two placeholder signatures, a SHA-1 and an MD5, and no payload digest, and rpm 6 (Fedora 44) answers "does not verify: no digest" — 0.1.232, the latest, is no different. The task puts the payload's SHA-256 in the main header (`PAYLOADDIGEST`) and writes a new signature header with the header's SHA-1 and SHA-256, the MD5 and the sizes, and no signatures. It also **replaces the dependencies**: the tool's are Fedora package names (`openssl-libs`, `libicu`, `krb5-libs`), which openSUSE does not have, so zypper refused the package. `RpmRequire` in the `.proj` lists shared-library names instead (`libssl.so.3()(64bit)`), which every RPM distribution's packages provide whatever they are called, and ICU — whose library carries its version in its name — as one rich dependency, `(libicuuc.so.80()(64bit) or … or libicuuc.so.60()(64bit))` (the task adds `rpmlib(RichDependencies)` for it). `SkipRpmDependencies` keeps the tool's list out. The rest of the header and the payload are kept byte for byte. `-t:FinishRpm -p:RpmToFinish=<rpm>` runs the task alone, without rebuilding the app.
- **The RPM has a `%postun` that removes `/usr/share/iterminal` on uninstall** (`PostRemoveScript` in `iTerminal.csproj`: `if [ "$1" = 0 ]; then rm -rf /usr/share/iterminal; fi`). rpm removes the files it installed but not the folders, which the tool never lists, so a removed package left a tree of empty folders. `$1` is the number of versions left: 0 is an uninstall, 1 an upgrade, when the folder holds the new version. The app writes nothing there. It is not `find -empty -delete`, which it was first: openSUSE's base system has no `find`, and the script silently did nothing. **The `.deb` gets no such script** — dpkg removes its own folders, and a `.deb` with a `postrm` is kept as "config-files" after `dpkg -r` until it is purged — which is why the packaging project builds the tarball and the `.deb` in one inner build and the RPM in a second, with `LinuxPackagingRpm=true` (incremental, so it costs little).
- **Two switches go on the inner command line because they must reach the referenced projects too**: `DebugType=none`/`DebugSymbols=false` (set in the csproj they cover that project only, and four `.pdb` files came along). The Playwright driver is not in the package at all (see *Runtime dependencies*), so the old `PlaywrightPlatform` switch is gone.
- **`TarballPrefix` starts with a slash**: the task writes `.` in front of it, and without one the top folder is `.iterminal-<v>` — hidden.
- **What has been tested, and where** (`x86_64` only). **Ubuntu 22.04** (WSL): the tarball unpacked and run; the `.deb` installed with `dpkg -i` (its dependencies resolve with nothing extra to install), checked against its own `md5sums`, run, removed. **Fedora 44** and **openSUSE Tumbleweed** (Docker containers): the `.rpm` installed with `dnf` and `zypper` — each pulling in its own ICU (77 and 78) — `rpm -K` "digests OK", `rpm -V` clean, run, removed. In every case the app was started by an ordinary user from the PATH on a pseudo-terminal (`script -qec "stty rows 40 cols 140; timeout 8 iTerminal"` — it draws the menu, the splash and the hot key bar), with its data in `~/.config/iTerminal` and nothing written into `/usr/share/iterminal`. `dpkg -r` warns that `/usr/local` is not empty: the package lists that folder because the link is in `/usr/local/bin`. zypper needs `--allow-unsigned-rpm`: the RPM is not signed.
- **The data folder's parent is asked for with `SpecialFolderOption.Create`** (`iTerminalApplicationBuilderExtension.UserDataRoot`, also used by the vault and the playlists). That first run on Linux is what found it: on an account with no `~/.config` yet, `Environment.GetFolderPath(ApplicationData)` answers with an *empty string*, and "iTerminal" under an empty string is a folder in whatever directory the app was started from — the database, the vault keys and the playlists, a new set in every folder the app was run in.
- What the tool decides and this project does not: the RPM's summary ("iterminal version 1.2.3-0"), and `/usr/local/bin` rather than `/usr/bin` for the link. The licence field is set by this project: `RpmFinisher` writes `RpmLicense` (`MIT`, from `iTerminal.Packaging.Linux.proj`) into the header, replacing the tool's "iterminal License".
- `linux-arm64` is mapped but has not been built here.
