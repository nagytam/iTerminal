# AI features overview

A current-state record of AI features, protocols and tools that could suit iTerminal, what each needs in this codebase, and where it would live. Every item is checked against the source of the commit named under "Sources surveyed". The earlier record, `Documentation/ai-integration-opportunities.md`, is read-only: its items use letters (A to AA) and are cited here as "prior record" with the letter, and they are not repeated. Nothing here is scheduled, and each proposal is for its own `/incremental-improvement` run.

Summary: 42 items, 35 Missing and 7 Partly present (items 4, 15, 16, 19, 20, 37 and 38); none Built. Items 26 to 30 come from survey 6 (2026-11-21), items 31 to 36 from survey 7 (2026-11-22), and items 37 to 42 from survey 8 (2026-11-24).

## Suggested order

Each survey gave its own order for its new items. The four orders are kept as they were written, in survey order, and are not ranked against each other.

Survey 1 (items 1 to 8):

- Item 1, typed answers: small, and it gives the plan types that prior record A, B and S need.
- Item 8, traces of model calls: small and local, and it shows what the other features send.
- Item 6, ACP: the largest gain, but its permission and file methods must go through the approval path first.
- Item 7, instruction folders: useful with no new data flow.
- Item 5, read aloud: local with a system voice, and opt-in.
- Item 3, web search tool: sends queries out, so it needs an opt-in and a visible remote label first.
- Item 2, in-process model: large native packages; only worth it if a model without a server is wanted.
- Item 4, sqlite-vec: pre-v1, and the brute-force index works at the current library size.

Survey 2 (items 9 to 14):

- Item 13, token counts: small and local; it gives the bulk approvals of prior record 3.5 a number to show.
- Item 11, response cache and replay: small; it lets the evaluation harness (prior record AA) and the tests for items 9 and 14 run without a model.
- Item 10, Content Credentials read: local and read-only; a useful label in the image viewer.
- Item 14, Foundry Local: medium; a second on-demand runtime for users who have no Ollama; Windows first.
- Item 12, injection screening: a real safety layer, but the gated licence, the unresearched .NET path and the 512-token limit make it a later choice.
- Item 9, A2A client: larger and network-facing; after the approval path of item 6 exists, and of lower value than ACP for a file manager.

Survey 3 (items 15 to 20):

- Item 17, context reduction: small and local; it caps a history that grows without limit.
- Item 19, other local servers: small; setup text, a probe and a test double, and it helps users who already run llama-server or LM Studio.
- Item 15, native Anthropic provider: medium; it gives prompt caching and the full API, but the meaning search endpoint must stay separate.
- Item 16, approval shape: small, but it pays off only when item 6, 9 or prior record X is built.
- Item 20, Docling: medium; a Python runtime, so later; useful for PDFs with tables.
- Item 18, Microsoft Agent Framework: large and not recommended now; items 16 and 17 supply the parts it would replace.

Survey 5 (item 25):

- Item 25, Phonon 2: medium; a local speech server that a .NET app can call over HTTP, but English only and a Python or container runtime, so it is an alternative to Whisper for English, not a replacement for it.

Survey 4 (items 21 to 24):

- Item 24, licence labels: small and informational, and it is shown before a model is downloaded.
- Item 22, the Responses route: medium; one route that compatible local servers and a remote endpoint could share, tested against a real server first.
- Item 23, a local embedding model: medium; meaning search without a server, but the runtime and the tokenizer need their own checks.
- Item 21, command marks: small in its writing direction; the reading direction does not apply to a host terminal, so the value is limited.

Survey 6 (items 26 to 30), in the order it was written:

- Item 29, evaluators: small, and it is test-only groundwork for prior record AA; the NLP evaluators need no model.
- Item 30, redaction: small and local; it is needed before any terminal output or log is sent (prior record 3.2, H, K and M).
- Item 27, voice activity detection: small and local; it lets a question end on a pause instead of a second Alt+F1.
- Item 26, Kokoro-82M: medium; a local voice for item 5 with an Apache-2.0 model, but it waits on the choice of a voice engine.
- Item 28, Moonshine: medium; a second speech engine for speed on weak hardware, with a language and licence check first.

Survey 7 (items 31 to 36): the order is in its own section, ranked by value to iTerminal.

## Items

### Assistant

**1. Typed answers from the model.** Status: Missing. Size: not estimated in the survey.

A call that asks the model for a typed result (a list of rename rows, one value from a set) and parses it, instead of free text. Every call today is a plain `GetResponseAsync` over messages (`AiChatClientFactory.cs`, `LlmTranslationProvider.cs`). Fits: `AiChatService` and `AiChatClientFactory`, with the plan types that prior record A, B and S need. Data: the same content and the same endpoint as chat, so nothing new leaves the machine. Opt-in: none beyond the AI setting. Caveat: whether Ollama's `/v1` endpoint accepts a JSON schema response format is unverified; the quickstart uses a provider with that support. **Seen in:** [Microsoft Learn quickstart](https://learn.microsoft.com/dotnet/ai/quickstarts/structured-output). Search terms (not found): `GetResponseAsync<`, `ChatResponseFormat`, `JsonSchema`, `AIJsonUtilities`, `response_format`.

**2. An in-process model (LLamaSharp).** Status: Missing. Size: not estimated in the survey.

A chat client that loads a GGUF file in the app's own process. The only local model today is an Ollama server reached over HTTP (`OllamaServer.cs`). Search terms (not found across the tree): `LLamaSharp`, `\bLLama\b`, `gguf`, `llama.cpp`, `InferenceExecutor`; the one `llama` match is a model name in a test. Fits: an `AiProvider` case beside `Ollama`, the native backend as a runtime dependency, and the model file pinned by size and hash as `WhisperRuntimeDependency` does. Data: nothing leaves the machine. Caveats: the README says the backend and model must match the library version; the native size is not stated; whether the library implements `IChatClient` is not stated in the README. Licence: MIT. **Seen in:** [LLamaSharp repository](https://github.com/scisharp/LLamaSharp).

**12. Screen prompt text for injection (Llama Prompt Guard 2).** Status: Missing. Size: not estimated in the survey.

No classifier checks text before the model reads it. Partly present: the chat's system prompt tells the model to treat file names and tool output as untrusted (`iTerminal.Core/AI/AiChatService.cs`, line 30); that is a prompt rule, not a check. Fits: a call on a background task inside `read_panel_file` (`iTerminal.Core/AI/AiPanelTools.cs`) before the text reaches the model, with the label shown in the approval view. A flagged text is shown to the user and is not dropped silently; the approval still decides. The card describes an 86M model with binary labels and a 512-token input, so longer text is split into segments. Data: none once the model is local. The one download from Hugging Face is gated under the Llama 4 Community License: the user logs in, accepts the terms on the model page, and the form asks for a legal name, a date of birth and an organisation. Opt-in: a setting, off by default, and the download is a user action. Caveats (from the card): adaptive attacks can evade it; it flags an attempt to override instructions, not harmful content; its accuracy shifts with the data, so it is one layer and not a control. The .NET runtime path was not researched; the card names Hugging Face Transformers. **Seen in:** [Llama Prompt Guard 2 86M model card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M). Search terms (not found): `injection`, `prompt guard`, `PromptGuard`, `jailbreak`. The word "untrusted" matches only the system prompt above.

**15. A native Anthropic provider (Messages API).** Status: Partly present. Size: M.

`AiProvider.OpenAI` takes any OpenAI-compatible endpoint, and its default base URL is `https://api.anthropic.com/v1/` with the key in `ANTHROPIC_API_KEY` (`iTerminal.Core/AI/AiOptions.cs`, lines 31 and 35). Claude therefore already runs through Anthropic's compatibility layer. Missing: a provider that calls the native Messages API, which the compatibility page recommends for prompt caching, summarized thinking and PDF input. Search terms (the only hits are the two `AiOptions.cs` lines above): `anthropic`, `api.anthropic`; not found: `cache_control`, `/v1/messages`, `prompt caching`, `AnthropicClient`. Fits: a new case beside `Ollama` and `OpenAI` in `AiChatClientFactory.Create`, built on the same background path. The Anthropic adapter for Microsoft.Extensions.AI was not checked (unverified). Limit: the Anthropic API has no `/v1/embeddings`, so meaning search (`media-and-documents.md`) would keep a second endpoint. Data: the same content and the same key as the `OpenAI` provider today; nothing new leaves the machine. Opt-in: the existing `AI:Provider` setting and key. Caveats from the page: the layer hoists system messages, drops prompt caching and does not return thinking, and the page says it is not meant for production. **Seen in:** [OpenAI SDK compatibility](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk).

**16. A shared shape for tool approval (ApprovalRequiredAIFunction).** Status: Partly present. Size: S.

Every write tool in `AiPanelTools` and `AiPanelTools.ArchivesAndFolders` previews first and calls the app's `IAiActionApprovalService`, which shows the app's own dialog (`iTerminal.Core/AI/AiActionApprovalService.cs`). Missing: a type that marks a function as approval-required, returns a request object instead of running it, and accepts a response object. Search terms (not found): `ApprovalRequired`, `ToolApproval`, `FunctionApprovalRequest`, `approval_mode`. Fits: a wrapper applied to the tool list in `AiChatService.BuildTools`, with the request turned into an `AiActionApprovalRequest` for the dialog, so the decision stays in the dialog. Items 6, 9 and prior record X need the same request shape for an external agent, a remote agent or an MCP server. Data: none, since the wrapper runs in process. Caveats from the page: standing "always approve" rules persist in session state and apply to a replacement tool with the same name, so they must not be used for write tools; an unbound approval response is ignored by default in the Python binding, because a replayed response could approve a privileged call. **Seen in:** [Agent Framework tool approval](https://learn.microsoft.com/en-us/agent-framework/agents/tools/tool-approval).

**17. Context reduction for long chats (IChatReducer, ReducingChatClient).** Status: Missing. Size: S.

No reducer. Every turn sends the whole conversation: `AiChatModel.History` is an unbounded `List<AiChatMessage>` (`iTerminal.Core/AI/AiChatModel.cs`), and `AiChatService.BuildMessages` copies all of it into the request. The 50-entry limit in `AiPromptBar` (`HistoryLimit`) covers the recall of typed questions, not the model history. Search terms (not found): `ChatReducer`, `IChatReducer`, `ReducingChatClient`, `UseChatReducer`, `MessageCountingChatReducer`, `SummarizingChatReducer`, `context window`, `token budget`, `compaction`; no `History.RemoveAt` or `History.Clear` in the AI code. Fits: a `ReducingChatClient` in `AiChatClientFactory.Create` beside `UseFunctionInvocation`, or a trim in `BuildMessages`. A tool result must not be cut from its call, so the test sends a tool sequence past the limit. Data: no new destination. A summarizing reducer makes a second model call on the same endpoint, on a background task, so it carries the provider label of item 15 and the same privacy note. Caveats: the class is experimental (MEAI001) in v11.0.0; the behaviour of the message-count reducer is from a search snippet (unverified). **Seen in:** [ReducingChatClient reference](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.ai.reducingchatclient).

**22. The Responses route (Open Responses).** Status: Missing. Size: M.

The OpenAI provider calls only the chat completions route (`iTerminal.Core/AI/AiChatClientFactory.cs`, line 32, `GetChatClient(options.ModelId)`). Search terms (not found): `GetResponsesClient`, `/v1/responses`, `previous_response_id`, `Open Responses`, `openresponses`. The word `responses` matches only a comment in `iTerminal.Core/AI/AiChatService.cs` (line 31). Fits: a second route chosen by an `AI` setting in `AiChatClientFactory.Create`, beside the chat path, with the item types mapped to the messages of Microsoft.Extensions.AI (the mapping was not checked). The specification says an endpoint is compliant when it implements it directly or as a superset, so a compliant server is called the same way. Data: the same endpoint and content as the OpenAI provider, so nothing new leaves; a remote endpoint keeps the privacy label that the OpenAI provider has. Opt-in: a setting, off until chosen. Caveats: the specification is modelled on OpenAI's Responses API and names no licence; its acceptance tests are linked from the page but not described there; the launch partners named in a search snippet (Ollama and LM Studio among them, unverified) would each need a test. Survey 3, item 19 already notes the route on LM Studio's server. **Seen in:** [Open Responses specification](https://openresponses.org/specification).
