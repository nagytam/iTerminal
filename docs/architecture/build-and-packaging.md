### `iTerminal` — composition root
`Program.cs` (top-level statements) wires DI via `AddiConsoleCore()` and `AddiTerminal()`. New services and controls should be registered in `iConsoleApplicationBuilderExtension` or `iTerminalApplicationBuilderExtension`, not in `Program.cs`. `appSettings.json` holds the `FeatureManagement` flags and the `AI` section (`Provider` — `None` (no AI, Ollama is never offered), `Ollama` (the default; the server is downloaded when the start-up offer is accepted) or `OpenAI` for an OpenAI-compatible API — the model id, base URL, `DisableThinking`, prompt-bar height).

### `iTerminal.Installer` — the Windows installer
A WiX Toolset 5 project (`WixToolset.Sdk` from NuGet — nothing to install on the build machine) that produces `bin/Release/iTerminal-<version>-x64.msi`: the app in `Program Files\iTerminal`, a Start menu shortcut, the install folder on the machine PATH (a feature, on by default), an entry in Apps & features, and in-place upgrade.

- **Building it publishes the app** (`PublishApp` in the `.wixproj`): `dotnet publish ../iTerminal -c Release -r win-x64 --self-contained` into `obj/publish`, emptied first. The MSI therefore needs no .NET runtime on the target machine, and always holds the app as it is in the checkout. It is a separate `dotnet publish` rather than an MSBuild task call so the runtime identifier does not leak into the installer project's own evaluation.
- **`Package.wxs` packs whatever was published** (`<Files Include="…**">`), minus `*.pdb` and `*.log`: listing files by name would have to be kept in step with every package the app references. Only `iTerminal.exe` is authored by hand, because the shortcut points at it. A file added to the app's output needs nothing here.
- **In the solution, never built by it** (`<Build Project="false" />` in `iTerminal.slnx`): it is Windows-only, and it publishes and compresses ~240 MB each time. `dotnet build iTerminal.slnx` and `dotnet test iTerminal.slnx` are unaffected.
- **`UpgradeCode` in `Package.wxs` must never change** — it is what lets a newer MSI find and replace an older install (`MajorUpgrade`). The version comes from `-p:Version=`, default `1.0.0`, and is also stamped on the published `iTerminal.exe`; Windows Installer only compares the first three parts.
- **The shortcut starts in Documents, not in the install folder**: the app writes `iTerminal.log` into its working directory (`Logger` — a relative path), and `Program Files` is not the user's to write to. Started from a shell, the log still lands in whatever folder the shell is in; moving it under the data directory is an app change, not an installer one.
- **The wizard has no licence page** — the repository has no licence text, so `WixUI_InstallDir`'s page is skipped by two `Publish` elements. Add a `License.rtf` and remove them to bring it back.
- **Not signed, and no icon**: Windows SmartScreen will warn on an unsigned MSI. Signing needs a certificate (`signtool` after the build).
- Most of the size is the .NET runtime. The Playwright driver is not in the package: the app downloads it on first start (see *Runtime dependencies*).
- **To check an MSI without installing it**, extract it: `msiexec /a <msi> /qn TARGETDIR=<short path>` — a short path, since Windows Installer refuses paths over 260 characters and the Playwright files are deep. The ICE60 warnings in the build are about four font-like files without a language and are harmless.

### `iTerminal.Packaging.Linux` — tar.gz, deb and rpm
One command produces, per runtime, `iterminal-<v>-linux-x64.tar.gz`, `iterminal_<v>_amd64.deb` and `iterminal-<v>-0.x86_64.rpm` in `iTerminal.Packaging.Linux/bin/Release` — all self-contained, so the target needs no .NET runtime. The packages install to `/usr/share/iterminal` with `/usr/local/bin/iTerminal` linking to the executable; the tarball unpacks to `iterminal-<v>/`, run `./iTerminal` from it.

- **The formats are written by Packaging.Targets** (NuGet, MSBuild tasks in managed code): no `dpkg`, no `rpmbuild`, so the packages build on Windows as well as on Linux. Its targets have to be in the project being packaged, so `iTerminal.csproj` references it — **only when `LinuxPackaging` is `true`**, which only the packaging project sets. An ordinary build neither restores nor loads it.
- **`iTerminal.Packaging.Linux.proj` is the loop and the names**: for each runtime in `Runtimes` it runs `dotnet msbuild ../iTerminal -restore -t:CreateTarball;CreateDeb;CreateRpm` as its own process (the runtime identifier must not leak into anything else, and the restore has to be for that runtime), then copies the results to the names each format's tools expect. `KnownRuntime` maps a runtime to Debian's and RPM's word for the architecture; a runtime not listed there is refused by name. It is a plain MSBuild file, not in the solution.
- **The Debian dependency list is ours, in `iTerminal.csproj`.** Packaging.Targets' own stops at `libssl1.1` and `libicu70`, which nothing since Ubuntu 22.04 ships — with it the package cannot be installed on a current system at all. Each line is alternatives (`libssl3t64 | libssl3 | libssl1.1`); **a new Debian or Ubuntu release means a new `libicuNN` to add**.
- **The RPM is finished by `RpmFinisher.cs`** (an inline MSBuild task — compiled against .NET Standard 2.0, which is why it is written the old way), run on the copied RPM. Packaging.Targets' RPMs **cannot be installed on a current Fedora**: their signature header holds two placeholder signatures, a SHA-1 and an MD5, and no payload digest, and rpm 6 (Fedora 44) answers "does not verify: no digest" — 0.1.232, the latest, is no different. The task puts the payload's SHA-256 in the main header (`PAYLOADDIGEST`) and writes a new signature header with the header's SHA-1 and SHA-256, the MD5 and the sizes, and no signatures. It also **replaces the dependencies**: the tool's are Fedora package names (`openssl-libs`, `libicu`, `krb5-libs`), which openSUSE does not have, so zypper refused the package. `RpmRequire` in the `.proj` lists shared-library names instead (`libssl.so.3()(64bit)`), which every RPM distribution's packages provide whatever they are called, and ICU — whose library carries its version in its name — as one rich dependency, `(libicuuc.so.80()(64bit) or … or libicuuc.so.60()(64bit))` (the task adds `rpmlib(RichDependencies)` for it). `SkipRpmDependencies` keeps the tool's list out. The rest of the header and the payload are kept byte for byte. `-t:FinishRpm -p:RpmToFinish=<rpm>` runs the task alone, without rebuilding the app.
- **The RPM has a `%postun` that removes `/usr/share/iterminal` on uninstall** (`PostRemoveScript` in `iTerminal.csproj`: `if [ "$1" = 0 ]; then rm -rf /usr/share/iterminal; fi`). rpm removes the files it installed but not the folders, which the tool never lists, so a removed package left a tree of empty folders. `$1` is the number of versions left: 0 is an uninstall, 1 an upgrade, when the folder holds the new version. The app writes nothing there. It is not `find -empty -delete`, which it was first: openSUSE's base system has no `find`, and the script silently did nothing. **The `.deb` gets no such script** — dpkg removes its own folders, and a `.deb` with a `postrm` is kept as "config-files" after `dpkg -r` until it is purged — which is why the packaging project builds the tarball and the `.deb` in one inner build and the RPM in a second, with `LinuxPackagingRpm=true` (incremental, so it costs little).
- **Two switches go on the inner command line because they must reach the referenced projects too**: `DebugType=none`/`DebugSymbols=false` (set in the csproj they cover that project only, and four `.pdb` files came along). The Playwright driver is not in the package at all (see *Runtime dependencies*), so the old `PlaywrightPlatform` switch is gone.
- **`TarballPrefix` starts with a slash**: the task writes `.` in front of it, and without one the top folder is `.iterminal-<v>` — hidden.
- **What has been tested, and where** (`x86_64` only). **Ubuntu 22.04** (WSL): the tarball unpacked and run; the `.deb` installed with `dpkg -i` (its dependencies resolve with nothing extra to install), checked against its own `md5sums`, run, removed. **Fedora 44** and **openSUSE Tumbleweed** (Docker containers): the `.rpm` installed with `dnf` and `zypper` — each pulling in its own ICU (77 and 78) — `rpm -K` "digests OK", `rpm -V` clean, run, removed. In every case the app was started by an ordinary user from the PATH on a pseudo-terminal (`script -qec "stty rows 40 cols 140; timeout 8 iTerminal"` — it draws the menu, the splash and the hot key bar), with its data in `~/.config/iTerminal` and nothing written into `/usr/share/iterminal`. `dpkg -r` warns that `/usr/local` is not empty: the package lists that folder because the link is in `/usr/local/bin`. zypper needs `--allow-unsigned-rpm`: the RPM is not signed.
- **The data folder's parent is asked for with `SpecialFolderOption.Create`** (`iTerminalApplicationBuilderExtension.UserDataRoot`, also used by the vault and the playlists). That first run on Linux is what found it: on an account with no `~/.config` yet, `Environment.GetFolderPath(ApplicationData)` answers with an *empty string*, and "iTerminal" under an empty string is a folder in whatever directory the app was started from — the database, the vault keys and the playlists, a new set in every folder the app was run in.
- What the tool decides and this project does not: the RPM's summary ("iterminal version 1.2.3-0") and licence field ("iterminal License"), and `/usr/local/bin` rather than `/usr/bin` for the link.
- `linux-arm64` is mapped but has not been built here.
