### Rendering pipeline
Two `JobPriority.Rendering` jobs run continuously and are deliberately decoupled — nothing renders synchronously from a key handler:

1. `ControlRendererJob` walks each `Screen`, collects controls whose `HasStateChanged` is set, renders them into per-Z-order `BufferLayer`s, then `Buffer.Merge()`s them into `MergedLayer` (only when something actually rendered — merging blank new layers would blank the screen).
2. `ConsoleBufferRendererJob` diffs `MergedLayer` against `LastBuffer` line by line (SIMD byte compare), batches runs of changed cells into single `IConsoleDriver.Write` calls, and detects terminal resizes. Both jobs force a full redraw every second as a safety net.

Set the `ITERMINAL_RENDER_DUMPS` environment variable to dump up to 100 frames (buffer contents, render steps, and a reconstructed "what the console actually received" snapshot) to `%TEMP%/iTerminal/renderer-dumps` — the fastest way to debug a visual glitch.

Set `ITERMINAL_STARTUP_TRACE` to a file path to time start-up: `StartupTrace.Mark(name)` calls (process start, `main`, `built`, `run`, the database initialisation, screen initialisation, `first-frame`) are written there as `name;milliseconds since the process started` when the first frame is drawn. Compare builds by the intervals (`first-frame` minus `run`), not the absolute times: process creation varies by seconds from one launch to the next on a machine with a virus scanner. Anything that takes a long time before the first frame belongs on a background task — a process started, or a PATH walked, by a service constructor is paid at every launch. Two warm-ups run beside the rest of start-up: `DatabaseWarmUp` (started first thing in `Main`) pays Entity Framework's first-use cost against a throw-away in-memory database, and `StartupWarmUp` (started once the host is built) builds the slow independent singletons on their own threads while the host builds the rest of the object graph. A service on `StartupWarmUp`'s list must not need a particular thread (not a COM object that wants an STA thread), and a new slow singleton that nothing else depends on is a candidate for it.

The desktop starts the jobs in two waves: the `Rendering` and `Input` jobs first, and every `Background` job (indexers, weather, quotes, drive scans, settings write-back, ...) only once `ConsoleBufferRendererJob.FirstFrameRendered` completes, or after `Desktop.BackgroundJobsGracePeriod` (3 s) if no frame is ever drawn (`render-jobs-started` and `background-jobs-started` in the trace). Twenty threads starting together are CPU the first frame does not get. `WeatherJob` and `OnlineQuoteJob` show their cached value at once and then wait `StartupDelays.FirstNetworkRefresh` (5 s) before the first request, and `DatabaseInitializationHostedService` removes obsolete cache rows 10 s after start instead of compiling three queries on the start-up path: every reader of those caches judges an entry's age itself, so the clean-up is housekeeping, not correctness. A new job that does real work at start belongs in the second wave (the default for `JobPriority.Background`) and, if it reaches the network or the disk, should wait a few seconds more.

`Buffer.SyncLock` guards the layer array; take it around any resize or merge.
