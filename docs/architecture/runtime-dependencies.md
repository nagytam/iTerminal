### Runtime dependencies (`Services/RuntimeDependencies/`, `RuntimeDependencyDialog`)
Components the app needs at run time but does not ship are downloaded into the data folder (`%APPDATA%/iTerminal/runtimes`) by a setup dialog, not packaged. Today that is Playwright — the .NET library is shipped, but its driver (a Node.js runtime and Playwright's JavaScript package, ~130 MB) and the Chromium it drives are not — and Ollama, the local model server the AI bar talks to (see the last bullets of this section).

- **The shipped build must not carry the driver.** `Microsoft.Playwright` is referenced with `ExcludeAssets="build;buildTransitive"`: its build targets are what copy `.playwright` into the output, and the Windows installer and the Linux packages both pack whatever was published. Remove that attribute and every package grows by the driver again.
- **`PlaywrightRuntimeDependency` installs the driver from the NuGet package for the version the build was compiled against** (`Microsoft.Playwright` `<v>.nupkg`, `.playwright/package` and this machine's Node only), then runs the driver's own `install chromium`. The package is checked against the SHA-512 its NuGet catalog entry records before anything is unpacked, and a mismatch is deleted. The library finds the driver through `PLAYWRIGHT_DRIVER_SEARCH_PATH` and the browsers through `PLAYWRIGHT_BROWSERS_PATH`, both set by `Activate()` — nothing has to sit next to the executable. The nupkg is ~210 MB because it carries Node for every platform.
- **An update stays on the build's line** (same major.minor). Playwright's protocol is tied to its library, so a newer line is reported as a note ("1.64.0 is out, but this build uses 1.63.0") rather than installed; adopting it is a rebuild.
- **`OllamaRuntimeDependency` is the same contract for Ollama, from GitHub releases**: versions come from `ollama/ollama` (stable tags only, the same `major.minor` line rule as Playwright), and the program is the asset of this platform (`ollama-linux-amd64.tar.zst`, `ollama-windows-amd64.zip`, `ollama-darwin.tgz`). The download is checked against the `sha256` digest GitHub records for the asset, and an asset without one is refused. Linux ships zstd only, so `ZstdSharp.Port` decodes it (.NET has no zstd in its BCL). Extraction refuses entries that would land outside the folder, and keeps symlinks only when their target stays inside too. A version counts as installed only with the configured model downloaded into it (`model.installed` holds the name); installing pulls the model through `/api/pull` on a server started for the purpose.
- **`OllamaServer` never takes over a server that is already there**: `EnsureRunningAsync` returns at once when the configured address answers (a system Ollama is used as it is), starts `ollama serve` from the data folder only when nothing answers and the address is this computer, and stops only the process it started. `OllamaServerJob` keeps that server up while the app runs and re-checks the AI bar (`CheckAvailabilityAsync`) whenever reachability changes, because the bar checks once when it starts. Only registered when `AI:Provider` is `Ollama`; the end-to-end suite omits the job and replaces the dependency service.
- **An Ollama that was there before iTerminal counts as installed** (`IRuntimeDependency.IsExistingInstall` / `ExistingInstallNote`, default no). `OllamaRuntimeDependency` looks for a running server (`OllamaServer.GetInfoAsync`: version and models, asked during the *check*, never from `InstalledVersion`, which runs on the render thread) and for an `ollama` program on the PATH and the usual per-OS folders (never one inside the data folder). It is complete once the configured model is in it (the server holds it, or `model.installed` says it was pulled). Such an install is never offered an update, is started by `OllamaServerJob` with its own models folder (`ModelsDirectoryFor` returns null, so `OLLAMA_MODELS` is not set), and installing only pulls the model. Tests pass the search folders explicitly (`null` looks nowhere) so a machine with Ollama on it cannot change the result.
- **`GitRuntimeDependency` is installed by the system's package manager, not downloaded into the data folder.** git is found on the PATH (then the standard install folders, which `Activate()` adds to the process PATH — the Windows installer only updates the machine one), and a git that is there counts as an existing install (never offered an update; the system updates it). When missing, `GitInstallPlan.For` picks the first manager present: winget (`Git.Git`, elevates itself), Homebrew, then apt-get / dnf / zypper / pacman / apk. A non-root Linux user goes through `sudo -n`: a password prompt has no terminal to appear on, so a failure says the exact `sudo …` command to run by hand. The version is read with one short `git --version` per program found (cached by path and write time) — `InstalledVersion` is first called when the service is built, not on a key handler. `ListVersionsAsync` is empty: the package manager installs whatever it offers.
- **`FfmpegRuntimeDependency` is the same contract for `ffmpeg` and `ffprobe`**, which the F3 video and image viewers and the FLAC/Ogg/Opus/M4A audio decoders run. It installs through the system's package manager by way of `SystemPackageInstallPlan` (the generic form of `GitInstallPlan`, with one package name per manager): winget `Gyan.FFmpeg`, Homebrew `ffmpeg`, then apt-get / zypper / pacman / apk `ffmpeg` and dnf `ffmpeg-free` (Fedora's own repositories; the full build needs RPM Fusion). Both programs ship in one package but are separate files, so it counts as installed only when **both** are found (PATH, then the winget link and package folders on Windows, `/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin` elsewhere); any that is there already is an existing install, never offered an update. Any 4.x or later is compatible, and a development build (`N-…`, no number) reads as a very high version rather than as missing. `FfmpegAudioDecoder` and `FfmpegVideoDecoderFactory` probe for the programs **once per process**, so `Activate()`/`Invalidate()` reset those answers — without that the viewers keep saying "needs ffmpeg" until restart after a successful install. The viewers' message points at Tools > Runtime Dependencies.
- **The runtime-dependency dialog is shown only when something is missing or can be updated.** At start-up it opens when `ShouldOfferAtStartup` is true (a dependency is missing or newer, and not skipped). From Tools, `RuntimeDependencyDialogCommand.CanExecute` is true only while `RuntimeDependencyDialog.HasWork` is, so the command is unavailable when everything is up to date. When shown, the dialog is a wizard (unless an install is already running) with one `Wizard` step per dependency that needs work (installed, up-to-date ones get no page and are not listed anywhere in the dialog) in list order, so the first page is the first dependency that needs work (`RuntimeDependencyStepPage`: name, state, note, and a tick that starts on), then a last "Install" summary step (`RuntimeDependencySummaryPage`; it refuses to finish with nothing ticked). The overview page (`RuntimeDependencyOverviewPage`) is shown only when nothing needs work (or none is registered), and says so; Enter closes it. The plain list shown while an install runs (`Rows`) lists the same dependencies. The wizard's header ("Step 2 of 3: Ollama") and `StepIndicator` show how many steps there are. Enter/→ next, Backspace/← back, Space ticks the step's dependency (ignored on an up-to-date one), S skips the ticked versions. Finish calls `IRuntimeDependencyService.StartInstall(ids)` / `SkipOffers(ids)`, or the parameterless calls when every one is ticked, and the dialog then shows the plain list with the install log; with nothing to install Finish just closes.
- **`RuntimeDependencyService` owns the list**: `Statuses` is an immutable snapshot replaced whole, the install log is capped, and one install runs at a time (`StartInstall`). Settings keep the newest version seen (`RuntimeDependencies.Latest.<id>`, so the start-up offer needs no network), the skipped version (`…Skipped.<id>`) and the announced one (`…Announced.<id>`).
- **Start-up** (`TerminalScreen.OnInitializeAsync`) opens the dialog when something is missing or newer and not skipped for that exact version. `RuntimeDependencyCheckJob` checks the publisher 30 s after start and every 12 h, and announces a new version once by notification; the offer at the next start and Tools > Runtime Dependencies show it until it is installed or skipped.
- **`OnlineQuoteJob` waits** while Playwright is not installed, and a failed launch calls `InvalidateInstalled` so the dialog offers Chromium again. It no longer runs `pwsh playwright.ps1`.
- The end-to-end suite replaces the service with `SandboxServices.Dependencies` (nothing to install, no offer) and omits the check job, so no run downloads anything or opens the offer over the panels.

### Self-update (`Services/Updates/`, `UpdateDialog`, `UpdateCheckJob`)
iTerminal checks its own GitHub repository (`nagytam/iTerminal`) for a stable release newer than the running build, using the same `GitHubReleaseFeed` as Ollama. The compare is over the whole version, so release builds numbered `0.0.0.<run>` order correctly (the dependencies' `ToString(3)` would drop the build number).

- **`UpdateCheckJob` checks 30 s after start (its start mode defaults to Delayed, not on demand, so an update is offered without opening About) and every 12 h.** The first finding opens `UpdateDialog` on the first screen (resolved on demand, like `ErrorPromptService`, to stay out of the desktop's construction graph); later ones only post a notification. A release is announced once per run, and S in the dialog stores it in `Updates.Skipped` so it is not offered again until a newer one appears. A check that fails (offline, rate limited) offers nothing and says nothing.
- **Windows installs; other systems get a toast naming the release and its address, no dialog.** The Install updates button downloads the release's `.msi`, checks it against the `sha256` digest GitHub records (an asset without one is refused, as for every download here), starts `msiexec /i … /passive /norestart` and then cancels the desktop so the installer can replace the running files. The MSI is per-machine, so Windows asks for administrator rights itself; its `MajorUpgrade` replaces the old install. A release without an `.msi` asset is reported in the dialog.
- **Nothing is published to GitHub Releases by `release.yml` yet** — it only attaches artifacts to the run — so no update is offered until an MSI is attached to a release tagged `v<version>`.
- The end-to-end suite omits `UpdateCheckJob`, so no run reaches GitHub or opens the offer over the panels.
